iOS 认证凭证与会话层的攻击面：收回访问权这件事，为什么多半不在你这台设备上发生

1. 执行摘要

  • 这一族的名字应该叫"访问跟着会话走，不跟着口令走；撤销跟着签发方走，不跟着你的意图走"。前面十六根竖条处理的依次是进来的字节（#118、#122、#123）、进来的调用（#119、#127）、进来的设备与信号（#121、#125、#129）、进来的操作请求（#126）、留下之后被合在一起的内容（#128）、画到屏幕上之后的内容（#130）、到达时以什么样子被你认出的东西（#131）。本篇处理第十七种位置：一次验证通过之后，留下来的那份能力归谁持有、在哪里失效、由谁收回。全系列此前讨论的都是"系统怎么处理数据与设备"，本篇讨论的是别人系统里那些长期以你的名义存在的记录。
  • 核心命题：凭证有持有人，会话有有效期，撤销有签发方——这三个答案常常不在同一个人手里。 你换掉的是凭证，别人握着的是会话；你能操作的是设备，能终止会话的是服务方。这条错位是本族所有伤害的共同成因，也是为什么"我已经改过密码了"在多数服务里推不出"已经没有别人能进了"。
  • 三层切分：P1 凭证层（口令、App 专用口令、恢复码与恢复密钥、通行密钥与硬件密钥、生物识别、一次性验证码）；P2 会话层（验证通过后签发出来的长期能力：Web 会话与令牌、移动端的长期刷新令牌、"已登录设备/信任此设备"记录、推送确认通道、第三方应用授权与 API 密钥、配置与描述文件里携带的服务凭证）；P3 归属与撤销层（谁有权让一次访问停下来：账户提供方、身份供应商、家庭组织者、设备管理方、恢复联系人、平台商店与订阅系统）。缺陷密度在 P2（能力的存续规则由服务方设计，端侧不显示），长期风险在 P3（收回要按签发方走，而签发方不是你的设备），P1 是个人杠杆最大却最少被真正管住的一层。
  • 六个"通过即在场"的触发点 T1–T6。两个最反常识：T1 一次登录即长期在场——验证通过之后留在世界里的是一条有有效期的能力，而不是一次动作；T4 授权即数据通道——第三方登录与应用授权交出的是范围化的长期读取，不是一次性登录，而它的撤销入口位于服务方的网页，不在 iOS 的任何面板里。
  • 一条方法论结论：用 #66 的授权面板、#127 的槽位清单、#128 的来源清单、#130 的通路清单、#131 的对象—显示对照清单做审计，都会漏掉这一族，因为"谁还持有对我的长期能力"既不是本机开关，也不是本机文件——它是别人系统里的一条记录。本篇因此需要的是一张能力持有人清单（谁能以我的身份长期做什么、在哪里可以撤、上次核对是什么时候），这是全系列第五个系统性漏检（前四：#127 槽位、#128 聚合、#130 显示、#131 呈现）。
  • 第六种不提权的伤害形状：未经同意的共同持有。 #126 借系统功能、#127 借你请进来的代码、#129 在别人的系统里你就是本人、#130 被读走的不是数据是画面、#131 借你自己的手；本篇的形状是伤害不发生在某一次动作，而是作为一种长期共存的能力留在系统里——一条仍然有效的会话、一个仍然被授权的应用、一份别人手里的恢复因子。它不需要再次接触你，直到被撤销。这也是全系列第一个以"共存"而不是"事件"为形态的后果：#116 的时间窗模型在此失效的原因不是证据被销毁，而是它不在设备上，也不在某一刻。
  • 端侧可观测性是中低档，且归属跨系统：你这台设备能枚举自己的因子、受信任设备、App 专用口令、自动填充条目与已装配置；枚举不到第三方服务的会话清单、令牌有效期、已授权应用与别人持有的恢复关系。比 #129 略好（至少账户页能列出因子与设备），比 #128/#131 弱（清单本身在别人手里）。由此得到本篇唯一的正向主张：能核对的只有"我这一侧给了什么"，不能核对的是"别人那侧还留着什么"——所以处置必须按服务逐家做，而不是按设备做一次。
  • 与 #129 的关系是本系列最容易混淆的一对：#129 问"谁能通过验证成为我"（因子通道与签约关系），本篇问"通过了之后留下来的那份能力由谁持有、怎么收回"。号码是被冒充的手段，会话是冒充成功的结果。交界：签发与验证通道归 #129，凭证存续与撤销归属归本篇。
  • 与 #124 的关系：那一篇管密钥作为数学与容器对象（在哪存、能不能导出、算法有没有被降级），本篇管凭证作为权利凭证（谁持有它、它能做什么、由谁作废）。一个密钥可能谁都撤不掉但只用于解密，一个令牌可能随时被签发方作废却给了别人读你全部数据的权利。交界：容器与可导出性归 #124，能力与撤销归本篇。

2. 这根竖条补的是哪一块

系列里已有多篇擦到过口令、双因子、自动填充与登录设备，但没有一根从"一次验证通过之后，世界上多了什么、归谁、怎么让它停下来"出发把能力测绘成表。这是第十七根竖条，攻击面子族的第十四个成员（#118 文件与媒体解析器、#119 用户态系统服务、#121 配件与有线连接、#122 文件系统与磁盘结构、#123 网络协议栈、#124 密码学与密钥生命周期、#125 定位与传感器、#126 辅助功能与外设控制、#127 第三方扩展插槽、#128 本地索引与跨 App 聚合、#129 蜂窝订阅与号码身份、#130 显示与屏幕内容捕获、#131 标识与呈现，以及本篇）。

3. 三层切分：凭证、会话、归属

3.1 P1 凭证层——你能换掉的那部分

口令、App 专用口令、恢复码与恢复密钥、通行密钥与硬件密钥、一次性验证码，以及只在设备本地生效的生物识别。这一层的共同属性是可以被属主替换，因此它是个人杠杆最大的一层；它同时也是最容易被当成"全部问题"的一层——换凭证这件事在心理上是可完成的，在系统上常常是不完整的。

三条需要在心里固定住的性质：

  • 凭证的强度与凭证的可撤销性是两件事。 一枚很强的通行密钥可以被它的注册记录长期绑住：只要那一条注册还在 relying party 的账户里，它就是一项能力；删除注册这件事发生在对方的系统里。
  • 一次性验证码不是弱口令，而是一种通道证明（接 #129）：它证明"当下能收到"，不证明"是本人"。把验证码当凭证交出去，等价于把会话交出去。
  • 生物识别在服务端记录里只是一次本地解锁事件。它证明设备解锁过，不证明是谁登录的；把它当作"抗冒充"证据时，这条边界要写清楚（与 #84 的本地边界、#78 的归因限制合读）。

3.2 P2 会话层——真正在场的那部分

验证通过之后签发出来的东西才是访问本身：Web 会话 cookie 与令牌、移动端的长期令牌与刷新令牌、"已登录设备/受信任设备"记录、推送确认通道、第三方应用与网站授权（授权码换出来的长期令牌）、服务账号的 API 密钥、以及配置与描述文件里携带的服务凭证。这一层的规则全部由服务方决定：有效期多长、能不能并发、被异地登录时是否终止、改密时是否失效、设备列表能不能逐个撤。

它是本族的缺陷密度所在，原因不是"实现得差"，而是这些规则从来不是给用户看的：没有任何一个界面把"以我为名的活跃能力"完整列出来。同一族问题在不同服务上的答案差别极大（有的改密即断全部会话，有的只断发起那次改密的会话；有的把第三方授权列在账户页，有的藏在另一个产品域名下）。本篇因此不给任何"某某服务如何"的清单式断言，只给当场核对的方法（§8），因为清单会随版本与服务变更而失效——这与 #130/#131 处理显示规则时的口径一致。

3.3 P3 归属与撤销层——决定"没有了"这三字归谁

撤销动作的真正属主通常是签发方：账户提供方、企业的身份供应商、家庭组织者、设备管理平台、恢复联系人、商店与订阅系统。这一层的规律和 #101/#120/#129 是同一条律的不同界面：关系结束了、人变了、你改了口令，能力不会自动消失；它只在被签发方明确作废时消失。

由此得到本篇的判据（也是全篇最有操作价值的一句）："这件事撤销之后，需要对方配合吗？" 需要——它是一项关系，按 #120/#101 的流程侧处置（工单、书面确认、时限）；不需要——它是本端可当场完成的动作。同一个"取消授权"的意图，在这两类里的成本、时限与可验证性完全不同，把它们混在一张待办里是这一族最常见的失败方式。

3.4 谁必须改

  • 签发方与撤销方不是同一个人是设计事实（#93 的 L1）。个人侧无法用设置项解决，只能把每一次授权当成一项需要未来作废的资产来登记。
  • 平台能做的是把可撤销性往前推：登录与安全性面板里给出设备与已登录应用入口（各版本与地区入口不同，以你的账户页现行显示为准）、推广通行密钥与硬件密钥、提供账户级的恢复与损失保护选项、在配置层面限制高风险动作的会话新鲜度。
  • 服务方能做的是把"会话"当成可审计对象：逐个终止、显示签发时间与来源、并发数上限、改密默认全断、第三方授权列表放在同一账户页。
  • 个人真正有效的动作只有一个：先列能力，再谈凭证。顺序反了就等于只做了一半。

T1 与 T4 是本族最反常识的两格。 T1 意味着"我没有再登录过"不能推出"没人能用我的会话"；T4 意味着你最容易给出去的恰恰是最难收回的——点一次"允许"就换到了一整段可持续读取的能力，而它的撤销需要你去到另一个域名、登录另一个账户、找到另一个页面。T6 之所以重要，是因为它把最常见的自救动作（改密码）变成了一项需要验证才算完成的动作，而不是一个"做过了就放心"的动作。

家庭与组织者角色家庭组织者逻辑缺陷 / 授权混淆Apple + 组织者部分：能看能退，但不能阻止组织者发起的共享动作（#99/#110）
描述文件与设备管理配置发起安装方 + MDM授权混淆组织 + Apple能：清理不再需要的配置文件（通道侧详见 #67/#76）

这张表的净结论：本族可关闭比例很高，可验证比例很低——几乎每一项都有"撤"的动作，但绝大多数撤销的结果只在对方系统里可见。这与 #123 形成对照（那边关不掉但能按协议面推理），也和 #131 形成对照（那边判据在自己脸上，这里判据在别人库里）。所以本篇把逐项验证（撤完之后回看列表是否真的变化、来源是否真的断）放在清单第一位，权重高于任何一次性的"设置收紧"。

6. 七类契约违背

  • M1 凭证即身份。把"持有凭证"当成"是本人"。持有即可用是这一层的默认语义；身份是账户记录里的东西，凭证只是它的入口（#129 M1 号码即身份的近亲）。
  • M2 匹配即归属。用域名匹配决定哪份凭证可用、哪个服务是"同一个"。这是 #122 P4（名字即对象）与 #131 M1（显示即属主）在本族的第三次成立，只是这次后果不是看错，而是把凭证交出去。
  • M3 一次批准即长期读取。点一次允许换到一段可撤销性很差的持续能力。#107 的撤销不对称在此换了对象：数据出口 → 访问能力。
  • M4 改密即收回。把换凭证当成断访问。会话的生命周期是服务方的设计选择，不随你的凭证变更自动传导。
  • M5 因子即属主。谁掌握恢复因子，谁在验证逻辑里就是本人。这是"账户的属主"与"账户的可进入者"两件事被系统混同的地方。
  • M6 恢复即同意。备份恢复与换机继承下来的授权，没有一次对应的用户批准事件（#126 M5 在本族第二次成立）。
  • M7 失败即信息。第五次出现在系列里（#123 N6、#125 M7、#129 M7、#131 M7）：验证码没来、自动填充没出现、通行密钥列表里少了那一项、受信任设备列表少了一台、授权页显示的范围与你记得的不一样——这些缺失与差异本身就是判读输入。反向同样成立："没看到异常"不是一项证据，因为清单在别人手里。

其中 M3、M4、M5 不是软件缺陷，是各家服务的策略与设计选择；因此本篇的可改内容比 #131 更偏流程、比 #129 略偏技术：你改不了对方的规则，但你可以在每一家把"撤销 + 验证"写成两个动作。

7. 后果落点（接 #91）

  • C1 数据与内容外流：长期令牌读走的不是你当时给的那一条，而是整个范围（接 #107 的 E4）。这类外流不可回收，且设备侧没有工件——动作发生在服务方的接口上。
  • C3 账户级接管（不提权）：攻击者不需要碰设备，用自己的会话或以你的凭证进入即可。这是 #129 那一格的存续版本：那里是"成为你"，这里是"继续是你"。
  • C4 服务与费用滥用：开通、扣款、订阅变更、退款与改绑都按会话记账；服务方记录里"已登录且已验证"就是授权前提（接 #89 的支付令牌面）。
  • C6 判定污染：伪造或滥用的登录记录进入账单、工单、审计流水之后，成为"用户本人当时在场"的第三方记录；赔钱的不是设备厂商，处置必须走关系侧（#120/#101/#105 同一路）。
  • C7 归因失效：会话内的每一个动作在服务端记录里都写着"本人"。#78/#116 的形态与时序区分在此失效的原因与 #131 不同——那边是"没有第二种形态"，这边是根本没有一个可以被指认的时刻：共存态不是事件。
  • 可逆性的特殊位置：本族的可逆性取决于签发方的作废规则，而不是你的动作。因此本篇给的不是"如何恢复"，而是"如何证明它已经停了"——每一项撤销都必须落到一个可回看的列表变化上，否则视为未完成（这条与 #111 的"入口消失才算修复"是同一判据换到账户层）。

8. 五步审计法与判定式

判定式："这件事撤销之后，需要对方配合吗？如果需要，我拿到对方的确认记录了吗？"

  1. 列能力，不列开关。按账户逐个写下：谁能以我的身份长期做什么（服务、能力范围、撤销入口所在域名、上次核对日期）。这张清单的单位是"持有人"，不是"设备"——它和 #66 的权限面板、#127 的槽位清单、#130 的通路清单、#131 的对象—显示对照都不是同一张表。
  2. 分三档。本端可撤（换因子、删 App 专用口令、清理配置）／需对方配合（终止会话、撤回授权、注销第三方连接、移除组织者角色）／不可撤销只能换替代（被回收的号码、已泄露的恢复码、别人手里那份副本——按 #129 的方式替换掉依赖）。
  3. 当场降级。高风险账户先做三件事：删不认识的注册项、撤不需要的第三方授权、把号码因子换成不依赖可达性的因子。原则与 #104 一致：一次只做可当场验证的改动。
  4. 把"改密"与"撤权"写成两个动作。任何一次因疑似暴露而改密之后，逐服务执行"终止全部会话 + 重设恢复因子 + 重新核对设备列表"，并把三家最要命的（邮箱、云账户、金融）放在最前——这个次序继承 #129 的"优先替换能改绑账户的那几个"。
  5. 验证与留档。撤完之后回到对方的列表回看是否真的消失；拿不到确认记录的关系项（服务商不回复、只能靠邮件往来）写进 #104 的台账并设复查时限；例外项按 #117 的口径留档，不指望设备侧工件。

顺序纪律：先列后撤。没有第 1 步就动手改密码，是这一族最常见的失败方式——你换掉了 P1，留全了 P2。

9. 设备端可观测性——诚实边界

能当场核对的：我的账户里列了哪些设备与登录位置、开了哪些 App 专用口令、装了哪些描述文件与配置、钥匙串里存了哪些条目、哪些 App 请求过密码自动填充、家庭与共享关系里我是成员还是组织者。

永远核对不到的：别人系统里以我为名的活跃会话与授权——不在 iOS 的任何一个面板里；第三方服务给出去令牌的具体范围与到期时间、并发会话数、异地登录时是否终止；其他服务把我的邮箱或手机号当成恢复因子的那份记录（是别人在持有对我的可进入性，而这条记录不出现在我任何一台设备上）。

位置：中低，且归属跨系统。比 #129 略好（那边连"号码被换走"都不产生设备事件，本族的因子与设备至少可枚举），比 #128/#131 弱（那两族至少对象在自己设备上，本族的核心清单在别人的库里）。因此本篇的审计天然要求离开设备：登录另一家服务、看另一张页面。这是全系列里第一次"处置动作主要发生在浏览器而不是手机上"的层。

10. 加固清单

10.1 个人七项（按可验证性排序）

  1. 建一张能力持有人清单：从"能改绑其他账户"的那几个开始（邮箱、云账户、支付、主密码管理器），逐个记下撤销入口域名与上次核对日期；季度按 #104 复查。
  2. 因子升级，且逐项验证：把口令 + 短信的组合替换为通行密钥或硬件密钥优先（#129 的同一动作，本篇要求替换后回看注册列表），并对每家确认"旧因子是否仍可用作恢复路径"。
  3. 改密与撤权永远成对做：任何改密之后立即执行"终止全部会话 + 重设恢复码 + 核对设备列表"三步，缺一律视为未完成（M4/T6 的直接对策）。
  4. 每季度撤一轮第三方授权与 API 密钥：判据沿用 #107——"它拿到的是那一条，还是全部"；不用的一律撤，撤不下手的记录为例外项。
  5. 恢复材料离线分置：恢复码/恢复密钥不留在同一账户的云笔记或同一邮箱里；分置两份并定期轮换，同时在清单里写明"谁能拿到"。
  6. 公用与他人设备按会话处置而非按登录处置：在他人设备上使用后，除点退出外，回到自己账户终止那一次会话/移除那台设备，并记下时间（T1 的直接对策；这条与 #96 的设备处置互不替代）。
  7. 把"谁是我账户的组织者/管理员"当成一项资产来核对：家庭组织者、订阅共享成员、恢复联系人、备用管理员——每一项都是能力，不是设置（接 #99/#110/#120）。

10.2 组织五项

  1. 离职撤权必须双向且逐项（#120 的技术版）：IdP 会话、SaaS 应用授权、服务账号与 API 密钥、恢复管理员角色、移动端的设备信任记录，逐项终止并留存对方系统的确认记录，不以"已禁用账户"作为完成判据。
  2. 把会话生命周期当成可审计配置：令牌有效期、并发会话上限、改密是否全断、异地登录是否终止——写成组织标准并要求供应商说明，而不是接受默认值。
  3. 禁用共享账户；长期凭证登记属主：App 专用口令、服务账号、集成令牌必须有属主与轮换周期，交接时按 #120 的关系型授权处置。
  4. 高风险动作要求"认证新鲜度"而不是"已登录"：改绑、批量导出、大额支付类操作按时间窗与因子类型二次确认；这条是 M1/M3 在组织侧唯一可落地的对策。
  5. 恢复流程按人复核，不按号码复核：管理员恢复必须有第二人复核与留痕（与 #129 的客服社工面、#97 的冒充面同一条防线），并明确恢复动作等于一次长期授权，要进台账。

11. 十条常见误解

  1. "我改过密码了，所以没有别人能进。" 改密与断会话是两件事，规则由服务方决定（T6/M4）；本篇给的是"成对做 + 回看列表"。
  2. "退出登录就等于撤销授权。" 退出结束的是一个会话，撤销的是第三方应用的长期令牌（T4）。
  3. "清除浏览器数据就清干净了。" 清的是本端副本；服务端的会话与授权记录不受影响（§9）。
  4. "通行密钥很强，所以不会被远程注册。" 强度解决的是凭证被破解，不解决注册项由对方持有这一格（§3.1）。
  5. "恢复码只是我的一份备份。" 每一份副本都是一个持有人；分置同时意味着多人可及（M5/T3）。
  6. "受信任设备列表就是全部。" 它至少不是别的服务的活跃会话清单，也不包含别人账户里以你的邮箱为恢复因子的记录（§9）。
  7. "自动填充没填错就没有风险。" 填充由域与关联域归属决定，你在哪个域上被填什么取决于对方的归属声明（T2/M2，接 #131）。
  8. "App 专用口令不算凭证。" 它是范围明确、常被遗忘、且多数情况下不随主口令变更而失效的凭证（M4/T6）。
  9. "没看到异常登录就说明没事。" 清单在别人手里，"没看到"本身不是证据（M7）。
  10. "这是账户问题，与 iOS 安全无关。" 一半对：设备确实没被攻破；但凭证与会话是本族全部内容的场地，把处置写成"设置收紧"就会漏掉那一半需要离开设备才能做的动作（§9、§10）。

12. 总结

本篇把十七根竖条里最后一个未被测绘的位置——验证通过之后的能力存续层——测绘成表：P1 凭证（个人杠杆最大、可替换性最好的一层）、P2 会话（真正的在场所在，规则全部由服务方决定且端侧不可见）、P3 归属与撤销（"已经没有了"这句话由签发方说，而不是由你说，长期风险在此）。三个不可回避的结论是：这一族的入口不是缺陷而是签发与存续的设计选择（#93 的 L1，故 #79 的缓解成本曲线在此不适用）；这一族的伤害形状是未经同意的共同持有，全系列第一次出现"没有时刻可指认"的后果，因此归因与时间窗模型在此失效不是因为证据被销毁；以及这一族的处置第一次要求主要动作发生在设备之外——列持有人、逐家撤、回看对方列表、拿确认记录。也正因如此，它与 #129、#101、#120 合成本系列的能力与关系侧四篇：#129 问谁能通过验证成为你，#101 问关系结束了凭证为什么还有效，#120 问组织侧的授权由谁收回，本篇问你走了之后，谁还持有对你的长期能力。
