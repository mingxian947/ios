iOS 车钥匙与家庭门禁凭证：钱包里的东西不只影响钱，还决定谁能进门

本文是防御视角的凭证链分析与清点、处置方法，不提供可利用代码，不包含复制门禁卡、中继或任何可照做的物理入侵操作。面向使用数字车钥匙、小区/办公楼门禁、智能家居与租户/房东共享设备的用户，以及需要管理员工门禁凭证的企业与物业场景。各功能名称与可用性随 iOS 版本、车型、门禁系统与地区变化，以实际界面与合同为准。

1. 为什么这是独立的一个方向

#89 已经把钱包凭证列为一条独立通路，并在结尾给出那句判断："钱包凭证是一次物理访问令牌"——评估口径不是"损失多少钱"，而是"谁能进入哪些门、哪些车"。那篇的主语是支付，本篇把主语换成进入权（access rights）：

  • 支付凭证被盗，损失可以拒付、可以补卡；
  • 进入权被盗，损失形态是"人进入了不该进入的空间"——不可逆、且通常不留交易记录；
  • 数字车钥匙与门禁卡的撤销路径不在 Apple 手里，在发卡方（物业、门禁系统、车企、经销商）手里；
  • 这类凭证最容易长期滞留：离职了卡还在、分手了还能进门、车卖了钥匙没注销（#96 的残留物逻辑在物理侧同样成立，而且更严重）。

所以本篇的问题清单是三问：这台设备持有谁的进入权、这些进入权什么时候该失效、失效由谁执行。

2. 把这条链拆开看

┌─ 凭证发放方（决定风险的地方）──────────────────────────┐
│  车企/经销商（数字车钥匙账户与授权关系）                │
│  门禁系统管理方（物业、公司 IT、校园、公寓运营商）      │
│  智能家居生态（家庭组织者、邀请成员、自动化触发条件）   │
├─ 分发与绑定通道 ───────────────────────────────────────┤
│  钱包添加流程（谁批准、用什么因子验证）                 │
│  分享机制（临时钥匙、访客邀请、家庭成员）               │
├─ 设备侧（本文可核验的部分）────────────────────────────┘
│  钱包内的卡片与 Pass、安全元件上的凭证实例              │
│  近场交互与天线、备选电源/断电可用性                    │
│  认证策略：面容/触控/密码/锁屏（#84 的四态在这里适用）  │
├─ 读取侧 ───────────────────────────────────────────────┤
│  门锁/车辆接收端的日志、离线白名单、限额与超时规则      │
└───────────────────────────────────────────────────────┘

三条决定后续所有判断的设计事实：

  1. 凭证的权威在发放方。设备侧抹机、退出登录、删除卡片都不等于后端撤销；很多门禁系统的"已下发凭证"在控制器本地白名单里，不联网就撤不掉（这正是"清除是否可信"的诚实边界，#96 的同一句话在物理侧要重说一遍）。
  2. 分享机制是一等的产品功能，不是一等的治理对象。临时钥匙、访客码、家庭成员邀请创建容易、过期与核对很少有人做。风险主要来自这里，而不是来自漏洞。
  3. 断电与备用通路改变可用性假设。数字钥匙在设备没电、系统降级或离线时的行为（备用卡、实体钥匙、NFC 备选）是安全属性而不是便利属性：备用通路往往是更弱的那一条。

3. 四条通路，按"谁必须失败"分层

通路需要设备被攻破吗需要账户被接管吗现实危害防守杠杆在哪
① 设备丢失/被盗后尝试进入否（要已解锁或认证被绕过，#84）否中—高（进入住所/车辆，可能升级为盗窃）锁屏与认证策略、Wallet 限制项、发放方的单笔/单次认证要求
② 凭证未随关系结束而撤销否否高且持续：离职员工、前任、租客、二手买家发放方流程（这是本篇的主战场）
③ 账户侧被滥用（以"合法"流程重发/加卡）否是高（车企与门禁后台通常按账户身份批准）发放方的验证因子、PIN、线下变更约束（与 #89 第③条同构）
④ 近场协议与中继类风险否否中，取决于发放方是否要求在线校验与距离假设系统选型与配置（属于发放方/厂商责任面）

① 设备丢失：真正起作用的是认证时机，不是钥匙本身

数字钥匙每一次生效通常要求本机认证（部分场景例外，如"快捷模式/Express"类免认证近场——这恰恰是要逐项核对的设置）。所以这条通路的实际风险全部落在 #84 描述的窗口里：设备处于已解锁状态、密码强度不足、短期离开视线（餐厅、代客泊车、试驾、维修、快递代收）。

加固动作与 #84、#99 完全相同（换密码、关闭锁屏必要可见项、限制快捷模式），没有第三条。

② 关系结束后凭证还在：这一条最常被忽略且危害最大

典型清单：

  • 换工作后，公司门禁与停车权限仍在钱包里；
  • 分手/离婚后，对方仍持有你家门禁、你的家庭组织者权限、共享车钥匙；
  • 卖房/卖车/退租时，历史凭证与"分享出去过的临时钥匙"没有注销；
  • 设备转手给家人继续用时，钥匙跟着账户走（#96 的十类残留里 Wallet Pass 不自动消失，同一结论）。

正确处置不是"从钱包删掉"，而是双向：设备侧删除 + 通知发放方在后端撤销并要求确认撤销已下发到读取侧。只删设备侧，控制器白名单里的凭证可能仍然有效；只通知后端，你的旧设备上还有一份可用副本。

③ 账户侧：以合法流程重发凭证

车企与门禁后台的补办/重发流程通常按账户身份批准，验证因子往往包含手机号或邮箱（#89 的结论逐字适用：只要发放方接受这类因子，设备之外的通路就足以拿到进入权）。

可执行项只有三条：核对每个发放方用什么方式批准重发；对高价值个体把居住与车辆凭证的发放方账户换成非手机号主导的验证；把发放方账户列入 #80 的季度核对清单。

④ 协议与中继：这是发放方的责任面，不是你的加固面

与 #89 第①条同构：能被欺骗的是"距离假设"，缓解在系统选型、在线校验与限额策略上。个人可做的只有两件事：知道自家/公司的门禁用的是哪一类系统（有无在线校验、能否远程撤销），以及选车/租房时把"凭证可远程撤销"当成一项配置要求——这条对企业与物业尤其可执行。

4. 端侧清点表（约 20 分钟）

#核对项位置"有"意味着什么
1钱包内所有卡片与 Pass钱包 App逐张记下发放方名称（这是撤销时要联系的对象）
2数字钥匙的免认证/快捷模式设置对应卡片详情 / 设置决定设备被拿走时钥匙是否仍可用（#84）
3分享出去过的钥匙与临时访问车钥匙的"人员/共享"清单、智能家居的家庭成员与邀请、门锁的访客码最容易有陌生人的一类；逐个确认是否已过期
4家庭组织者/管理员是谁智能家居设置里的成员角色、门禁系统侧的管理账户管理员权限可授予也可撤销别人（#92 的"合法擦除权限"同一结构）
5自动化与触发条件自动化里的"到家/离家"、门锁状态触发的动作自动化把一次凭证泄露放大成整屋暴露
6备用物理通路实体钥匙、备用卡、机械钥匙藏点、密码门通常是最弱的一条，且不随数字撤销而失效
7设备流转时的钥匙残留二手机/维修/给家人继续用按 #96 的交出流程：先撤销关系，再处理设备
8通知与锁屏可见门禁/家居类 App 的通知预览"谁在门口""门已开"这类内容本身就是暴露面（#95/#99）

第 3 项与第 6 项是这一场景独有的两项，其余都能复用上系列的清单。

5. 企业与物业视角：四件能控的事

  1. 把进入权当资产登记：发放（谁批准）、当前持有人（含设备形态）、有效期、撤销执行人、撤销确认。离职/退租流程里必须有这一行，且与设备回收流程（#96 的"先撤访问、再注销、后抹除、留台账"）串在同一条线上。
  2. 选型阶段就问三个问题：能否远程撤销？撤销多久生效（是否依赖控制器联网）？重发凭证用什么验证因子？这三问决定后续所有治理成本。
  3. 临时权限要有默认过期：访客码、临时门禁、试驾/施工期钥匙一律设过期时间；无过期的临时权限就是永久的正式权限。
  4. 事件响应顺序：怀疑某人失去可信度（离职、纠纷、设备丢失）时，第一步是在发放方侧撤销并要求确认下发，第二步才是设备侧；反过来会留一个"后端已撤、白名单未同步"的窗口（与 #89 的"先锁卡锁号"是同一个时间轴原则）。

6. 五个常见误解

误解事实
"从钱包删掉就撤销了"发放方后端与读取侧白名单可能仍有效；必须双向撤销并要确认
"设备丢了还能刷开，说明有漏洞"多数情况是免认证的快捷模式与锁屏状态，不是缺陷（#84）
"分享出去的临时钥匙会自动过期"只有设置了过期才会；默认很多系统不会
"车企批准了改手机/重发钥匙"由发放方按账户身份批准，验证因子弱则设备之外即可重发（#89）
"有实体钥匙备份更安全"备用通路通常是更弱的一条，且不随数字撤销失效（第 4 节第 6 项）

7. 一句话结论

进入权与支付权的差别只有一句话：钱没了可以补，家门被开过就开过了。

  • 对个人：做第 4 节的 8 项清点，重点在第 3 项（分享出去的钥匙）与第 6 项（备用物理通路）；处置永远双向——设备侧删 + 发放方撤。
  • 对高价值个体：把发放方账户的验证因子当成 #89 那条原则的延伸，别只加固设备。
  • 对企业与物业：把进入权登记成资产、选型时问三件事、临时权限一律设过期、事件响应先撤销再动设备。

设备侧维持 #80/#84/#96/#99 的既有结论即可——本篇新增的只是"关系结束必须由发放方确认撤销"这一条纪律。
