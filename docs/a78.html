iOS 商业间谍软件归因方法论：如何区分 Coruna、DarkSword 与其他套件

编制日期：2026-10-18 数据来源：Citizen Lab、Google Project Zero、Amnesty International、Lookout、ESET、MITRE ATT&CK Mobile、公开 CVE 情报 性质：防御性安全研究分析（Defensive Security Research），不提供可利用代码

1. 执行摘要

归因（Attribution） 是威胁情报中最困难也最关键的一步：不仅要判断"这是一次攻击"，还要判断"这是谁的哪一款套件"。

归因的价值不是学术的：

归因结果直接带来的行动
确定套件型号可推导其架构弱点（如是否有持久化）→ 选择正确检测手段
确定供应商可预测其能力边界（版本覆盖、漏洞来源）→ 评估剩余风险
确定客户方支持法律保护、外交行动、受害者赔偿
识别复用修补一处可同时防护多处

本文整理一套可执行的 iOS 间谍软件归因方法框架：以 Coruna 与 DarkSword 为主要对照，说明从何种工件出发、按何种顺序、用什么判据做区分，以及归因中最常犯的错误。

2. 归因的四个证据层次

层次 1：工件层（最易获取，价值最低）
        崩溃报告、日志、缓存、文件残留
              ↓
层次 2：载荷层（中高价值）
        模块结构、ABI、加密方案、字符串、代码风格
              ↓
层次 3：基础设施层（高价值，可跨事件关联）
        域名、证书、IP、ASN、注册信息、TLS 指纹
              ↓
层次 4：漏洞层（最高技术价值，最难获取）
        使用的 CVE 组合、组件选择、利用链编排顺序

关键原则：单层次证据不足以归因。可信归因需要至少两个独立层次交叉印证。

3. 层次 1：工件层归因

3.1 从"有什么"判断

观察到的工件指向
落地文件 + 启动项 plist持久化型：Coruna、Pegasus、Predator 类
完全无文件痕迹 + 有可疑网络事件无持久化型：DarkSword 类
大量混淆 JS + 分层载荷下载平台化套件（Coruna）
单次会话 + 极简请求一次性架构（DarkSword）

3.2 工件层的核心判据：持久化

"有没有文件"是最强的第一分流判据（详见 #47、#45）：

是否存在落地文件？
  ├─ 是 → 持久化阵营
  │        → 可用备份扫描 / MVT / IOC 匹配
  │        → 样本可提取，逆向可获得完整技术细节
  └─ 否 → 无持久化阵营
           → 文件扫描完全无效
           → 必须依赖网络日志 + 运行时取证
           → 归因难度大幅上升（往往需要主动研究）

这一条分流决定了后续所有工作该怎么做——也是为什么 DarkSword 的归因主要靠 Project Zero 而非 IOC 匹配。

3.3 崩溃报告的归因价值

报告中的信息可推断
崩溃进程（WebContent / mediaserverd / GPU 服务）链条所处阶段
异常类型（EXC_BAD_ACCESS 地址模式）越界/UAF 类型缺陷
故障偏移可定位到具体函数 → 具体 CVE
二进制映射与 slide环境信息
栈中的模块组合逃逸路径特征

实例化判据：

  • 崩溃发生在 IOGPU/AGX 相关调用栈 → 图形栈逃逸尝试（Coruna 部分链 / DarkSword）
  • 崩溃发生在 JSC 内部 → 初始执行阶段失败（所有 WebKit 链共有，需其他证据区分）
  • 崩溃发生在 mediaserverd → 媒体服务注入（DarkSword 强特征，见 #44）

4. 层次 2：载荷层归因

4.1 结构特征对比

特征CorunaDarkSwordPegasus 类
载荷形态多文件 + 模块清单无文件（内存态）分层 implant（KiteRisa/Carthage）
模块 ABI明确的 init/run/cleanup不适用有成熟 ABI 规范
混淆方式多层 JS 混淆 + 编码依赖无痕，混淆较轻强混淆 + 加密
字符串特征存在可搜索 IOC极少可搜索丰富（历史 IOC 来源）
更新机制版本协商 + 增量下发每次会话全量版本协商

4.2 加密与协议指纹

项归因价值
会话密钥协商算法组合高（同一厂商常复用实现）
自定义消息头字段顺序极高（近乎"签名"级别）
加密库特征（自研 vs 开源）高
消息序列化格式（protobuf/自定义/JSON）中高
HMAC 截断长度等细节选择中（易被复制，不宜单独使用）

4.3 代码风格与"作者指纹"

安全研究中反复验证的现象：同一团队的代码有可识别习惯。

可观察习惯说明
错误处理结构一致性 vs 分散
内存分配模式是否统一走自研分配器
日志/断言残留即使被剥离，常留下痕迹
内部命名缩写模块代号风格
数据结构选型偏好红黑树 vs 跳表 vs 哈希

谨慎使用：风格证据易受"复制他人代码"（如 GHOSTBLADE 复用泄露链）干扰，只能作为辅助。

5. 层次 3：基础设施层归因（最高实战价值）

5.1 关联维度

关联线索方法强度
证书公钥/序列号复用跨域名查找同一公钥或签发模式极高
注册信息（邮箱/电话/名字）WHOIS 历史 + 关联注册高
ASN/托管商偏好是否集中于特定云/小众 VPS中
IP 历史复用被动 DNS 追溯高
TLS 自研栈指纹JA3/JA4 聚类极高（同一实现 → 同一工具）
DGA 算法种子逆向后可预测域名 → 强聚类极高
时间模式运营时区、维护窗口中
目标画像重合受害者集合的相似度中高

5.2 Coruna vs DarkSword 的基础设施差异（可用作分流）

特征CorunaDarkSword
架构层级三层洋葱（前端/中转/后端）扁平 1–2 节点
域名策略分层轮换 + 云服务混入DGA 生成
托管偏好主流云 + CDN + 小众 VPS小众 VPS 为主
会话模式长周期心跳（分层频率）单次短会话
流量伪装模仿合法 App API模仿合法 REST 请求
存活周期数月级运营极短（小时–天级）

实用推论：

网络侧观察到：
  多次长周期心跳 + 域名分层 + 云托管       → 强烈指向 Coruna/平台化套件
  单次短时外连 + 高熵新域名 + 之后完全静默 → 强烈指向 DarkSword 类无持久化
  同目标反复出现"新的单次外连"（重启后重来）→ DarkSword 的架构缺陷特征（见 #55）

5.3 基础设施归因的优势

优势说明
攻击者无法清除与你无关的日志，他删不掉
可跨事件关联一套基础设施服务多次行动
不依赖接触设备无设备也能分析（企业/公民社会常用）
可提供法律价值注册与托管记录可支持司法请求

6. 层次 4：漏洞层归因

6.1 CVE 组合指纹

方法说明强度
CVE 集合完全重合同一套件特征高（但泄露链会打破唯一性）
组件类型组合JSC + GPU + mediaserverd 这种组合较少见中高
版本覆盖范围Coruna 13–17.2.1 是明确特征高
原语实现顺序泄露在前 / 逃逸在中 / 提权在后（通用）低（各家相同）

Coruna 的强特征：5 条链 × 23 CVE × iOS 13–17.2.1 的覆盖矩阵，是极难误认的指纹。

DarkSword 的强特征：JSC DFG GC + ANGLE/WebGPU 两阶段 + mediaserverd 注入 + 无持久化——这个组合在公开案例中独特。

6.2 漏洞复用的干扰（归因最大的陷阱）

套件 A 使用漏洞组合 X
     ↓
A 被分析、样本泄露
     ↓
套件 B（不同厂商）复用 X
     ↓
观察到 X → 归因到 A？  ❌ 错误

GHOSTBLADE 就是这一模式的实例。因此：

漏洞组合是必要但非充分证据。必须与基础设施/载荷层交叉印证。

6.3 从漏洞推断"套件所处供应链位置"

（详见 #77）

观察推断
大量 N-day采购导向，成本敏感
单批高质量新洞独家供给或自研能力强
版本覆盖突然截止供给断点（可预测其后续行为）

7. 完整归因工作流

7.1 推荐顺序（按证据易逝性）

【0】 冻结现场，禁止重启（内存证据最易逝）

【1】 运行时采集
     sysdiagnose / 进程线程 / 网络快照 / 内存（若有能力）
     → 判定：有无落地、有无注入、有无异常执行页

【2】 备份与文件采集
     完整备份 + AFC 提取
     → 判定：持久化 or 无持久化（第一分流）

【3】 网络侧证据
     DNS 日志、TLS 元数据、流量时序
     → 判定：心跳型 or 突击型；提取域名/证书做关联

【4】 崩溃报告分析
     → 定位失败组件 → 反推 CVE → 锁定链条阶段

【5】 样本逆向（若拿到文件）
     → 模块 ABI、协议指纹、加密实现
     → 与已知套件特征库比对

【6】 基础设施关联
     证书公钥 / 注册信息 / DGA 种子 / ASN
     → 跨事件聚类，判断是否同一家族

【7】 交叉印证与置信度评定
     至少两个独立层次一致 → 才给出归因结论

7.2 置信度分级表述（专业惯例）

等级判据表述方式
确认（Confirmed）载荷代码 + 基础设施 + 漏洞组合三重一致，且有厂商样本比对"归因于 X 套件"
高（High）两个独立层次一致，无冲突证据"高度可能为 X"
中（Moderate）单一层次强证据 + 间接支持"与 X 特征一致"
低（Low）仅行为相似或单一弱线索"不能排除 X"
未知工件不足以区分"确认攻击但无法归因"

实践要求：报告必须写明置信度与支撑证据。"归因于某国/某厂商"这类无置信度表述是行业常见错误。

7.3 归因矩阵（实用速查）

观察组合最可能指向置信度依据
落地文件 + 多链 + 长心跳 + 分层域名Coruna / 平台化套件三层一致，高
零文件 + 单次会话 + DGA + mediaserverd 异常DarkSword / 无持久化型架构特征独特，高
崩溃含 IOGPU 栈 + 无持久化DarkSword 类逃逸失败中高
落地 + 泄露链特征与他家重合复用型（GHOSTBLADE 类）需基础设施另证
0-click + 基带/固件层Triangulation 类国家级能力天花板特征，极高
崩溃在 JSC，无其他证据任意 WebKit 链低——不足以归因

8. 常见归因错误

错误说明后果
单一证据下结论只看 CVE 重合泄露链导致误归因
代码风格过度解读把通用做法当特征聚类污染
基础设施短期复用攻击者换基础设施极快时间错配导致漏关联
忽略目标画像差异同一套件服务多客户，目标不同误以为不同套件
把"未检出"当"未发生"无持久化攻击本就不留痕漏判
忽视误投攻击者误把研究员当目标样本被公开，链条归零
混淆厂商与客户套件供应商 ≠ 行动方严重归因错误（政治/法律风险）
公开时机不当提前披露破坏受害者取证损害法律与人身安全

最严重的一条：把"供应商"当成"使用者"。商业套件的供应商是固定几家，而客户是众多机构——归因到套件不等于归因到委托方，后者需要额外的基础设施、时间与目标证据链支撑。

9. 归因能力建设建议

9.1 组织应具备的最低能力

能力为什么必需
≥60 天网络元数据留存唯一攻击者无法清除、且跨越设备重启的证据
备份采集与解析流程判定持久化型攻击
sysdiagnose 采集与初步分析运行时证据（DarkSword 类唯一设备侧解）
IOC/TI 订阅与自动更新基础设施关联
外部取证机构合作渠道多数组织不具备深度逆向能力

9.2 需要外部协作的情形

情形建议对接
目标是记者/活动人士/政要Citizen Lab、Amnesty、Access Now
需要法律效力证据专业数字取证公司 + 法律顾问
发现未知新链条上报 Apple Security + 联系研究机构
需要跨组织关联行业 TI 共享机制

9.3 归因结果的产出规范

一份合格的归因报告应包含：

  1. 证据清单（含采集时间、采集人、哈希）
  2. 各层次独立分析（工件 / 载荷 / 基础设施 / 漏洞分开陈述）
  3. 交叉印证说明（哪些层次一致、哪些存在冲突）
  4. 置信度等级与理由
  5. 替代解释（已排除的其他可能性及排除依据）
  6. 明确区分：套件归因 vs 行动方归因
  7. 影响评估：受影响设备范围、数据类型、时间窗
  8. 处置建议：修补、清除、凭证轮换、监控

10. 总结

#结论
1归因是四层证据的交叉印证（工件/载荷/基础设施/漏洞），单层证据不足以支撑结论
2第一分流判据是"有没有落地文件"——它决定后续所有工作该用什么方法
3基础设施层是实战价值最高的层次：攻击者无法清除、可跨事件关联、不需要接触设备
4漏洞组合会被复用（GHOSTBLADE 现象），单独使用会误归因
5Coruna 的强指纹 = 多链 + 23 CVE + 宽版本 + 三层 C2；DarkSword 的强指纹 = 无文件 + mediaserverd 注入 + ANGLE 两阶段 + DGA 短会话
6必须严格区分"套件归因"与"行动方归因"——后者需要额外证据链
7归因必须按置信度分级表述，"确认/高/中/低/未知"是行业惯例而非修辞
8采集顺序错了等于没归因：运行时证据最易逝，必须最先采集

一句话总结：

归因的真正难点不是"识别恶意代码"，而是在攻击者刻意不留证据的前提下，仅凭他无法控制的那部分痕迹（网络日志、基础设施、受害者自身备份）重建完整链条。 Coruna 留下了文件，因此可被逆向；DarkSword 没留下文件，因此只能被"观测行为"。 两者的归因方法根本不同——这正是防御体系必须同时具备静态与运行时两种能力的理由。
