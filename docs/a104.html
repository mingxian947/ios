iOS 安全季度巡检执行表与台账：把"该做什么"变成"谁做、多久一次、留下什么"

本文是运营方法与模板，不提供可利用代码。面向需要真正落地执行的个人与家庭、企业 IT/安全负责人、以及给客户交付巡检方案的咨询场景。所有检查项都是"在自己或本组织的设备/账户上查看并记录"，不涉及任何第三方设备的探测或取证操作。

1. 为什么这是独立的一个方向

系列里的其它文章回答的是"该做什么"：#80 给了分层防护与月度清单，#85 给了漏洞情报监测与暴露窗口运营，#89/#96/#99/#101/#102/#103 各给了自己那一层的处置动作。

但从"知道"到"做完"之间缺一份东西，而这份东西不是知识：

缺口表现巡检表要解决的
没有判定标准检查完不确定"这样算不算合格"每行给出可当场判定的阈值
没有责任人家庭里"以为对方看过"，企业里"以为 IT 管过"每行有唯一执行人与复核人
没有证据下次巡检从零开始，无法比较每行留可归档的证据（截图/导出/记录）
没有例外台账做不完的项悄悄消失未合格项进例外登记并带关闭期限
没有周期分层要么天天紧张，要么一年什么都不做按周/月/季/年 + 事件触发分层

所以本篇是一个执行件，不是新的一根分析轴：条目全部来自既有文章，本篇负责把它们排成可执行、可归档、可对比的表单。这也是为什么它值得单列——没有这份表，前 103 篇的边际价值会衰减。

2. 五条设计规则（先定规则再抄表）

  1. 每行必须可判定。"锁屏设置是否安全"不合格；"锁屏通知预览是否关闭 + 密码是否为非 4 位数字"才是判定项。
  2. 证据优先于结论。留一份导出/截图比写"已确认"有用：下次对比才有意义（#92/#99 的"固化"习惯在运营侧同样成立）。
  3. 例外要登记而不是清零。真实系统总有做不到的项；有台账的 6 条例外比假装 0 条例外安全得多。
  4. 按危害排序，不按容易排序。第 ① 优先级永远是账户与验证因子（#89/#99/#100），不是设备外观设置。
  5. 周期与触发双轨。季度是节拍，事件触发是补丁；只有季度表会在两次之间出事（见第 6 节）。

4. 例外登记台账（这张表才是让巡检不退化的东西）

建议字段固定，季度追加而不是覆盖：

字段说明反例（不要这样写）
例外编号稳定 ID，跨季度引用无编号，只有描述
主表行号对应第 3 节哪一项"一些设置问题"
未合格内容客观事实"IT 那边没管好"
原因分类能力限制 / 成本 / 依赖外部方 / 争议中一律写"暂时无法"
风险读法用 #90 的档位 + #91 的后果类型一句话定位空白
补偿措施做不到的项旁边做了什么替代空白（最危险的一种）
责任人与期限唯一名字 + 具体日期"相关同事"
上季状态新增 / 延续 / 已关闭 / 复发只写本季
复发标记同一例外第 3 次出现要升级处理从不统计

判读规则：一份健康的台账不会季度间一模一样——它应该有"已关闭"与"新增"。如果连续两个季度完全相同，说明巡检变成了拍照打卡（这是最常见的失败模式，见第 7 节）。

"依赖外部方"这一类要特别标记：发卡行、门禁/车钥匙发放方、运营商、服务商条款（#89/#101/#100/#105）——这些是你唯一不能靠自己关闭的例外，正确的表达是升级路径（换发放方、换验证方式、走客户/员工沟通渠道），不是等待。

5. 分层节奏（避免"每季度一口气做完"）

周期做什么时长来源
每周（15 分钟）只看三件事：更新是否可用、是否有异常登录/验证码通知、有无新装描述文件或证书提醒15 min#80/#85/#103
每月（40 分钟）主表第 3、4、8 项 + 通知与订阅扫一遍（谁在扣费）40 min#80/#89
每季（60–90 分钟个人 / 抽样企业）主表全量 + 例外台账更新60–90 min本篇
每年（半天）长期安排类：#102（遗产/紧急）、#101（进入权全量重审）、#96（设备流转与退役计划）、#100（数据授权重审）3–4 h各专篇
事件触发见第 6 节即时本篇

一句判读：季度是"完整性"的节拍，周/月是"及时性"的节拍。只有季度表意味着最长 90 天的盲区；只有周表意味着没有系统核对。

6. 事件触发清单（不等下一个季度）

触发事件立即加查（按顺序）
收到验证码/登录提醒但自己没操作验证因子 → 设备清单 → 钱包内的卡 → 通知里那次操作的时间点（#89/#99）
设备丢失或被盗服务端优先：标记丢失、改密、锁卡锁号；是否涉及证据再决定是否抹除（#92/#99）
关系变化（分手、离婚、亲属纠纷、纠纷对象获得过访问）完整走 #99 的 12 项 + 门禁/车钥匙发放方撤销（#101）+ 家庭共享与组织者身份（#98/#102）
离职/岗位变化/外包结束撤访问 → 注销 → 抹除 → 留台账（#96 的顺序逐字适用）+ 进入权（#101）+ 订阅归属（#89）
被要求安装描述文件/证书，或"客服"引导操作#103 第 5 节最后一行 + #97 的核验通道；加查根证书与描述文件（第 3 节 5、6 行）
高危 CVE / 在野利用披露版本覆盖 + 关闭非必要暴露面 + 是否给关键人群临时开锁定模式（#85/#90）
医疗事件、失能、去世按 #102 的三条流程走，不要临时发明顺序
换机旧设备按 #96 交出流程；新设备不从风险账户的旧备份恢复（#99 的硬约束）

7. 六个失败模式

失败模式后果对策
只留结论不留证据下季度无法比较，趋势全部丢失第 2 节规则 2；证据目录固定命名与存放
阈值写成"安全/不安全"每次判定标准不同，同一个人两次结果不一样每项写成"能不能当场看到的答案"
例外清零式汇报真实风险被隐藏，问题复发无人认领强制例外登记 + 补偿措施必填
责任人虚设（"IT"）没有名字 = 没有人每行一个具体人名 + 复核人
把 MDM 当成风控以为管住了设备，实际管不到账户、支付、运营商与发放方（#76/#89/#101）主表把"设备外"的行列成独立检查项
巡检与事件响应混用平时不看，出事时按巡检清单一条条念，错过止损窗口事件走第 6 节触发清单；巡检只在平静期做

8. 一句话结论

这份表的价值不在条目，而在四个字段：判定阈值、责任人、证据、例外期限。

  • 个人：季度 60–90 分钟做主表 12 项 + 年度做一次 #101/#102/#96 的长期项；例外台账可以只有三列（内容、补偿措施、下次看的时间）。
  • 企业/小团队：全量 + 抽样，把 3 个数字拿出来——版本覆盖率、暴露窗口 P95（#85）、例外平均关闭周期；这三个数比"我们做了几次巡检"更能说明状态。
  • 一切条目都来自既有文章，本篇不新增攻击面分析；新增的只是执行方式。

一句提醒：如果只能做一件事，做主表第 3、4 行（验证因子与设备清单）——#89/#99/#100 的结论在这里同样成立，账户层的失控不是设备加固能补的。
