iOS 漏洞按引入阶段分类：缺陷是什么时候被写进去的，决定了谁能修、修得多快

本文是防御视角的分类框架与评估方法，不提供可利用代码，不包含漏洞构造、变体挖掘或任何可照做的研究操作。面向需要判断"这条补丁之后同类问题还会不会再来、该向哪个环节提要求"的用户、企业安全负责人与咨询场景。

1. 为什么"何时被写进去"是一根独立轴

系列里已有的分类方式各答各的问题：#2 错在哪个系统层，#81 错成什么形态，#82–#89 打的是谁，#90 对手从哪儿出发，#91 造成什么后果，#92 其中破坏类那一格单独展开。

这六根轴描述的都是缺陷存在之后的事。而咨询里有两个问题它们答不了：

  1. 这个补丁打完之后，同类问题还会反复出现吗？（同一形态在"实现阶段"和"设计阶段"的答案完全相反）
  2. 要减少这类问题，该让谁改流程？（改代码、改默认值、改架构评审、改供应链、改版本支持政策是五个不同的部门）

按引入阶段分一次类，这两个问题就变成可以直接问的表。它也是唯一能预测"复发概率"的轴。

2. 六个引入阶段

阶段缺陷在哪一步被写进去典型形态Apple 侧的修法是补丁能否真正修完
L1 设计与架构写第一行代码之前的信任模型、协议与流程选择离线小额授权窗口、账户即密钥、送达即解析、无法关闭的功能通道、配对信任改设计（下一代机制、新沙箱模型、协议替换）不能。补丁只能收窄，不能消除这个选择本身
L2 实现具体代码里的错误越界读写、UAF、类型混淆、整数溢出、TOCTOU、并发误用（#81 那张表）改代码 + 编译器/运行期加固能，修一处少一处
L3 配置与构建出厂默认值、权限声明、签名与打包环节entitlement 过宽、备份豁免、调试标记残留、描述文件默认允许项改默认值、收紧门禁、重新签名策略半能：默认值能改，已经按旧默认配好的存量不会自动变
L4 演进与回归改动旧代码时带进来的新特性引入的同类缺陷、修复不完整留下变体、功能耦合导致的边界失效再修 + 回归测试与变体清理能，但这是"同一个 CVE 号出现第三次"的主要原因
L5 依赖与第三方别人的代码或别人的配置进入你的产品开源/媒体/字体解析组件、SDK 数据出口、App 侧存储与鉴权选错（#83）、Web 内容Apple 只能替换或加固上游；App 侧要开发者改Apple 修不完：这一格的供给是外部持续的
L6 长尾与弃用产品生命周期政策与硬件世代遗留停更版本的未修问题、老芯片不可改的启动层（#88/#64）、旧固件支持周期不同步（#72）只能靠 RSR/静默修补延长（#61），或干脆不修不能。要么延长支持，要么承认这台设备停在某个能力上限

一句读法：L2/L4 是"错误"，L1/L3/L5/L6 是"选择"。前者的数量会随工程投入下降，后者的数量只会随产品政策改变。

3. 阶段决定谁该改流程

阶段要改的东西现实信号（说明流程没改）
L1威胁建模与架构评审、默认信任范围的取舍同类损失在不同子系统里反复出现，只是换了入口
L2语言与内存安全投入、编译与运行期加固、自动化挖掘覆盖同一子系统内同一形态集中出现
L3出厂默认值评审、签名与发布门禁、配置审计出现"能用但从未需要"的宽权限、豁免项长期存在
L4回归测试、变体清理机制、修复范围定义同一份公告里反复出现同一子系统的相邻编号
L5上游组件治理与 SDK 准入、应用审核与开发者文档漏洞标题里出现第三方组件名、SDK 版本成为影响范围
L6版本支持政策、老机型安全更新节奏、退役沟通设备仍在售卖/使用，但已拿不到安全更新

这张表的价值在于把"苹果不安全"这类判断拆成可提要求的具体环节。企业采购、供应商评估、内部 App 治理，各自该问的行不一样。

4. 阶段 × 修复时长：两类完全不同的时间曲线

  • L2/L4 走"补丁周期"：从披露到 SWU 的延迟与暴露窗口（#61/#75/#85 讨论过），可度量、可运营，你的动作是尽快升级。
  • L1/L6 走"产品周期"：以年为单位，且往往需要换设备或等新架构。你的动作不是"等补丁"，而是接受这一格的长期存在并做风险转移（关键内容不落在这台设备上、离线备份、把资金与账户从手机号验证的通路里拆出来，见 #89/#92）。

混用这两套时间尺度是防御规划里最常见的错误：把 L1/L6 当成"苹果迟早会修"来排期，等于无限期承担；反过来把 L2 当成"结构性问题"放弃跟进，又白丢了最容易拿到的一层收益。

5. 用这根轴读情报（可直接执行）

看到一条新 CVE，先按描述给它贴三个标签再决定动作：

  1. 它是哪一格？ 描述里出现"越界/释放后/类型"多为 L2；出现"策略/默认/权限/可被诱导"多为 L1 或 L3；出现第三方组件名多为 L5；只影响老机型或已停更版本多为 L6。
  2. 它会不会复发？ L2 → 修一处少一处；L1/L3/L5 → 会换入口再来；L4 → 关注同一子系统的相邻修补次数。
  3. 动作落在哪？ L2/L4 落到升级纪律；L1/L6 落到架构性风险转移；L3 落到配置与默认值核对；L5 落到 App 与 SDK 审计（#83 的三层审计法）。

"复发概率"只有这根轴能给出：同一缺陷形态在不同机型/子系统反复出现，通常不是工程能力问题，而是它本来就长在 L1/L5 这类"选择/外部供给"里。

6. 五个常见误解

误解事实
"补丁数量多说明质量好"补丁数量衡量 L2/L4 的产出，与 L1/L6 的长期风险几乎无关
"同一类 bug 反复出现说明没在修"要先看阶段：L1/L5 的同类会持续出现，这是结构与外部供给决定的
"苹果修了就没有了"L3 的存量配置不会自动变（豁免一旦下发仍在设备上）；L6 根本不在补丁范围内
"第三方组件的问题也是 iOS 的问题"是 iOS 的暴露，但要改的是上游与 App 侧；把它塞进设备加固项目会漏掉真正的动作（#83 结论）
"升级了就免疫 L1"设计类缺陷的收窄靠新机制，不靠版本号；版本号解决的是暴露窗口

7. 一句话结论

按引入阶段分完类之后，两件事第一次变得可预测：同类问题会不会再来，和该让谁改流程。

  • 对个人：绝大多数你听到的严重漏洞在 L2/L4，动作就一个——维持升级纪律；真正需要长期策略的是 L1/L6，动作是风险转移而不是等补丁。
  • 对高危个体：L1（送达即解析、账户即密钥）和 L6（机型与版本长尾）是你必须用架构手段对冲的两格，锁定模式与"敏感内容不落在这台设备上"就是为此存在。
  • 对企业：把漏洞台账按 L1–L6 打标签，你会发现相当比例的"未修复项"本来就不该指望补丁，它们属于配置治理、供应链准入或设备退役政策——分错项目的结果是预算全花在升级上，而损失来自配置与依赖。
