Coruna 与 DarkSword 场景下的身份提供商：改密码只是第一步，会话才是最长的尾巴

1. 执行摘要

  • 在组织环境里，"设备被入侵"很快就会变成"身份被借用"：攻击者真正想要的不是那台手机，而是那台手机上已经登录的会话。
  • 核心命题一：会话的生命周期长于密码。 改密码只让"下一次登录"失效，已经签发的令牌仍可能在有效期内继续工作；不处理会话，等于只关了一半的门。
  • 核心命题二：会话的形态不止一种。 浏览器 Cookie、应用刷新令牌、设备注册、SSO 联邦断言、API 长期凭据——每一类有不同的吊销路径，漏掉任何一类都会留下存续项（#159）。
  • 核心命题三：单点登录放大了收益，也放大了损失。 一次登录打通几十个应用，意味着一次会话失守就可能横向覆盖几十个应用。
  • 核心命题四："强制重新认证"是最有性价比的动作。 它比逐个应用排查快、比全量重置影响小，且效果可验证。
  • 核心命题五：处置的完成标准是"下一次认证必然经过新的判断"，而不是"用户说已经退出了"。
  • 一句话结论：把事件处置的第一优先级，从"改密码"改成"让所有存量会话失效，并让下一次认证带上新的条件"。

3. 五类会话载体与各自的吊销方式

载体典型寿命吊销方式常见漏点
浏览器会话 Cookie小时到天服务端会话失效只清了本地缓存，服务端仍有效
移动应用刷新令牌天到月撤销授权 / 刷新令牌轮换只在一台设备上退登
设备注册（受管/受信）长从设备名录移除名录里存在但无人认领
联邦断言（SSO）取决于 IdP 策略IdP 侧会话终止 + 应用重新认证应用侧仍缓存旧断言
API 长期凭据可能无限轮换或吊销存在于脚本与自动化里，无人知道

第五行最危险。 长期 API 凭据通常不挂在任何"人"身上，不在设备名录里，也不会随密码更改而失效；它往往是事件之后几个月仍在活动的那个"存续项"。

4. 为什么"强制重新认证"应当是第一个动作

对比三种处置策略：

策略生效时间副作用覆盖度可验证性
改密码下一次登录小仅密码类高
逐个应用排查天到周中取决于是否查全低
强制重新认证 + 会话失效分钟到小时中（全员需重登）高（覆盖绝大多数载体）高

第三行的关键在"高覆盖 + 可验证"。 你可以直接验证"旧会话是否还能用"——这是唯一一个能自己给出结论的动作。改密码做不到这一点，因为它不触及已签发令牌。

5. 处置顺序：一个可执行的七步

  1. 冻结。 暂停该身份的敏感操作权限（不是停用账号，停用会让日志线索断掉一部分）。
  2. 失效会话。 在 IdP 上终止该主体的全部会话与刷新令牌。
  3. 吊销长期凭据。 逐一确认并轮换 API 令牌、服务账号密钥、Webhook 密钥。
  4. 清理设备注册。 移除无法认领的设备；对可认领的标注属主（#157）。
  5. 收紧认证条件。 对高风险主体临时提高认证强度或限制来源。
  6. 验证。 用旧令牌尝试访问，确认被拒；这一条是"完成"的唯一硬证据。
  7. 记录。 每一步的时间、执行人、影响范围写入决策日志（#184）。

第六步经常被省略。 没有验证的处置，只是一次"相信已经生效"的动作。

6. 条件访问：把"事后处置"前移为"事前约束"

事件之后，真正降低复发概率的不是"再查一次"，而是让下一次认证自动带上判断：

条件作用代价
设备合规状态非受管/非合规设备不允许访问敏感应用需要设备管理能力
位置与网络来源异常地理或网络直接挑战误伤差旅与家庭办公
会话时长上限缩短令牌寿命增加重认证频率
高风险操作二次认证敏感操作单独挑战增加操作摩擦
令牌绑定（设备/密钥）令牌离开原设备即失效兼容性要求较高

这张表在本系列的 #160（组织管控栈可见性与可阻断动作）里已经出现过一次，但那篇讲的是"管控栈能看见什么"；这里讲的是"身份层能拒绝什么"。两者互补，不能互相替代。

7. 四个最容易搞砸的地方

  1. 只在一台设备上退登。 移动应用的退登往往只影响本机，服务端授权仍然有效。
  2. 停用账号代替失效会话。 停用会同时切断你自己查看日志的能力，且恢复时旧会话可能被一并恢复。
  3. 忘记非人类身份。 服务账号、集成账号、共享邮箱，这些往往没有"人"去改密码。
  4. 没有验证就宣布完成。 未验证的"已处置"，会在两周后的复核中变成新的问题。

8. 与业务侧协调的三条底线

  1. 先通知受影响的应用负责人，再执行。 一次全量重认证会造成大面积登录失败，提前告知可以把它从"事故"降级为"维护"。
  2. 为关键岗位准备例外流程。 强制重认证不能把核心业务卡死；例外必须是"有记录、有时限、可复核"的。
  3. 把"为什么现在做"写清楚。 事件期的时间压力很大，但优先级必须能被解释，否则会引发新的内部冲突（#186）。

9. 加固清单（八条）

  1. 会话清单化：先列出五类载体的现状，再动手。
  2. 先失效再改密：顺序反了会留下短暂的混合状态。
  3. 长期凭据单独盘点：脚本、集成、自动化里的密钥，逐个轮换。
  4. 设备名录清零：无法认领的一律移除。
  5. 验证而非相信：用旧令牌实测一次。
  6. 收紧而非关闭：用条件访问替代"一刀切停用"。
  7. 全程记录：执行人、时间、影响面。
  8. 事前演练：强制重认证流程每年至少走一次（#176）。

10. 八条常见误解

  1. "改了密码就安全了。" 已签发令牌不受影响。
  2. "退出登录就断了。" 多数应用只断本机。
  3. "停用账号最彻底。" 会切断你自己的可见性。
  4. "会话过期会自然解决。" 长期令牌的"有效期"可能以月计。
  5. "服务账号不涉及人，不用管。" 恰恰最容易被忽略。
  6. "重认证太扰民，先不做。" 不做的代价通常远高于一次打扰。
  7. "应用侧退登就够了。" IdP 侧会话仍然存在。
  8. "处置完就不用再看了。" 复发判定需要随访（#166 结案随访复发判定与长期暴露管理）。

11. 与既有各篇的接口

  • 与 #132 是"攻"与"守"的两面：一篇讲攻击者怎么用会话，一篇讲你怎么让会话失效。
  • 与 #159 直接衔接：本篇给出执行动作，那篇给出存续项地图。
  • 与 #160 互补：管控栈看得见什么，身份层就拒绝什么。
  • 与 #166 衔接：会话治理需要随访，而不是一次性动作。
  • 与 #184 对接：跨团队执行需要一份统一的决策日志。
  • 与 #188 对接：处置前先固定账号侧留存，否则你无法证明"入侵时有哪些设备"。

12. 总结

身份系统的本质是一组关于"谁现在还能做什么"的判断。事件之后，你要做的不是"重置一切"，而是让这组判断重新成立：

  1. 让旧判断失效：终止会话、吊销凭据、清理设备。
  2. 让新判断带上约束：条件访问、设备合规、令牌绑定。
  3. 让判断可验证：用旧令牌实测，而不是相信"应该生效了"。

把这三步做完，"改密码"才真正有意义——否则它只是关上了一扇本来就没人走的门。
