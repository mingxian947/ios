iOS 推送服务与通知通路攻击面：无交互投递的第一公里

编制日期：2026-10-21 数据来源：Apple 开发者文档（Remote Notifications / Notification Service Extension）、Google Project Zero、Citizen Lab 的推送唤醒相关披露、Lookout、Amnesty International Pegasus 项目、CVE 情报库 性质：防御性安全研究分析（Defensive Security Research），不提供可利用代码

1. 执行摘要

#60 讲清了 0-click 为什么集中在解析器，本文补上那条链路的前半段：攻击者的触发信号与载荷是怎样在没有用户交互的前提下到达设备并被交给解析器的。

推送/通知通路在这一过程中的角色常被误解为"另一个漏洞入口"。更准确的描述是：它是攻击者唯一可以借用 Apple 自有基础设施的投递与唤醒信道，其价值主要在三点：

价值说明对防御的含义
唤醒能力让休眠的目标进程/扩展按攻击者节奏醒来可把 0-click 触发时机压到最有利窗口
合法信道流量来自 Apple 域名与证书，被企业网络默认放行网络侧几乎无法分离（与 #63 盲点一致）
载荷投递通知携带附件时由扩展进程下载并解析把不可信字节自动送进解析器（#37、#60）

三个结论先给：

  1. 推送通路本身不是"0-day 生产者"，而是"0-click 放大器"：它让已有的解析器漏洞更容易在正确时间被触发，且不引入新的可疑外部连接。
  2. 对它的防御不能靠网络检测（会被 Apple 基础设施遮蔽），只能靠削减通知侧的自动解析能力与设备侧配置（锁定模式、预览关闭）。
  3. 归因与取证上，推送通路留下的最强工件是时间线矛盾——"用户没有打开任何应用，但相关进程在此刻活动"，这恰是 #63 里 HUNT-01 的输入特征。

2. 通路的六个组件与信任边界

 提供方（App 后端 / Provider）
        │ ①鉴权：Provider 令牌（基于 APNs 密钥或证书）
        ▼
 APNs（Apple 推送基础设施）
        │ ②按 device token 路由（令牌由 App 注册时向系统申请）
        ▼
 设备：apsd（推送守护进程，维持与 APNs 的长连接）
        │ ③按 payload 的 aps 字段决定行为：alert / badge /
        │   sound / content-available / mutable-content / thread-id
        ▼
 目标 App 或其通知服务扩展（NSE）
        │ ④若 attachment：扩展进程从 URL 下载并处理内容
        ▼
 展示层（UserNotificationCenter）与后台执行窗口
边界谁控制攻击者视角的价值现实难度
① Provider 鉴权应用运营方令牌泄露=可向该 App 全体用户推送与漏洞无关，属凭据治理问题
② device token系统/App拿到目标令牌=可精确投递到单台设备令牌不公开，但可从他处泄露
③ aps 字段解释系统可请求"静默推送""可变内容"等语义需合法 provider 身份
④ 扩展下载与解析App 扩展最直接的 0-click 解析面：URL 由外部可控内容引导依赖具体 App 的扩展实现
⑤ 展示与后台窗口系统/App提供有限执行时间沙箱严格

关键结构性认识：①②属于"谁能让设备醒来"，④属于"醒来后解析谁的数据"。真实利用链通常把 ①② 当调度器，把 ④（或消息/媒体通路）当执行面——这两件事分开看，才能理解为什么"推送漏洞"在公开记录里稀少，而"推送参与利用"的披露反复出现。

3. 五类攻击面逐一评估

3.1 令牌与凭据滥用（非漏洞类，但最常被低估）

场景后果治理手段
Provider 密钥/证书泄露攻击者可向任意/全部用户下发推送，作为唤醒信号密钥轮换、最小权限、按环境隔离
device token 从后端泄露单目标精准投递能力（定向攻击的"地址簿"）token 存储加密、访问审计
token 在日志/分析 SDK 中泄露目标可识别、可关联数据分级与脱敏（与 #50 的画像维度相关）

为什么对国家级/商业投放方有吸引力：它不需要任何 iOS 漏洞就能获得"精确到设备的可达性"。定向攻击最贵的往往不是漏洞，而是"确认这台设备在线且属于目标"这一能力。

3.2 载荷解析面：aps 与附件

载荷要素系统行为攻击面属性
alert展示文本（富文本/本地化参数）文本渲染解析，历史上低风险
mutable-content触发 NSE 处理，允许改写通知内容把外部内容交给扩展进程
attachment URL扩展下载并处理媒体高价值：与图像/媒体解析器同构（#37）
content-available（静默）App 后台获得有限执行窗口执行调度面，非直接内存安全面
thread-id / category会话归类与操作按钮低

工程上最该被注意的一条："下载并解析外部附件"这件事发生在扩展进程里，而扩展进程同样在沙箱内。因此它给攻击者的不是权限，而是入口 + 一次自动执行的解析调用——与 #52 讨论的 BlastDoor 语义相同：自动执行的解析器是 0-click 的经济学基础。

附件下载在设备侧有流量与尺寸限制，且下载通常经 App 的扩展进程完成。这个"限制"本身也是防御资产：任何绕过限制的路径都值得作为高优先级审计目标。

3.3 apsd 与守护进程位置

apsd 是长驻系统守护进程，维持与 APNs 的连接并派发通知。攻击者视角：

属性评估
进程权限系统级但职责窄，直接价值有限
作为逃逸跳板比 mediaserverd（#44）类媒体进程价值低——后者持有更多硬件与文件通路
作为持久化宿主与"注入系统进程存活"模型（#45）兼容，但需内核级能力，成本高
作为隐蔽信道端点有价值：其出站连接天然被信任

结论：apsd 在攻击链里的合理角色是信标与信道伪装，而不是提权落点。

3.4 借用 APNs 作为 C2 的隐蔽信道

设想现实约束判定
完全用 APNs 做双向 C2APNs 不提供应用自定义回传；需借用 App 自身后端可行但等于普通混合 C2
用推送做"任务下发信号"，实际数据走自己的信道只需一次唤醒最合理，也更难检测
借用 Apple 域名/IP 做前置（fronting）Apple 基础设施不可被攻击者占用，但流量混杂其中只能借"同出口/同 ASN"的混叠效果

对防御者的直接后果（与 #59 的网络侧结论并列）：

  • JA4/SNI 类指纹对 Apple 服务段无效：目标设备的 APNs 连接与其他用户的 APNs 连接看起来一样。
  • 单设备稀有性检测仍然有效：不是看"它连了 Apple"，而是看"这台设备在此刻被唤醒后紧接着做了什么"。这就是 HUNT-01 的会话形态翻转特征（#63）。
  • 心跳模型改变：若对手把唤醒交给 APNs，其自有 C2 可以退化为"纯上行、按需短会话"，让长连接心跳检测（#46）失效。这是网络检测侧一个真实的盲点。

3.5 静默推送与后台执行窗口

content-available 给 App 的后台窗口，是"无用户可见痕迹"的活动来源：

可被用于观测痕迹
触发数据采集任务（#42）传感器/权限指示器可能亮起（矛盾信号，见第 4 节）
拉取任务清单再建立自有信道唤醒后立刻出现新的外发连接（HUNT-01）
维持"看起来像正常 App 行为"后台活动统计异常，需设备侧可见性（不存在，P1）

4. 时间线矛盾：这条通路最好的检测抓手

推送通路唯一无法隐藏的东西是"没有用户动作，却有系统活动"。可交叉验证的组合：

组合信号含义数据来源
通知到达时刻 ≈ 外发连接建立时刻唤醒式任务下发网络元数据 + 通知日志
屏幕未点亮但上行字节突增静默推送驱动的采集NetFlow + 设备状态（MDM）
权限指示器亮起但无前台 App后台访问传感器（高危）设备侧观察（人工）+ 用户访谈
目标设备在"无操作"时段集中活动心跳/采集窗口#63 HUNT-01

必须承认的局限：前三项都需要设备侧或用户侧配合，无法批量自动化；企业网络看不到 APNs 载荷内容，也看不到通知到达时间。所以这条通路的检测本质上依赖高危角色的行为约定（例如"发现无来由的通知/权限指示灯立刻上报"），这在 #48 的用户上报路径里是同一件事。

5. 与 Coruna / DarkSword 形态的关系

公开披露对两套体系在推送通路上的具体做法并没有给出可靠细节，因此这里只做结构推断，并标注为推断而非事实：

体系特征（已发布结论）推送通路能提供的增益推断
Coruna：水坑投递 + 落地驻留 + 批量采集（#39、#42、#45）唤醒采集窗口、复用合法信道高收益，尤其便于"定时采集 + 定时外传"
DarkSword：无落地、内存驻留、重启即失效（#43、#45）用唤醒降低自有信道存在感；重启后可低成本再触发收益更大，因为它的信道设计目标是短会话
两者都强调反检测（#47、#55）借用 Apple 基础设施 = 天然降噪与"减少自建基础设施暴露"的洋葱式分层一致（#46）
两者都以 WebKit/媒体面为入口（#39、#43、#58）推送负责时机，不负责漏洞符合"调度器 + 执行面"分工

反过来说，水坑投递（#50）与推送唤醒是互补而非替代：水坑负责"送到人"，推送负责"送到时刻"。防御者若只加固站点而不削减通知侧自动解析，等于只关了半扇门。

6. 为什么平台方很难一刀关停这条通路

关停动作代价现实可能性
禁止通知携带外部附件 URL破坏新闻/聊天/会议类 App 核心体验低（默认不允许，需扩展显式处理）
禁止静默推送后台执行邮件、同步、健康类 App 受损中（锁定模式已部分收紧）
强制通知内容本地化处理服务端逻辑改动大中
限制扩展进程的网络与文件权限附件类通知功能整体退化高（锁定模式方向即在此）

这正是"移除型防御优于检测型防御"（#57）的具体形态：与其等某个解析器出 0-day，不如让扩展进程在高风险配置下没有能力去下载和解析外部内容。对高危个体，可用手段排序：

  1. 启用锁定模式（同时收紧推送、附件与后台执行）（#34、#13）
  2. 关闭非必要 App 的通知，尤其带富媒体/附件的第三方 App
  3. 关闭锁屏预览，减少未解锁状态下的自动渲染与处理
  4. 对极高价值角色：定期重启（#64 的重启重置效力）+ 每日重启后的状态核对

9. 总结

#结论
1推送通路的攻击价值是"唤醒 + 合法信道 + 自动解析入口"，而不是自身产生 0-day
2令牌与 Provider 凭据治理是最省事也最常被忽视的一环：它无需漏洞即可获得精准可达性
3附件类通知把外部字节自动交给扩展进程解析，与 #37/#60 的解析器 0-click 逻辑同构
4借用 APNs 会让自建信道的检测特征退化：心跳检测可能失效，单设备稀有性检测仍有效
5企业网络无法分离 APNs 内容，本通路防御重心必须从检测转向削减自动解析能力
6唯一稳定的观测抓手是"无用户动作却有系统活动"的时间线矛盾，需人员上报机制补位
7水坑与推送互补：一个决定送到谁，一个决定送到什么时刻，只加固一侧等于留半扇门

一句话总结：推送与通知通路是攻击者在 iOS 上唯一可以搭 Apple 便车的投递信道——它不提供权限，却提供"什么时候醒、醒后自动解析什么"，因此防御它的正确姿势不是在网络里认出它（认不出来），而是收紧高风险角色设备上的自动执行与富媒体解析能力，并把检测精力放在它唤醒之后必然留下的行为形态变化上。
