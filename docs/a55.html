Coruna 与 DarkSword 反取证与痕迹清除体系

编制日期：2026-10-18 数据来源：Amnesty International Security Lab、Google Project Zero、Citizen Lab、MVT、OWASP 移动取证指南、公开 CVE 情报 性质：防御性安全研究分析（Defensive Security Research），不提供可利用代码

1. 执行摘要

反取证（Anti-Forensics） 是攻击者与检测者之间最直接的一对一对抗。攻击链的其他环节针对的是 Apple 的防御机制，而反取证针对的是研究人员的分析方法本身。

Coruna 与 DarkSword 在这一维度上呈现"清除已产生的痕迹"与"不产生痕迹"两种范式，但都远超多数人的直觉认知——它们对抗的不是某个杀毒软件，而是 Amnesty 的 MVT 方法论、iMazing 备份解析、以及研究员从崩溃报告中还原漏洞细节的整套流程。

本文系统梳理：

  1. iOS 上攻击者会留下的全部工件类别（含具体路径与价值评级）
  2. 时间篡改、日志清除、缓存净化、崩溃规避四类主动反取证技术
  3. Coruna 的清除体系与已知失效点
  4. DarkSword 的"零生成"体系与残留弱点
  5. 检测延迟（Detection Latency） 这一被低估的战略指标
  6. 防御者如何对抗反取证：证据保全的正确顺序

2. iOS 工件全景图：攻击者必须处理的清单

反取证策略的设计必须以"我到底会留下什么"为起点。以下是完整的工件地图。

2.1 文件系统工件

路径（概念位置）内容对攻击的价值对检测的价值
/private/var/mobile/Containers/各 App 容器⚠️ 沙箱限制中（异常容器可发现）
/private/var/mobile/Library/Caches/用户级缓存⚠️ 常见藏匿点中高
/private/var/mobile/Library/Logs/App 日志低中
/private/var/mobile/Library/HTTPStorages/Cookie/URLCache高（水坑直接证据）高
/private/var/wireless/Library/Databases/通信数据库高（采集目标）中
/private/var/mobile/Library/WebKit/WebKit 存储、localStorage高高
/private/var/root/Library/Preferences/系统偏好⚠️ 需 root中高（新增 plist）
/var/mobile/Library/SMS/短信库高中
/private/var/db/系统数据库（含 DNS、通知）中高高
/private/var/mobile/Library/Logs/CrashReporter/崩溃报告极高（最怕）极高

2.2 网络相关工件

工件位置存活期攻击者可控性
DNS 缓存内核/服务缓存短（TTL + 重启）✅ 可清除（重启即清）
网络连接历史系统网络日志视配置⚠️ 部分可控
路由器 DNS 日志防御者侧长期❌ 完全不可控
ISP/企业出口日志防御者侧长期❌ 完全不可控
CDN 访问日志若使用 CDN中长期❌ 不可控（但难归因）

2.3 备份可捕获工件（关键类别）

备份类型包含内容攻击者可见性
iCloud 备份App 数据、消息、照片索引、部分设置⚠️ 攻击者无法阻止用户备份
iTunes/Finder 未加密备份广，含 Keychain❌ 严重暴露面
iTunes/Finder 加密备份全部但需密码✅ 相对安全
iMazing / AFC 直接提取文件级全域⚠️ 取决于是否 root

战略问题：用户可能在被入侵后主动做了一次备份，把攻击痕迹完整复制到攻击者无法控制的地方（iCloud 服务器、家人电脑）。这是任何反取证技术都防不住的路径。

2.4 运行时与内核工件

工件说明存活期
进程/线程表异常线程可见至进程终止
内存中的代码与字符串可被转储搜索至覆写/断电
文件句柄表打开的可疑文件至关闭
内核函数指针修改hook 痕迹至重启
页表异常映射驱动侧修改痕迹至重启
功耗/性能统计异常活动记录较长（Analytics）

2.5 元数据与副作用工件（最易被忽视）

工件说明
文件 mtime/ctime/atime落地时间证据
SQLite WAL/journal 残留数据库被读写的痕迹
iOS 分析上报（到 Apple）设备遥测可能含异常，攻击者不可见也难清除
App 使用统计Screen Time / 使用记录异常
通知历史攻击触发过的系统提示
电池/性能曲线异常 CPU 活动的物理证据

3. 主动反取证技术分类

3.1 时间篡改（Timestamp Manipulation）

手法说明
回溯 mtime/ctime把文件时间设为系统安装/最近 OTA 时刻，绕过"新增文件"式检查
批量统一时间多个工件设为同一时间点，模仿合法批量写入
避免未来时间戳明显的未来时间戳是低级失误

检测者应对：stat 全量导出后检查时间分布的统计异常；与安装时间基线比对；注意 ctime 无法被普通工具设为早于文件首次创建（但 root 可操作）。

3.2 日志与记录清除（Log Scrubbing）

目标手法难度
App 日志删除 /Library/Logs/ 相关条目低
系统分析日志清理 Analytics/PowerLog 相关条目中
Crash Report删除对应报告（最高优先级）低（root 后）
WebKit/HTTPStorages清理水坑访问痕迹低
Safari 历史删除特定记录或全站历史低
DNS 缓存触发刷新/等待过期低
通知数据库清除异常通知记录中

关键：清除本身可能留下痕迹（如批量删除导致 atime/mtime 异常、SQLite 页变化）。完美的清除极难实现。

3.3 缓存与浏览痕迹净化

对象为什么重要
HTTPStorages / Cookie 库直接证明访问了水坑域名
WebKit localStorage / IndexedDB水坑探测阶段可能写入标记
Safari 历史记录（History.db）最强时间线证据
预加载/预测缓存用户未点击也可能被记录
Web 推送/通知注册攻击者可能注册了推送，属持久痕迹

3.4 崩溃规避（Crash Avoidance）

这是最有战略价值的一类反取证。原因：

一次进程崩溃
   ↓
生成 Crash Report
   ↓
包含：异常类型、故障地址、调用栈、二进制与共享缓存映射
   ↓
研究员据此可推断：漏洞组件、偏移、利用阶段、甚至复现思路
   ↓
整条链条价值归零

攻击者对策：

措施说明
保守中止策略探测到不确定状态即停止，不冒险执行可能失败的步骤
异常处理器安装在提权后接管异常，防止生成报告
禁用 core dump减少内存快照落盘
版本严格匹配不在未测试的版本上尝试
崩溃后清理若崩溃已发生，重启后立即清除 CrashReporter 目录

DarkSword 因单次会话不可重来，中止策略远比 Coruna 保守——半成功对它意味着彻底失去这次机会。

3.5 一次性自毁（Self-Destruct / Burn）

触发条件行为
C2 下发烧除指令清除所有落地文件、启动项、痕迹，卸载
检测到分析环境立即清除并不再活动
证书/签名异常判定被中间人分析 ⇒ 中止
目标设备超出预期（非目标画像）主动清除
授权到期按运营周期自动过期清除

4. Coruna 的反取证体系

4.1 定位：持久化后的痕迹管理

Coruna 会落地、会持久化（详见 #45 对比），因此其反取证是主动清除型：产生 ⇒ 管理 ⇒ 择机清除。

4.2 具体策略

层面Coruna 的做法
落地位置集中在少数低关注路径（缓存类目录），便于一次性清除
命名伪装文件名模仿合法系统/缓存产物，避免直接字符串匹配
时间戳设为系统安装或近期合法写入时间
痕迹清理任务作为任务队列中的一个可调度模块，定期执行
浏览痕迹净化清除水坑访问相关的 HTTPStorages/WebKit 条目
崩溃规避探测失败即中止；崩溃报告作为高优先清理目标
自毁支持远程下发烧除，含完整清除清单

4.3 Coruna 的结构性弱点（已知失效点）

弱点说明现实后果
清除有覆盖盲区大量低概率路径难以全部处理留下残留，被 AFC/iMazing 发现
备份时竞态用户在清除前做了备份痕迹被复制到攻击者不可控处
文件被复用后残留已删除文件的块可能被恢复取证可恢复
基础设施泄露域名/证书复用归因突破，比设备侧更容易
模块驻留时间长内存捕获窗口宽运行时取证有效

关键事实：Coruna 系列之所以能被 Citizen Lab 大规模公开分析，正是因为它落地——分析人员从样本文件出发即可完整逆向。这是主动清除型架构的宿命代价。

5. DarkSword 的反取证体系

5.1 定位：零生成（Zero-Generation）

DarkSword 的根本策略是让清除动作变得不必要：

工件类别是否产生需要的清除
落地文件❌ 不产生无
启动项❌ 不产生无
持久配置❌ 不产生无
修改过的数据库❌ 通常不改写无
内存中代码✅ 产生需覆写/释放
内存中数据✅ 产生需覆写/释放
网络请求✅ 产生不可控（防御者侧留存）
浏览痕迹✅ 部分产生（访问水坑页面）需清除或依赖重启

5.2 技术实现

措施说明
匿名内存页执行不通过文件映射，文件系统中完全无对应记录
用后覆写释放前用零/随机覆写缓冲区，降低内存恢复可能性
加密驻留代码在内存中为密文，执行时按需解密，缩短明文窗口
短生命周期模块执行完立即卸载
禁 core dump防止崩溃时内存落盘
保守中止不确定性高时直接放弃，避免生成崩溃报告

5.3 "重启即灭"：免费的反取证

DarkSword 最强大的反取证能力是它不需要做任何事：

目标重启设备
   ↓
DRAM 断电，所有代码与数据物理消失
   ↓
内核 hook 复原、页表复原、进程表复原
   ↓
即使防御者此后取得完整设备镜像，也找不到任何东西

这构成一种时间维度的反取证：攻击者不需要预测防御者的检测手段，只需要目标正常生活（几天重启一次设备）。

5.4 DarkSword 的残留弱点

弱点说明防御者可利用
DNS/流量日志完全不可控✅ 最主要的检测途径
水坑页面痕迹重启前的浏览记录、HTTPStorages⚠️ 短窗口内可捕获
运行时窗口未重启时内存可取证✅ 需主动、及时取证
重复投递每次重启后需重新攻击 ⇒ 网络事件多次出现✅ 频次本身是信号
失败崩溃若利用失败仍可能生成报告⚠️ 泄露链条细节
基础设施指纹DGA 若被逆向则可预测✅ 提前阻断

最有意思的一条：DarkSword 的"必须反复投递"这一架构缺陷，恰恰创造了一个可被检测的模式——同一目标设备在重启后多次解析新的低信誉域名。频次异常本身成为特征。

6. 对比：两种反取证范式

维度Coruna（清除型）DarkSword（零生成型）
设计哲学产生后管理消除从架构上不产生
文件系统需清除，有盲区无需处理
启动项需删除不存在
备份可捕获✅ 可被捕获（若竞态失败）❌ 不可能
崩溃报告需删除需规避（架构更保守）
时间戳伪造需不需要
内存痕迹长期驻留，宽窗口短驻留 + 覆写
网络痕迹不可控不可控（且是其主要弱点）
抗静态分析弱（样本会被提取逆向）强（无样本可提取）
归因难度中高
主要暴露点文件残留 + 基础设施网络日志 + 运行时窗口

核心结论：

最好的反取证是不产生证据。 Coruna 的整套清除逻辑，本质上是在弥补架构选择（持久化）带来的代价； DarkSword 通过放弃持久化，一次性消除了大半攻击面——这是架构决策优于技巧实现的典型例子。

7. 检测延迟：反取证的战略指标

7.1 定义

检测延迟 = 入侵首次发生 → 被外部发现的时间差
体系典型检测延迟原因
早期持久化型（初代 Pegasus）短（数周）大量文件痕迹、被 App Store 移除事件触发调查
Coruna中（数月级）落地但清除较好，依赖备份与基础设施线索
DarkSword长（往往至研究主动分析才发现）设备侧几乎无痕，依赖 Project Zero 这类主动逆向

7.2 为什么检测延迟如此重要

影响说明
受害时长延迟期内攻击者可无限积累数据
证据质量延迟越久，易逝证据（内存、缓存）消失越多
归因可行性基础设施若已更换，回溯难度剧增
修补时机漏洞可能已被多个客户复用才被发现
法律可用性取证链断裂，难以支持法律/外交行动

7.3 反制检测延迟的手段

手段原理
保留网络日志 ≥60 天攻击者无法清除，是唯一能跨越延迟的证据
建立行为基线让"异常"在发生时即可识别，而非事后重建
前置取证快照入侵前采集基线，事后差异比对
缩短取证启动时间从"怀疑"到"取 sysdiagnose"的流程要快（内存证据会随重启消失）
主动猎杀（Threat Hunting）不等待告警，周期性对高危设备做内存与网络检查
情报共享一家发现可立刻保护所有潜在目标

8. 防御者实操：对抗反取证的取证流程

8.1 铁律：证据易逝性排序

最易逝 ─────────────────────────────────── 最耐久
内存/运行时 → DNS 缓存 → 浏览痕迹 → 文件残留 → 网络侧日志 → 攻击者基础设施
   ↑                                                          ↑
必须最先采集                                            攻击者完全无法清除

违反顺序 = 永久失去证据。

8.2 正确采集流程

【第 0 步】 冻结现场
   - 不重启、不关机、不"恢复出厂"、不升级系统
   - 保持当前解锁/锁屏状态（记录之）
   - 断网用飞行模式，而非关机
   - 拍照记录设备外观与屏幕状态（含时间、电量）

【第 1 步】 运行时证据（分钟级易逝）
   - sysdiagnose 采集
   - 进程/线程/网络状态快照
   - 如具备能力：内存转储
   - 记录 uptime（判断是否发生过重启）

【第 2 步】 短生命周期设备侧证据
   - 完整未加密备份（含 WebKit/HTTPStorages/CrashReporter）
   - iMazing/AFC 文件系统级提取
   - 记录所有可疑文件的 stat（mtime/ctime/atime/size/hash）

【第 3 步】 网络侧证据（攻击者不可控）
   - 路由器/防火墙/网关 DNS 日志
   - 出口流量元数据、TLS 会话记录
   - 若企业：SIEM 中的历史告警与流量
   - 立刻导出，勿等日志轮转覆盖

【第 4 步】 云侧证据
   - Apple ID 登录历史、受信设备列表
   - iCloud 备份时间线（可能含攻击期快照）
   - 密钥/凭证使用异常记录

【第 5 步】 完整性固定
   - 所有证据 SHA-256 哈希
   - 记录采集时间、采集人、设备状态
   - 建立证据链文档（法律场景必需）

8.3 识别"已被反取证处理"的迹象

迹象含义
可疑的时间断层某目录内所有文件时间集中在同一秒 ⇒ 批量篡改/删除
异常的干净长期使用的设备缓存/历史空得反常
uptime 与声称的使用不符目标称每日使用但设备刚重启
CrashReporter 目录缺失可能被整体删除（正常设备会有零星报告）
备份与实时状态矛盾备份中存在、设备上已消失的文件 ⇒ 清除动作的证据
DNS 日志有可疑解析但设备无痕典型的无持久化攻击 + 已清除特征
SQLite 页碎片中含已删除记录清除逻辑只删索引未清理页

"备份里有、设备里没有"是最有力的反取证证据之一——它证明曾存在过被刻意移除的东西。

8.4 反制时间篡改

方法说明
ctime 交叉验证文件系统 ctime 与 mtime 不一致是常见破绽
依赖关系检查某文件声称创建于系统安装时，但其依赖组件晚于该时间
包管理器/安装记录比对合法安装应有对应记录
备份差分多次备份间同一文件时间戳变化 ⇒ 被改写过
文件系统内部元数据APFS 快照与克隆信息可提供独立时间源

9. 分场景建议

9.1 高危个人（T0）

  • 每日完整重启（注意：诊断前不要重启——先采集，后重启）
  • 保持路由器 DNS 日志开启（这是唯一能追溯攻击者的低成本手段）
  • 定期做备份并离线留存（防止攻击者清除后无处可查）
  • 记录设备异常：发热、耗电突增、异常延迟、意外重启

9.2 组织安全团队

  • 建立 iOS 事件响应 Runbook，明确"先内存、后备份、勿重启"顺序
  • 对 T1 以上人群保留 ≥60 天网络元数据
  • 预先与外部取证机构建立合同（多数组织不具备 iOS 内存取证能力）
  • 定期做威胁狩猎演练（含"攻击者已清除痕迹"的假设场景）

9.3 站点运营方

  • 页面内容哈希基线 + 变更告警（发现被水坑注入）
  • 保留访问日志（含完整 UA、时间序列）——攻击者无法清除你的服务端日志
  • CSP + SRI 降低注入生效概率

10. 总结

结论内容
1. 反取证对抗的是方法论，不是产品真正的对手是 Amnesty 的取证方法论、MVT 的工件解析、研究员的崩溃报告分析
2. 架构决定反取证成本不产生痕迹（DarkSword）在根本上优于精心清除痕迹（Coruna）
3. 攻击者无法清除的证据是主要突破口网络侧日志、iCloud/本地备份、Apple 遥测、攻击者自身基础设施泄露
4. 崩溃报告是最高价值工件攻击者对其极度警惕；防御者应把它作为优先巡检对象
5. 采集顺序错了就等于没采集内存证据先于备份，备份先于网络日志导出——反了就永久失去
6. 无持久化架构的软肋是频次每次重启都要重新投递，重复的"新域名解析"模式本身即特征
7. 检测延迟是核心战场缩短"怀疑 → 取证"的时间差，比增加任何检测规则都更能对抗反取证
8. "过于干净"是证据缓存/历史异常空、时间戳断层、备份与设备不一致——这些都是被处理过的痕迹

一句话总结：

反取证的军备竞赛已经证明：能消除的证据总有办法留下，不能消除的证据一定留下。 因此防御投资应集中在攻击者碰不到的地方——网络侧日志、离线备份留存、以及入侵前的基线快照。
