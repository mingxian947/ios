代码签名、库验证与 dyld 加载链：iOS 应用完整性的边界在哪里失效

编制日期：2026-10-24 数据来源：Apple Platform Security 与代码签名文档、Apple 开源 dyld/security 组件、Google Project Zero 关于签名与库验证的公开研究、Citizen Lab 关于商业间谍软件注入手法的披露、CVE 情报库 性质：防御性安全研究分析（Defensive Security Research），不提供可利用代码

1. 执行摘要

iOS 上"只能运行经过签名的代码"通常被当作一条绝对事实，但它在防御分析里的正确表述是：任意未经 Apple 认可的字节不能成为可执行页，但已签名的代码可以被合法地组合、替换参数、注入与劫持。攻击工程里大量"看起来违反直觉"的动作，其实都发生在这一句话留下的缝隙里。

四条结论：

  1. 签名不是"一次校验"，而是一条链：CDHash/TeamID → 描述文件与 entitlements → AMFI 授权 → 内核页级校验（cs_validate）→ 库验证（library validation）→ dyld 闭包与共享缓存。链上每一环的判定条件不同，"签名有效"与"行为受限"是两件事。
  2. 真实入侵里最常见的滥用不是"绕过签名"，而是借用合法签名的宿主：注入到一个已签名、已授权、已联网的进程，让它替攻击者执行采集与外发。这与 #66 的"路径 B（劫持已授权宿主）"是同一次攻击的两个视角。
  3. 共享缓存与 dyld 闭包把"加载"变成了高度受控的操作，因此历史上应用完整性缺陷集中在特殊豁免：允许动态加载的场景（扩展、WebView/JS 引擎、脚本与配置驱动的组件、企业托管组件）以及内核校验的旁路条件。
  4. 对防御方，签名层提供的最大价值不是阻止入侵，而是约束入侵者必须借用已有能力——这个约束是可审计的：被注入的进程会表现出"能力使用与用户意图不一致"（时间线矛盾，#65/#66/#71 的通用模板）。

2. 校验链与判定者

构建期
  开发者签名（CDHash + TeamID）+ 描述文件（entitlements）
        │
安装/启动期
  AMFI：这个进程可以带哪些 entitlement？是否需要 kill？
        │
执行期（每一次）
  内核：页缺失时校验该页哈希是否属于该签名（cs_validate）
        │
加载期
  library validation：允许加载的库是否属于同一 TeamID/经豁免？
        │
  dyld 闭包 + 共享缓存（系统库固定；App 私有 framework）
        │
运行期
  JIT/可写可执行页：需要显式 entitlement（与 #44 的 JIT 风险同源）
环节判定问题攻击者最优解需要的能力等级
签名有效性这页字节属于这个可执行文件吗不伪造签名，而是让已签名进程去执行攻击者数据代码执行原语
entitlement该进程被允许做什么选择 entitlement 多的宿主（系统服务、扩展宿主）提权或注入
AMFI是否放行特殊加载走被豁免的加载路径中—高
库验证能不能加载外来库同 TeamID 的合法库、或存在豁免标志中
dyld 闭包依赖关系能否满足借用系统已有组件（不引入新文件）低—中
JIT/W^X能否拥有可写可执行内存借用有 JIT 权限的进程（渲染/JS 引擎）高

核心判断：这一整条链的设计目标是"没有 Apple 认可就得不到可执行内存"，而不是"没有 Apple 认可就得不到任意行为"。因此攻击工程在签名层的问题被转化为一个组合问题：用哪些已签名的合法组件，把攻击者控制的数据变成行为。这解释了为什么 Coruna/DarkSword 类链条在提权成功后并不植入新二进制，而是采用借用 + 配置驱动的形态（与 #45 的文件less 驻留一致）。

3. 应用完整性失效的四种形态

形态机理攻击成本工件特征现实使用度
I1 进程注入借用宿主在已签名已授权进程内执行攻击者逻辑需要写入原语 + 绕过库验证宿主进程出现与其职责不符的行为（外发、传感器访问）高（商业间谍软件公开分析主线）
I2 动态库/插件加载滥用利用豁免或同 TeamID 组件加载非预期代码中加载路径异常、组件出现在容器内中
I3 配置/数据驱动的合法执行不改代码，改配置、描述文件或托管载荷低（多为合法通道，见 #67）安装数据库/描述文件变化中—高
I4 JIT/W^X 借权在有可执行内存权限的进程内构造代码高（需要该权限）渲染进程异常、崩溃形态中（与 #44 重合）
I5 签名验证旁路缺陷校验实现本身的缺陷极高与具体缺陷绑定，难通用低但影响大

防御优先级：I3 是唯一"完全合法且无技术缺陷"的形态，因此它靠流程防御（#67）；I1/I2/I4 靠架构与最小授权（收紧豁免、缩小 entitlement 面、把解析放进隔离域 #52）；I5 靠补丁与内存安全语言迁移（#61、#64）。

4. 借用宿主的审计方法

对防御方来说，最可操作的检查是"宿主能力清单"：

Step 1  枚举：哪些已签名进程同时具备以下三项？
        (a) 处理外部不可信输入（网络、附件、下载内容）
        (b) 拥有敏感能力（传感器、文件、网络、钥匙串访问）
        (c) 存在动态加载或脚本驱动路径
Step 2  排序：a×b×c 三项皆成立的宿主即高价值注入目标
Step 3  核对 entitlement 实际值（而非文档值），以设备生效版本为准
Step 4  与 #68 的 IPC 可达清单交叉：注入后能否进一步穿越沙箱
Step 5  输出可 diff 的基线，随 iOS 版本回归（#61）
宿主类型（示例分类，非具体清单）(a) 外部输入(b) 敏感能力(c) 动态路径综合
网页/消息渲染类进程高中高（JS/JIT）最高（#44、#71 同点）
媒体解析类守护进程高中—高中高（#44）
通知服务扩展宿主高中中高（#65）
安装/配置类服务中高中高（#67）
普通用户 App中低（受 TCC 约束）低低（#66）

这张表的真正用途是把"补丁优先级"从 CVE 顺序改为架构顺序：同一 CVSS 分下，处理不可信输入且能力多的宿主进程里的缺陷更值得优先修（与 #63 的狩猎优先级、#61 的补丁工程呼应）。

8. 总结

#结论
1代码签名是一条多环校验链，"签名有效"与"行为受限"是两个不同命题
2攻击工程的实际重心不是伪造签名，而是组合已签名组件、让合法宿主执行攻击者控制的数据
3失效形态集中在特殊豁免与借用：注入、动态加载、配置驱动、JIT 借权、校验实现缺陷
4宿主审计（外部输入 × 敏感能力 × 动态路径）应成为补丁优先级排序的架构依据
5签名校验通过不能证明未被注入；报告表述必须限于"未发现落盘第三方载荷"
6注入的可行检测来自"能力使用与用户意图不一致"的时间线矛盾，而非完整性校验本身
7长期收敛路径是缩小豁免面 + 内存安全迁移 + 并行信任域，而非在链上继续加校验点

一句话总结：iOS 的代码签名让 Coruna 与 DarkSword 这类攻击无法"装一个自己的程序进来"，从而把它们逼进了"必须借用系统已有的合法程序"这条成本更高、痕迹更多的路——防御方的正确策略不是反复确认签名有效，而是主动清点谁值得被借用（外部输入多、能力大、可动态加载的宿主），把补丁与隔离资源按这份清单而不是按漏洞分数排列。
