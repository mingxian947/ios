iOS 威胁狩猎手册：面向 Coruna 与 DarkSword 的六个可执行剧本

编制日期：2026-10-18 数据来源：Google Project Zero、Citizen Lab、Amnesty International、MVT 项目、Lookout、MDM 与网络遥测工程实践、ATT&CK 覆盖度核算（见 #59） 性质：防御性安全研究分析（Defensive Security Research），不提供可利用代码

1. 执行摘要

告警是别人替你写好假设，狩猎是你自己提出假设并去数据里证伪。iOS 场景下只有狩猎可行——因为不存在能产生实时告警的端点遥测（#59 的覆盖度核算已给出结论）。

本手册的三条设计前提，必须先接受，否则剧本会写成幻想：

前提含义违反后果
P1 主机侧批量遥测不存在不要写依赖 iPhone 本地日志的剧本规则永远零命中，团队误判为"干净"
P2 唯一稳定信号在网络与备份DNS/SNI/NetFlow/JA4 + 周期性备份扫描把预算投到无效数据源
P3 对手可以不留工件无痕驻留型（#45）对文件扫描天然免疫用"没扫到"证明"没中招"

六个剧本按"信号强度 × 实施成本"排序，前三个应优先落地：

剧本名称假设类型主要数据源成本覆盖对手类型
HUNT-01高价值角色的通信形状漂移行为异常NetFlow/SNI低全部
HUNT-02孤点设备发现（单台独有域名）稀有性DNS + 代理日志低全部
HUNT-03短生命周期基础设施关联资产侧写DNS + CT 日志 + WHOIS中全部（#46、#50）
HUNT-04崩溃群体异动回溯利用可靠性崩溃/诊断日志中迭代型攻击者（#47）
HUNT-05备份工件周期扫描工件存在性备份 + MVT 类工具高落地型（Coruna）
HUNT-06时间线断裂与反取证痕迹痕迹缺失备份 + MDM 记录高清除型（#55）

狩猎不是从零开始写规则，而是先确认"能不能问这个问题"。

三个必须处理的采集盲点：

  1. 私有中继：组织内 iPhone 常经由个人 Mac/PC 共享网络出口，客户端 IP 与设备不是一一对应，做设备级关联时需先归一化。
  2. 加密 DNS：DoH/DoQ 会让内网 DNS 日志丢失大量查询，必须显式记录出口解析器的位置，否则 HUNT-02 的稀有性计算失真。
  3. 蜂窝出口：Safari 蜂窝浏览会走 Apple 的私密中继（iP6 前缀段），中继之后无法归因原始主机名，只能做"中继流量异常"级别的粗粒度观测。这一条会显著影响剧本的召回率，必须在报告里写明适用网络类型（#48 已强调）。

3. HUNT-01：高价值角色的通信形状漂移

假设：被感染设备的外发通信在"会话形状"上会偏离该角色群体的历史基线——不是因为内容异常，而是因为心跳、批量上传、短会话重连这些模式在正常办公中很少出现。

为什么有效：这是 #59 结论 2 的直接应用——C2 与外泄是 iOS 上唯一可批量观测的战术。

数据：NetFlow + SNI，按设备（或设备级客户端 IP）聚合，窗口 14 天。

逻辑（伪查询，非检测规则）：

for dev in HIGH_VALUE_DEVICES:
    base = 该设备过去 8 周的每设备夜间特征向量
    cur  = 最近 14 天特征向量
    features = [
      夜间(00:00-06:00)会话数,
      上行/下行字节比 P95,
      单会话时长中位数 与 分布形态(长心跳 vs 短交易),
      唯一目的域名数,
      53/443 之外的协议占比,
      重复小报文(疑似握手/重试)比例
    ]
    if 任一特征 z-score > 3 或 分布形态类别翻转:
        raise HUNT-01 finding

关键判读细节：

特征正常办公解释可疑解释
长会话 + 低速率VPN、邮件推送心跳型 C2 长连接（#46）
短会话高频重连应用轮询交易型 C2 + 失败重试
上行突增但域名少云备份、相册同步采集后分卷外传（#42、#46）
夜间活动少数岗位真实存在采集器定时任务

误报处置：先排除"相册 iCloud 同步""备份""系统更新下载""VPN 重连"四类，剩余才进入调查。做法是把 iCloud/Apple 服务段 IP 与 Apple 域名做基线白名单，但注意不要把整个 ASN 段无脑排除，攻击者常借道合法服务（#46 的前置/借道策略）。

升级动作：命中后进入 #48 的采集顺序（先断网不断电、保持解锁），再做 HUNT-05/06。

4. HUNT-02：孤点设备发现

假设：定向投放的攻击几乎一定表现为稀有性——只有一台（或极少数）设备解析过某个域名，而组织内其余几百台从未解析。这是水坑/定向链最稳定的统计特征（#50）。

数据：DNS 日志（全组织）+ 设备归属映射。

逻辑：

freq(qname) = 过去 30 天内解析过该 QName 的唯一客户端数
candidates  = { qname | freq(qname) == 1 且 该 qname 的字符结构可疑 }
可疑结构 =  标签长度异常 / 高熵子域 / 与业务无关的 TLD /
           仿冒常见服务拼写 / 近期首次出现（新注册）

加分关联（把稀有性变成可信发现）：

关联项说明
该客户端 = 高价值角色优先级立刻提升（#50 的画像筛选）
同域名随后被其他设备解析说明可能不是定向，而是垃圾/广告噪声
域名注册年龄 < 90 天与基础设施生命周期模型一致（#46）
解析次数恰为 1—3 次且之后消失一次性触发型投递的典型形状
对应 SNI 在同 IP 上出现 JA4 异常客户端指纹与 Apple 网络栈基线不符

必须防的假阳性：个人域名、新装小众 SaaS、活动/会议域名、开发者本地测试域名。做法是维护"业务新增域名"变更源（申请流程/采购记录），把有流程记录的稀有域名降级。

输出物：每周一份"稀有域名 × 高价值设备"交叉清单，控制在 10 条以内，人工过一遍远比自动阻断有效——iOS 上你无法在设备侧阻断，只能做流量侧观察或引导用户升级补丁/开启锁定模式。

5. HUNT-03：短生命周期基础设施关联

假设：C2 基础设施的复用痕迹会暴露在同一运营方身上——即使域名不断更换，证书、IP 段、命名模式、注册商与 ASN 选择会重复（#46、#66）。

数据：CT 日志、被动 DNS、WHOIS、外部威胁情报（可自建被动 DNS 采集）。

逻辑：

seed = HUNT-01/02 命中的域名或 IP
for 每一轮关联:
    同证书序列/公钥复用 → 同注册人邮箱/组织名 → 同 IP 历史解析
    → 同命名模式（如 <数字>-<词>.<新 gTLD>）→ 同托管 ASN
输出：一个"基础设施簇"，标注簇内哪些成员曾被组织内设备访问

工程要点：

要点做法理由
回溯窗口至少 12 个月被动 DNS攻击者会重用过期域名（#13 的泄露/复用逻辑）
命名模式建模简单字符串结构特征即可，不必 ML可读、可交法务复核（#62）
内部命中优先只看"簇 ∩ 本组织访问记录"避免成为纯情报收藏
与站点侧联动若簇中含疑似水坑域名，触发合作方通知水坑防御只能在投递侧真正阻断（#50）

注意边界：基础设施关联能形成强一致性证据，但不构成归因结论；措辞按 #62 的分级表述，尤其涉及对外披露或法律程序时。

6. HUNT-04：崩溃群体异动回溯

假设：利用开发是概率性工程，链失败会留下崩溃。攻击者可选择规避崩溃（#55、#56），但在批量调试阶段不会每次都规避——因此在特定版本/机型群体中，某些进程的异常退出率会短期抬升。

数据：Apple 分析数据（若企业接入）、sysdiagnose、崩溃报告聚合、MDM 采集的构建号分布。

逻辑：

for (process, os_version, build) in 观测群体:
    rate = 崩溃次数 / 设备·天
    若 rate 相对上一 30 天基线抬升 > 阈值 且
       集中在同一 build 且 涉及攻击面相关进程
       (WebContent / mediaserverd / GPU 服务 / 解析类服务):
        记录为 HUNT-04 finding（滞后指标，不进实时告警）

为什么它是滞后指标：崩溃聚合需要时间窗与对照组，且必须区分"新版本自身质量问题"与"外部利用尝试"。判别线索：

观察更像产品质量问题更像利用尝试
分布全群体均匀抬升集中在少数高价值设备
时段更新后持续短时密集后回落（投放窗口，#50）
签名崩溃点分散集中在同一组件/同一异常类型
关联无网络异常与 HUNT-01/02 命中同设备同时段

用法：只做回溯与优先级排序（决定对哪些设备做 HUNT-05/06），不做"未崩溃即未感染"的反向推定——那是 P3 违规。

7. HUNT-05：备份工件周期扫描

假设：落地型载荷（Coruna 型，#45）在文件系统中留有工件；对高价值角色做周期性、有保留基线的备份扫描可以发现新增/异常容器内容。

数据：受控备份（iMazing/AFC 类）、MVT 类检测模块。

节奏与范围：

人群频率范围
极高价值（高管、法务、安全团队）月度全备份 + 崩溃日志 + 配置目录
高价值（财务、PR、研发核心）季度定向模块
一般员工不做—

关键操作要求（决定这个方法有没有价值）：

  1. 保留历史副本做差分：单次扫描意义有限，"这台设备上上周没有、本周出现"才是信号（这也是 #55 时间线断裂检测的原料）。
  2. 固定工具与特征库版本并留痕：否则跨月结果不可比（#62 的完整性要求）。
  3. 知情同意与合规前置：对高管设备做定期备份扫描涉及隐私与授权，须有书面政策与法务确认（#62 第 8 节）。
  4. 明确阴性含义：对无痕型（DarkSword）体系本剧本原理上无效，阴性结果不得用于排除（#47）。

替代增强：对极高价值角色，可结合"定期重启 + 重启后即时扫描"来压缩驻留窗口——重启会清除内存驻留，若重启后仍能扫到工件，说明存在落地驻留，信号强度远高于单纯命中（#45）。

8. HUNT-06：时间线断裂与反取证痕迹

假设：清除型对手会删工件、改时间戳、避免崩溃（#55）。这些动作本身会制造"应有的痕迹不见了"的负向痕迹。

可检测的负向痕迹：

应有的痕迹缺失意味着
某时段的日志轮转记录主动清理
崩溃报告目录为空但同版本群体非空崩溃规避或清除
文件 mtime < ctime 或时间戳落在不可能区间时间戳篡改
备份中出现"目录存在但内容为空"的空洞选择性删除
相邻时间戳序列突然中断工件被移除

逻辑：

从 HUNT-05 的历史备份对中取工件集合 A(t1), A(t2)
removed = A(t1) - A(t2)
对 removed 中每项检查:
    时间戳自洽性(mtime/ctime/atime 关系)
    所属目录的兄弟项是否仍在
    同版本对照组是否会出现同样删除
标记"非自然删除"候选 → 进入人工时间线复核

这一剧本最难，也最容易被误用：正常系统维护（备份滚动、存储清理、用户主动删）同样制造空洞。必须用对照组（同版本、同人群的其他设备）来区分"系统会这么做"与"只有这台设备这么做"。因此建议在 HUNT-05 稳定运行至少一个季度、积累出对照组基线后再启动。

11. 总结

#结论
1iOS 上没有能产出实时告警的端点遥测，威胁狩猎是唯一现实的检测范式
2六个剧本只有 HUNT-01/02/03 依赖常态网络数据，可立刻落地；后三个依赖备份与差分积累
3稀有性（单台设备独有）是定向投放最稳定的统计特征，优先级高于任何 IoC 匹配
4崩溃异动只能做回溯与排序，绝不能反向推定"无崩溃即无感染"
5备份扫描的价值来自历史差分而非单次命中；且对无痕型体系原理无效
6私有中继、加密 DNS、蜂窝出口三个盲点必须在每次结论中显式声明适用范围
7狩猎组织的真正瓶颈是数据保留期与设备归属映射，不是分析技术

一句话总结：iOS 威胁狩猎的本质，是在没有端点遥测、对手又能抹掉痕迹的前提下，用"这台设备与它的同类有什么不同"这一个统计学问题，去逼近一次无法被直接看见的入侵——因此决定成败的是保留期、对照组和诚实的阴性表述，而不是规则数量。
