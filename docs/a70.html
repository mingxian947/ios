Safari 与 WebView 取证工件目录：从浏览痕迹重建 iOS 入侵时间线

编制日期：2026-10-22 数据来源：Apple Platform Security 文档、MVT 与 OpenPDF 公开工件研究、Aleph1/XiVO 等取证工具的工件说明、Google Project Zero 关于水坑投递的披露、Citizen Lab 与 Amnesty 的 Pegasus 调查报告、CVE 情报库 性质：防御性安全研究分析（Defensive Security Research），不提供可利用代码

1. 执行摘要

在几乎所有 iOS 入侵调查里，"攻击者是怎么进来的"最终都要回答成一个具体问题：目标在什么时间访问了哪个 URL。对水坑/定向投递型链条（#40、Coruna 与 DarkSword 的公开描述均采用这一入口）而言，浏览器与 WebView 侧工件是唯一能直接指向投递页面的证据来源。

本文给出一个可执行的工件目录（Artifact Catalog）与解析顺序，而不是概念讨论。

四条结论：

  1. Safari 的工件分散在多个互不同步的存储里（历史数据库、本地/HTTP 缓存、Cookie 库、图标与读取列表、崩溃日志、iCloud 同步后的 Tab）。任何单一来源都不足以重建时间线，必须做交叉关联。
  2. 缓存命中不一定留下历史条目：某些重定向、iframe 子资源与 WebView 内加载只进缓存不进历史。这是"历史里没有可疑 URL"这一错误结论的技术根源，与 #62 的"未发现≠未感染"纪律同源。
  3. WebView（含 App 内嵌 WKWebView、通知服务扩展的渲染路径 #65、BlastDoor 解析面 #52/#68）的工件比 Safari 更稀疏，但归属更明确——它能告诉你"是哪个 App 加载了它"，这在水坑归因里是关键区分。
  4. 时间戳的可信度分层是本文最容易被忽略的部分：不同工件的时间源、精度与偏移不同；做时序论证前必须先声明时间基准，否则整条链条在法律与工程上都不成立（#62 的真实性与完整性要件）。

2. 工件目录

#工件内容时间精度主要取证价值局限
A1Safari 历史数据库URL、标题、访问次数、visited_time秒级投递页面直接证据无痕模式下不落；用户可清除
A2HTTP/本地缓存资源 URL、响应头、Date、ETag、内容片段依赖头部补历史缺口：重定向与子资源可见循环淘汰、无完整 URL 语义
A3Cookie 库域、名称、值、过期与创建时间秒级判定"确实加载过该站"、追踪标识值可能被服务端脱敏；跨站受限
A4站点图标/读取列表（Reading List）标题、URL、保存时间秒级用户主动行为标记，用于意图区分覆盖面窄
A5favicon 缓存域列表与时间粗只有域名，无完整路径常与其他缓存混存
A6自动填充/密码使用痕迹表单域、站点关联粗判定"登录动作发生过"与 #53 钥匙串风险交叉，敏感度高
A7WebKit 相关崩溃日志进程名（WebContent）、异常类型、时间秒级攻击尝试失败的痕迹（利用有崩溃成本，#63 HUNT-04）成熟载荷规避崩溃
A8iCloud 同步 Tab / 跨设备记录其他设备上的同源条目秒级目标设备已清除时的恢复路径（#69）需账户侧证据配合
A9App 沙箱内的 WebView 缓存宿主 App 容器内的缓存/Cookie依赖头部归因到具体 App 与入口各家容器路径与保留策略不一
A10DNS/连接元数据（设备侧可恢复部分）解析时间、域名秒级与缓存时间戳互证（#47）保留期极短
A11推送/通知触发记录唤醒时间与来源秒级与 A1/A9 时刻对齐（#65）无 URL 语义

目录里最被低估的是 A2 与 A9：A2 覆盖历史覆盖不到的子资源与重定向，A9 提供"哪个 App 加载的"这一归因维度。二者的组合通常决定了能否把入侵从"用户点了个链接"精确到"某 App 内的某次加载"。

3. 解析顺序（可直接作为剧本执行）

第 0 步  固定基准
        - 记录设备时区、NTP 同步状态、单调时钟偏移
        - 对每个提取文件计算哈希并写入保全记录（#62）
第 1 步  广度扫描
        A1 历史 → 可疑域清单（时间窗：投递期 ±48h）
        A2 缓存 → URL/域清单（与 A1 做集合差：只进缓存的项）
        A3 Cookie → 域清单（与 A1/A2 交集）
第 2 步  缺口判定
        集合差 = 仅出现在缓存/但不在历史里的资源
        → 这些是重定向与子资源候选，水坑落地页常在此出现
第 3 步  归因
        A9：可疑 URL 出现在哪个 App 容器？
        A11：该时刻前是否有通知/推送唤醒？
        → 区分「用户主动访问」/「App 内加载」/「唤醒后自动加载」
第 4 步  互证
        A2 响应头 Date ↔ A1 visited_time ↔ A10 DNS 时间
        三者偏移应在合理阈值内；超阈值 → 存在时钟/伪造问题（进入 #62 完整性审查）
第 5 步  跨设备补齐
        A8 从其他设备与账户侧恢复同源条目（配合 #69 设备列表审计）
第 6 步  失败尝试痕迹
        A7 崩溃日志聚合：同域名的多次 WebContent 异常
        → 即使最终未成功投递，也提供攻击者活动时间窗（#63）
第 7 步  结论形态
        每条结论标注证据强度（多源一致/单源/推定）并明确"未发现"的边界

第 2 步是本文最有价值的一步：很多调查在"历史里没有可疑链接"后就停止。正确动作是把 A2/A3 的集合差单独列出来看——"只在缓存里出现"本身就是重定向投递的形态特征。

4. 时间戳可信度分层

时间源可信度风险处理方式
设备文件系统时间（受 Data Protection 保护）高用户/攻击者可改系统时间（#55 反取证）与外部时间源（邮件、推送、服务端日志）比对
数据库内业务时间戳（visited_time 等）高与文件系统时间可能不一致（写入延迟/时区）双时间并列呈现，不做单一断言
HTTP Date 头中—高服务端时间、缓存代理可改写仅作互证，不作主证据
Cookie 过期时间低相对量，非绝对时刻不用作时序论证
缓存淘汰推算的时间窗低只能给上下界表述为"区间"而非"时刻"
崩溃日志时间中日志聚合延迟用于时间窗而非精确时刻

时序论证纪律：主张"访问 A → 随后 B 发生"时，必须给出两个时刻各自的时间源与可信度层级，并给出可容忍偏移。这与 #62 的"真实性/完整性/关联性/合法性"四要件一一对应——缺少时间基准声明的结论，在对抗性审查里应视为不成立。

5. 无痕、清除与工件灭失

场景结果可恢复证据防御/调查建议
无痕浏览A1 不落历史A2 缓存（部分版本仍产生）、A3（会话后清除）、A7 崩溃不能因"无痕"排除访问；重点转向缓存与崩溃
用户手动清除历史A1 条目删除A2/A3 残留、A8 其他设备、SQLite WAL/journal 残留清除后立即提取，越早恢复率越高
攻击者主动清痕（#55）多工件时间缺口缺口本身即证据：与其他设备/账户记录比对把"时间线缺口"写入结论，而非当作无数据
iCloud 同步开启跨设备扩散A8 为最强恢复路径与 #69 的设备列表审计同步进行
备份覆盖旧版本可能被覆盖历史备份中的同名文件保留多个时间点备份（与 #62 链条一致）
恢复出厂/擦除本机工件灭失仅云端与其他设备优先做非破坏性提取，再决定是否擦除（灭证风险）

表述纪律（延续 #62）：正确写法是"在本设备当前工件范围内未发现指向 X 站的访问记录，缓存与会话级工件不能排除无痕访问，其他设备未纳入本次提取"。不能写"目标未访问该页面"。

6. 与检测侧的接口：为什么浏览器工件也用于狩猎

用途做法对应篇目
投递页识别把 A2/A9 中的可疑域与已知基础设施指标（DNS/SNI 留存）比对#47、#63 HUNT-01
水坑页共性发现多台设备缓存中同一域/同一资源特征 → 群体命中#63 HUNT-04（群体基线）
载荷落地关联A1/A9 时刻 ↔ 安装数据库变化 ↔ 首次异常出站#42、#54（模块化载荷）
唤醒通路确认A11 通知唤醒时刻 ↔ 加载时刻（无用户动作）#65
攻击失败时间窗A7 崩溃聚合#63、#61（补丁优先级）
反取证告警历史被清除 + 无同期账户操作#55

浏览器工件因此不只是"事后重建"，它是把网络侧指标落到设备侧行为的唯一黏合层。

8. 总结

#结论
1Safari/WebView 工件分散在多个互不同步的存储里，单一来源不能重建时间线
2缓存与 Cookie 覆盖历史覆盖不到的重定向与子资源；"历史里没有"不是排除依据
3App 容器内的 WebView 工件提供归因维度（哪个 App 加载），价值高于其内容本身
4时间戳必须分层声明可信度；缺少时间基准的时序结论在法律与工程上都不成立
5清除与无痕造成的是"缺口"，缺口本身应作为证据写入结论
6崩溃聚合可以给出攻击尝试的时间窗，即使最终未成功投递
7浏览器工件是把网络侧指标与设备侧行为黏合起来的唯一层，因此同时服务于取证与狩猎

一句话总结：Coruna 与 DarkSword 这类链条最终都要经过"目标设备上的一次页面加载"，而这一次加载会同时留在历史、缓存、Cookie、App 容器和崩溃日志五个彼此独立、清除策略各不相同的地方——调查的正确做法不是找那一条"可疑链接"，而是对这五类工件做集合差与时间互证，因为真正指向水坑投递的，往往正是那条没有出现在历史记录里、却存在于缓存中的资源。
