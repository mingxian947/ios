DarkSword 无持久化内存驻留技术

编制日期：2026-10-02 数据来源：Google Project Zero、Synacktiv、8ksec、公开 CVE 情报、Apple 安全公告 性质：防御性安全研究分析（Defensive Security Research），不提供可利用代码

1. 执行摘要

DarkSword 是 2024 年被 Google Project Zero 披露的一代商业间谍软件利用套件，其最显著的设计特征之一是"无持久化"（Fileless / No Persistence）策略：不在目标设备上写入任何文件、不修改文件系统、不创建新的启动项——所有恶意代码仅在易失性内存（RAM）中运行，设备重启后痕迹即消失。

这一策略对传统取证与检测体系构成根本性挑战：

  • 文件系统扫描无法发现恶意二进制或脚本
  • 启动项检查（LaunchDaemons / LaunchAgents）看不到新增条目
  • 重启即清除，受害者可能在无意识状态下"自愈"
  • 内存取证（Live Forensics）成为唯一可靠的检测手段

本文将系统分析 DarkSword 无持久化驻留的技术原理、实现路径、反取证机制，以及与 Coruna 持久化策略的对比，最终给出防御与检测建议。

2. 无持久化驻留的设计动机

2.1 为什么选择"不落地"

传统间谍软件（如早期 Pegasus）会在设备上写入持久化载荷：创建 LaunchDaemon、植入二进制、修改系统文件。这种方式虽然能保证"重启后仍控制"，但也留下大量可被扫描、哈希匹配、完整性校验发现的痕迹。

DarkSword 的设计者显然做了不同的权衡：

考量持久化方案无持久化方案（DarkSword）
重启后控制✅ 自动恢复❌ 需重新投递
文件系统痕迹大量几乎为零
被 MDM / EDR 扫描发现概率高极低
被 iTunes 备份提取概率高零
被完整性校验（A/B 快照）发现可能不可能
对 C2 可用性的依赖低高（每次需重新投递）

核心权衡：用"每次需重新投递"的运营成本，换取"几乎不可被静态检测"的隐蔽性。对于高价值、短周期的目标（如 3-5 天的会议期间监控），这一策略极为合理。

2.2 与 iOS 安全架构的契合

iOS 的多层防御使得持久化越来越困难：

  1. 安全启动链（Secure Boot Chain）：从 Boot ROM 到内核，每一级都验证签名，篡改系统分区不可行
  2. 只读系统卷（SSV, Signed System Volume）：iOS 15+ 系统卷加密签名，运行时不可修改
  3. App Sandbox：第三方应用无法写入系统目录
  4. AMFI（Apple Mobile File Integrity）：阻止未签名代码执行
  5. A/B 系统更新快照：OTA 更新会覆盖整个系统分区

在这种环境下，试图在文件系统上持久化，等于主动在最容易被校验的层面留下痕迹。DarkSword 选择了更聪明的路径：不碰文件系统，只在内存中活动。

3. 内存驻留的技术实现

3.1 攻击链各阶段的内存驻留

DarkSword 的无持久化贯穿攻击链的每一个阶段：

[初始访问] WebKit RCE → 代码仅在 WebContent 进程内存中执行
     ↓
[沙箱逃逸] 利用 GPU/ANGLE 漏洞 → 逃逸代码在沙箱进程内存中
     ↓
[内核提权] PAC 绕过 + 内核漏洞利用 → 内核态代码仅在 RAM 中
     ↓
[载荷部署] 数据采集模块 → 动态加载到内存，不写入磁盘
     ↓
[数据外传] 加密外传 → 内存中组装数据，直接发送
     ↓
[清除] 释放内存 → 无痕迹残留

关键：每个阶段的载荷都是"内存中生成、内存中执行、内存中销毁"。

3.2 代码注入与内存执行

在无持久化架构中，代码注入必须在不创建文件的前提下完成。常见技术路径：

3.2.1 进程内代码生成

  • JIT 编译滥用：JavaScriptCore 的 JIT 编译器本身就会在内存中生成可执行代码。攻击者可以利用 JIT 页面执行任意原生代码，无需写入文件系统
  • 动态代码生成：通过 mmap + PROT_EXEC 创建匿名可执行内存页（无需文件映射）
  • ROP/JOP 链：不注入新代码，而是利用已有二进制中的 gadget 串联执行逻辑——完全不需要写入任何字节

3.2.2 跨进程注入（从逃逸后的进程到目标进程）

  • mach_vm_write + thread_create：通过 Mach API 向目标进程写入代码并创建新线程执行——全程在内存中完成
  • posix_spawn + exec 覆盖：不创建新文件，而是在内存中修改进程映像（更复杂，但更隐蔽）
  • dyld 动态加载：通过 dlopen 加载内存中的动态库（需配合 NSCreateObjectFileImageFromMemory 等 API）

3.2.3 内核态内存驻留

内核提权后，DarkSword 需要在内核空间维持执行能力：

  • 内核线程创建：通过 kernel_thread 等内核 API 创建新线程，执行代码仅存在于内核内存
  • 函数钩子（Hook）：修改内核函数指针（如系统调用表、vnode 操作函数），将控制流重定向到内存中的恶意代码
  • 内核扩展（KEXT）替代：不加载 .kext 文件，而是直接在内存中构造 KEXT 结构并注册到内核

3.3 数据在内存中的生命周期

DarkSword 采集的数据同样遵循"内存中来、内存中去"的原则：

[采集] 从目标进程/文件读取数据 → 存入进程堆内存
  ↓
[组装] 在内存中压缩、加密、打包 → 不写入临时文件
  ↓
[外传] 通过 HTTPS/DNS 等通道发送 → 数据直接在内存中送入网络栈
  ↓
[清除] 释放缓冲区 / 覆写内存 → 数据不可恢复

关键细节：

  • 不使用 tmpfile() / fopen("/tmp/...")：避免在 /tmp 或 /var 下创建临时文件
  • 内存覆写：释放前用零或随机数据覆写缓冲区，防止数据在物理内存中残留
  • 避免 Core Dump：确保进程崩溃时不会将敏感数据写入磁盘（通过 pthread_core_dump_disable 或类似机制）

4. 反取证机制

4.1 文件系统层面的反取证

技术说明
零文件写入所有操作在内存中完成，不创建、修改、删除任何文件
避免临时文件不使用系统临时目录、缓存目录、日志目录
不修改 plist / 配置文件不创建 LaunchDaemon、LaunchAgent、登录项
不修改钥匙串避免在 Keychain 中写入新条目（钥匙串修改可被检测）

4.2 进程层面的反取证

技术说明
进程伪装注入到合法系统进程中（如 mediaserverd、backboardd），不创建新进程
线程命名将恶意线程命名为与宿主进程一致的名称，混淆 ps / Activity Monitor
内存清理任务完成后覆写并释放内存，不留残余
避免异常崩溃精心处理异常，防止进程崩溃生成 Crash Report（Crash Report 会写入磁盘）

4.3 网络层面的反取证

技术说明
无日志通信不使用系统网络日志（如 netlog）
短会话每次通信会话短暂，减少网络流量分析窗口
域名伪装使用与合法服务相似的域名（如 CDN、云服务）
流量加密所有通信使用 TLS，内容不可被中间设备识别

4.4 对抗内存取证

即便防御者意识到需要内存取证，DarkSword 也有对策：

技术说明
内存覆写释放前覆写，使数据恢复困难
代码加密内存中的代码以加密形式存在，仅在即将执行时解密
短暂生命周期每个任务模块执行完毕后立即从内存中卸载
反调试检测调试器附加（sysctl、ptrace），被发现时清除内存

5. 无持久化的代价与局限

5.1 重新投递成本

每次设备重启后，DarkSword 必须重新完成整个攻击链：

  1. 再次投递水坑/钓鱼页面
  2. 再次触发 WebKit 漏洞
  3. 再次完成沙箱逃逸
  4. 再次完成内核提权
  5. 再次部署载荷

这意味着：

  • C2 必须持续在线：如果 C2 被封禁，攻击者无法重新控制
  • 受害者重启 = 攻击中断：目标如果频繁重启设备，攻击者需反复投入资源
  • 投递窗口暴露：每次重新投递都是一次被检测的机会

5.2 与 Coruna 的对比

Coruna 的设计哲学与 DarkSword 截然不同：

维度DarkSwordCoruna
持久化策略无持久化（Fileless）部分持久化（写入文件系统）
重启后存活❌ 需重新投递✅ 自动恢复
文件系统痕迹几乎为零有可检测文件
检测难度高（需内存取证）中（文件扫描可发现）
运营成本高（每次需重新投递）低（一次植入长期控制）
适用场景短期高价值目标长期持续监控

5.3 适用场景分析

DarkSword 的无持久化策略特别适合以下场景：

  • 会议/事件监控：目标在 3-5 天会议期间被监控，会议结束后痕迹消失
  • 高警觉目标：目标设备可能被定期检查，持久化载荷会被发现
  • 一次性数据窃取：只需获取一次特定数据（如密码本、加密密钥），无需长期控制
  • 测试/验证：攻击者验证目标设备是否可被突破，不急于建立持久控制

6. 检测与防御

6.1 内存取证（Live Forensics）

无持久化攻击的唯一可靠检测手段是运行时内存取证：

技术说明
进程内存转储使用 memdump 等工具导出进程内存，搜索异常代码模式
异常内存页检测扫描具有 PROT_EXEC 权限的匿名内存页（非 JIT 进程中出现则为异常）
线程枚举检查进程中的线程，寻找命名异常或堆栈异常的线程
Hook 检测检查内核函数指针、系统调用表是否被修改

6.2 行为检测

信号说明
WebGPU/ANGLE 异常渲染进程中出现异常的 GPU 调用模式
mediaserverd 异常媒体服务进程 CPU/内存使用异常，或出现异常线程
异常外传短时间内大量加密数据外传
JIT 页面异常非 JIT 进程中出现可执行匿名内存页

6.3 网络检测

信号说明
DGA 域名检测到与已知 DGA 算法匹配的域名解析
异常 TLS 指纹自定义 TLS 实现的指纹与系统原生不一致
短时高频通信短时间内多次与同一域名通信

6.4 防御建议

建议优先级
启用锁定模式极高 — 禁用 WebGPU/ANGLE，关闭 JIT，大幅收窄攻击面
及时升级系统极高 — 修补已知漏洞
部署运行时检测高 — 从静态扫描转向行为监控
定期内存取证中 — 对高危人群设备定期做内存分析
网络分段与监控中 — 监控异常加密外传
教育用户中 — 避免访问不可信网站，定期重启设备

7. 总结

DarkSword 的无持久化内存驻留策略代表了商业间谍软件设计的一个重要演进方向：从"控制设备"转向"短暂访问"。这一策略的核心逻辑是：

  1. 不碰文件系统：在 iOS 层层签名校验的环境下，文件系统是最容易被检测的层面
  2. 内存中来去：所有代码、数据、执行都在 RAM 中完成，重启即清除
  3. 反取证优先：从代码加密、内存覆写到进程伪装，每个环节都考虑痕迹消除
  4. 用运营成本换隐蔽性：接受每次重启需重新投递的代价，换取几乎不可被静态检测的隐蔽性

对防御者而言，这意味着：

  • 传统文件扫描、启动项检查已不够——必须引入运行时行为检测和内存取证能力
  • 锁定模式是最有效的缓解——通过禁用 WebGPU/ANGLE/JIT，直接关闭攻击链入口
  • 定期重启是简单有效的对抗——迫使攻击者反复投入资源，增加其暴露概率
  • 网络遥测不可或缺——即便内存中无痕迹，数据外传仍需网络通道

无持久化攻击不会消失，反而会越来越多。防御体系必须从"找文件"进化到"找行为"。
