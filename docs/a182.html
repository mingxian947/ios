Coruna 与 DarkSword 场景下的交易尽调：安全历史在被买卖时值多少钱

1. 执行摘要

  • 一起定向投放事件的长期代价，经常不在事件当年显现，而在三年后的一次交易里：并购尽调、投资尽调、客户招标的大型合同、上市前的合规梳理。本篇讨论这一场景——你的安全历史被当作一项资产或负债来估值。
  • 核心命题一："有没有出过事"与"有没有瞒着"是两笔不同的账。 前者影响估值，后者影响交易本身能否成立；后者通常贵一个数量级。
  • 核心命题二：尽调的问题不是为了了解你，是为了分配风险。 买方问的每一个问题，最终都会变成合同里的一个条款或一个价格调整项。
  • 核心命题三：陈述与保证的纪律只有三条：准确、可核对、说清范围。 与 #181 的审计陈述同构，但后果更集中——它直接进合同。
  • 核心命题四：交割后才发现的事件，有三种局面，且只有一种不伤交易。 提前披露 + 有闭环 = 价格问题；事后暴露 = 违约问题；被第三方先发现 = 信誉问题。
  • 核心命题五：卖方最容易忽略的不是技术材料，是"人"的材料：谁走了、谁带走了一份名单、谁在离职时保留了访问（#120 的离职边界在交易场景下的第二次发作）。
  • 一句话结论：在交易里，安全历史的价值不在于它有多干净，而在于它有多可核对。

2. 这一篇补哪一格

#181 处理审计与认证：周期性、以体系为对象、结论是"是否符合标准"。本篇处理交易：一次性、以历史事实为对象、结论是"价格与条款"。

#167 处理合同中的安全条款：日常供应商合同。本篇处理股权/资产交易中的陈述与保证——它不是一份服务合同，而是一次对所有权的重新定价。

#120 处理离职与账户交接：组织内部的人员退出。本篇是在交易语境下再看一次：被收购方的人员流动，是买方最关心、卖方最容易低估的一项。

#96 处理设备处置与流转：设备离开组织时留下什么。交易中会有大量设备、备份、账号随主体一起转移，这一篇的清单在这里第二次生效。

#102 处理数字遗产与代持：主体消失后的访问权。交易中的"主体变更"是它的商业版本。

#178 处理记录分层：尽调室里给什么、不给什么，依据同一套原则。

3. 交易中的三个时点

时点谁在问你暴露的程度关键动作
尽调期（签约前）买方、其顾问可控：你能决定给什么建立数据室，分层披露（#178）
签约到交割双方律师条款已定，事实仍在补充发现新事实须按条款处理，不能自行"消化"
交割后买方团队几乎完全暴露交接清单 + 保留期内的配合义务

最容易出问题的不是第一段，而是第二段。签约之后，团队的心理状态从"防守"转向"成交"，此时发现的新事实——比如一份旧的渗透测试报告、一台没人管的测试机、一个仍有效的服务账号——最容易被"内部消化"。而这一段的隐瞒，性质与签约前完全不同。

4. 买方会问的八类问题

#问题真正想确认的卖方常见错误
1过去 3–5 年是否发生过安全事件？是否有未了结的责任只报"已公开的"
2是否有正在进行的调查或诉讼？是否存在或有负债认为"只是内部调查"不算
3是否有已知但未修复的漏洞？交割后的修复成本用"都是低危"概括
4关键系统的访问权在谁手里？交割后能否真正接管只列在职人员
5是否有针对本公司的定向威胁？威胁是否随资产转移以"没有证据"回避
6第三方依赖与许可状况？供应链风险与合规只列主要供应商（#167）
7数据资产清单与合规基础？数据能否合法转移用"都在云上"概括
8安全团队与关键人员留任？交割后能力是否还在忽略已提离职的人

第八问在定向投放的语境下格外重要：一个刚刚经历过事件的组织，其安全团队往往处在疲劳与流失的高峰。买方知道这一点，所以会问；卖方如果只答"团队稳定"，在背景调查里很容易被推翻。

5. 陈述与保证的三条纪律

  • 准确：不把"未发现证据"写成"未发生"。前者是调查结论，后者是事实断言。
  • 可核对：每一个陈述都应能指向一份材料。没有材料支撑的陈述，在争议中等于没有。
  • 说清范围：时间范围、主体范围、系统范围。"本公司未发生"与"本集团未发生"是两个陈述。
陈述写法问题改写
"未发生过数据泄露"绝对化，且范围不明"2021-01 至 2026-10，本公司未发生依适用法律须通报的数据泄露事件"
"系统安全状况良好"无法核对"截至 2026-10，已知高危漏洞 0 项，中危 3 项，修复计划见附表"
"已采取行业最佳实践"不可验证"已实施 A/B/C 三项控制，验证记录见附件"
"无正在进行的调查"范围模糊"就本公司所知，无正在进行的监管调查；内部调查 1 项已于 2026-08 结案"

第四行的改写展示了最重要的技巧：把"无"拆成"就我所知无"与"具体有一项且已结案"。前者是法律上的谨慎，后者是事实上的诚实，两者并不矛盾。

6. 为什么"未披露"比"有事件"贵

三笔账，逐笔加重。

  • 价格账：有事件 → 买方要求价格调整或专项赔偿；未披露 → 买方在交割后主张违约，索赔基础是"如果早知道"，通常远高于实际损失。
  • 条款账：已披露的事实，可以进入"特别赔偿"或"除外条款"，责任被限定；未披露的事实，落入一般陈述与保证，责任无上限。
  • 信誉账：买方在交割后发现的第一件事，会成为它此后对你所有材料的默认假设。这一项在跨境交易里尤其明显，因为它会进入对方内部的"交易对手档案"。

值得注意的是：定向投放事件本身不一定是重大不利事项。很多买方对"被国家级行为体盯上"有心理准备，真正影响判断的是你有没有能力发现并处理。一份写得清楚的复盘（含未解项），在尽调里通常是加分项。

7. 交割后才发现：三种局面

局面触发方式后果能否挽回
买方自查发现常规扫描或接管审计违约主张、价格重谈部分：取决于披露义务条款
第三方（客户/监管）先发现外部通知交易信誉受损，可能触发回购条款困难
攻击者再次利用同一入口被复用最严重：证明"未修复"而非"未披露"极难

第三种最少见，但最能说明问题：它把"历史问题"变成"当下问题"，而当下问题的处理成本与历史问题不在一个量级。

一个实操建议：交割前做一次"遗留账号与入口"专项检查。交易期间最常见的遗留物是：测试环境的管理账号、离职人员的服务账号、为过渡期保留的 VPN、以及没人说得清用途的第三方集成。这四类东西在 #96 的设备清单与 #120 的离职清单里都出现过，交易只是把它们集中暴露了一次。

8. 数据与设备在交易中的处置

交易会同时触发前几篇里分别讨论过的三类问题：

  • 数据：哪些数据能随交易转移、哪些需要重新取得同意、哪些必须删除（#102 的历史数据、#105 的数据位置）。
  • 设备：随主体转移的设备上有什么、谁能解锁、MDM 是否随主体转移（#96 的十项残留、#160 的管控栈）。
  • 账号与关系：企业账号、Apple 商务管理、开发者账号、域名的所有权与恢复方式（#120 的 R1/R2/R3 归属规则）。

这三类的共同点是：它们在合同里通常被写成一句话，在执行时需要一份清单。清单不该等到交割日才写。

9. 加固清单（八条）

  1. 常备一份"安全事实底稿"：事件、漏洞、调查、改进项，一页可核对（#181）。
  2. 尽调数据室分层：事实轨与意见轨分开（#178）。
  3. 陈述句禁用绝对化词汇，全部加时间、主体、系统范围。
  4. 签约后保持同一套披露纪律，发现新事实按条款处理。
  5. 交割前专项检查遗留账号与入口（四类：测试账号、离职账号、过渡 VPN、用途不明的集成）。
  6. 关键人员留任方案写进交割计划，不只写在意向书里。
  7. 对外口径与尽调口径对齐（#175），避免"对客户说一套、对买方说一套"。
  8. 交割后保留配合期：材料、人员、访问，写清期限与范围。

10. 八条常见误解

误解实际情况
"没被公开报道就不用说"披露义务看事实，不看是否公开
"内部调查不算调查"在陈述里通常需要说明
"低危漏洞不用列"买方要的是完整清单与修复计划；隐瞒一项会波及全部
"签约后不用再报"多数交易文件对签约后新事实有专门约定
"有事件一定影响估值"更影响估值的是"发现与处理能力"
"口头说过就行了"陈述与保证是书面文件；口头不构成
"数据都在云上，没什么可查"云的配置、账号、导出权限恰恰是重点
"交割完成就结束了"配合期、赔偿期、信誉影响都还在

12. 总结

问题一句话答案
交易里什么最贵未披露，而不是事件本身
陈述的三条纪律准确、可核对、说清范围
买方真正关心什么你的发现与处理能力，而非"是否干净"
最容易漏的材料是什么人：离职、账号、关系型授权
签约后发现新事实怎么办按条款处理，不内部消化
交割前必须查什么遗留账号与入口四类
一句话判断标准你的每一句陈述，能否被一份材料接住

在交易里，安全历史不是一段过去，是一份可以被定价的证据。
