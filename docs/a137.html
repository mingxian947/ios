iOS 安全研究文章库 · 第 137 篇 · 防御性安全研究，不含可利用代码

iOS 相机与相册采集通路的攻击面：你以为分享的是那张照片，一起走的是位置、时间、设备和"你还拍过什么"

1. 执行摘要

  • 这一族的名字应该叫"载荷不是一个像素，是一整套上下文"。前面二十一根竖条的位置依次是进来的字节（#118 格式、#122 卷、#123 报文）、进来的调用（#119 接口、#127 插槽）、进来的设备与信号（#121 配件、#125 定位、#129 号码）、进来的操作请求（#126 辅助功能）、被合在一起的内容（#128 索引与聚合）、画到屏幕上的内容（#130 显示与捕获）、到达时被你认出成谁（#131 标识与呈现）、验证之后存续下来的能力（#132 凭证与会话）、按下之后交给谁执行（#133 派发）、什么时候被执行（#134 调度）、一次发送覆盖多少人（#135 批量投递）、很多身份怎么被组织成一种气氛（#136 群控与协同）。本篇是第二十二根竖条，它补的是这条链上唯一还没被单独测绘过的一段：内容在你的设备上被生产出来的那一瞬，系统顺手多写了什么，以及那些多写的东西跟着这张图走了多远。
  • 核心命题：相册通路的失效几乎从不是"图被偷走了"，而是"图带着它的说明书一起走了"。 一张照片在 iOS 上从来不是一个 JPEG：它是一个容器，里面装着拍摄时刻、设备身份、光学参数、方位与倾斜、可能还有经纬度、深度图、音轨、连拍关联、人脸几何，以及一份可以还原成原图的非破坏性编辑记录。你分享出去的从来不是你以为的那个东西。
  • 三层切分：A1 采集层（快门那一瞬，相机进程写进容器的全部上下文，以及其中哪些由一个你几乎不会去改的开关决定）；A2 授权层（PhotoKit 的四档授权粒度、"选中的项目"在语义上到底给了对方什么、以及授权之后新拍的那张算不算在授权范围内）；A3 外发层（分享、备份、云同步、第三方 SDK、再压缩与平台剥离——上下文在哪一跳被删掉、在哪一跳被保留、在哪一跳反而被加上）。风险密度在 A3，因为不可逆动作发生在那里；不可逆点在 A2，因为一次"允许访问相册"的授权换来的是一种持续的、你无法逐张回收的读取面。
  • 一条方法论结论，也是第十个系统性漏检：用 #66 的隐私面板、#125 的定位与传感器清单、#128 的来源清单、#130 的通路清单、#110 的落点表去做相册审计，全都会漏掉这一族。原因是同一个：这些面板审计的单位是"某个 App 能不能访问相册"，而本族的伤害单位是"某一张图在离开设备时携带了什么"——这两件事在系统里没有同一个可查对象。 权限面板告诉你三个 App 有相册权限；它无法告诉你这三家里有任何一家在你把照片发给它时，会顺手拿走拍摄位置、设备型号和你被标了名字的那张脸。本篇需要的是第十个补丁：一张"导出物核对表"——每张准备离机的图，其上下文是按哪种方式被带出去的（原文件 / 再压缩 / 截图 / 转发 / 云端链接）。
  • 后果上它给出第十一种不提权的伤害形状：伤害作为随件附带的上下文。#126 借系统功能、#127 借你请进来的代码、#130 被读走的是画面、#131 借你自己的手、#135 合法的批量在场、#136 以数量冒充共识；本篇的形状是"你没打算给的那一半，贴在你要给的那一半上"——不需要任何漏洞、任何提权、任何越权，只需要你点一次"分享照片"。
  • 撤销不对称在本族第八次成立（#107）：关掉相机定位、撤回相册权限、把照片从共享相簿移出、删除原图，全部只对未来生效。已经带位置出去的那份副本、已经进了对方服务器的那份原文件、已经存进对方相册的那张转发图，没有任何一条开关能够追回。#131 的"显示即属主"在本族第四次成立：你在分享面板上看到的一张缩略图，与对方实际收到的一个容器，不是同一个东西。
  • 可观测性的诚实定位：能核对的比 #136 多，比 #130 少。你能核对：这张图现在带着哪些元数据（文件 App 的显示信息、快速查看）、它的编辑历史能不能被还原、它在哪些云端位置有副本（iCloud 照片、备份、共享相簿）、哪个 App 在什么时间访问过相册（#66 的隐私面板，注意其记录粒度）。你永久核对不到：对方收到之后做了什么处理、有没有二次分发、平台在传输中是否剥离过、以及任何云端已删列表——iOS 上不存在这样一个视图。
  • 正向结论只有一句：把"分享这张图"重新定义成"分享这张图的上下文"，然后在离机之前把上下文当作内容来审。 具体动作只有三类，且全部当场可验证：用分享方式决定载荷（截图 / 再压缩 / 原文件是三种不同的东西）；用位置开关决定最高价值那一项（拍摄经纬度）；用落点判断决定该不该离开这台设备（对方是谁、对方服务器在哪、这份副本会不会被二次分发）。

2. 这根竖条补的是哪一块

系列里已经有多篇擦到过照片：#118 测绘了格式解析器（图被别人怎么解码），#125 测绘了定位与传感器（设备怎么知道你在哪），#128 测绘了本地索引与聚合（散落在各 App 里的内容怎么在设备内被合成一个可查询对象），#130 测绘了显示与捕获（屏幕上的东西怎么被读走），#95 测绘了追踪与指纹（不读文件也能知道你的作息），#100 测绘了健康数据（一个特别高价值的数据类），#110 测绘了多身份与落点（什么内容放在哪台设备），#121 测绘了配件与有线连接（设备到达即握手）。

但这些位置都缺同一格：内容被生产出来的那一刻起，就附带着一层用户看不见、也不由任何权限授予的东西；而这层东西的传播路径与内容本身完全不同。 #118 讲别人怎么解你的字节，本篇讲你自己怎么写进去这些字节；#125 讲传感器怎么推断位置，本篇讲位置怎么被固化进一个可分享的文件；#130 讲画面被读走，本篇讲画面连同它的说明被复制走。

这是第二十二根竖条，仍然在 iOS 内部（采集与文件层），但它造成的可见性缺口是系统口径的：系统按"App + 权限"暴露风险，而本族的最小风险单位是"一次导出 + 一个容器"，两者不同尺度。

与相邻各篇的分界必须写死：

  • 与 #118（解析器）：那一篇是读入侧（你没打开的东西系统已经替你解析过）；本篇是写出侧（你以为只给了画面，其实给了容器）。两者共用"容器"这个词，但方向相反。分界线：本篇不讨论解码缺陷、内存破坏与格式模糊测试。
  • 与 #125（定位与传感器）：那一篇的产出是"设备知道你在哪"这个推断；本篇的产出是"这个位置被写进了一个可以被转发的文件"这个物化。#125 关掉定位服务能收敛的东西，本篇里有一部分关不掉（因为写入已经发生）。
  • 与 #128（索引与聚合）：那一篇讲设备内部的聚合让单条合规内容变成敏感对象；本篇讲外部的聚合：一张图的元数据 + 另一张图的元数据 + 时间序列 = 作息与住址推断。同一件事的两个方向，#128 是内向聚合，本篇是外发后的再聚合。
  • 与 #130（显示与捕获）：那一篇的载荷是渲染结果（像素，被读走的画面）；本篇的载荷是存储对象（容器，被复制走的文件）。一个可以只靠画面说话，另一个必然带着结构化的旁证。
  • 与 #110（多身份与落点）：那一篇给"什么内容放哪台设备"的设计轴；本篇给"内容自带的那一半也算落点"的补丁：你换了一台干净设备，但你的图库导出物仍然指向旧设备的身份。
  • 与 #121（配件与有线连接）：那一篇讲导入方向（配件把东西送进来）；本篇讲导出方向（图把东西带出去），并在 §5 与 #121 的"双侧存储"律合并：照片一旦进了对方设备/对方的云端，收回动作就发生在你的能力之外。
  • 与 #95（追踪与指纹）：那一篇的标识单位是设备与浏览器；本篇里出现的是内容级标识——传感器噪声、镜头与去噪特征、连拍序号——它们不需要网络，也不需要权限就能识别"这几张图来自同一台机器"。#95 的指纹在这里不是被采集的，是被你亲手发出去的。

3. 三层切分：采集、授权、外发

3.1 A1 采集层——快门那一瞬写进去的东西

一张 HEIC/JPEG 在 iOS 上的实际构成（具体字段随版本与机型变化，核对方法见 §4）：

层内容由谁决定能否在导出前关掉
像素画面本身你不适用
拍摄上下文精确到秒的时间、曝光与光学参数、方向、色彩配置相机进程，无开关只能事后删（且要防"删不干净"）
位置经纬度、海拔、有时含方位/倾斜一个开关（相机/系统定位授权 + 精确位置）能，且这是唯一高价值可关项
多帧结构Live Photo 的视频与音轨、人像深度、全景、连拍关联拍摄模式只能不用该模式，或导出时降级为静帧
身份关联人脸识别几何（用于"人物"相簿）系统在本机维护不给图库视图即可，但已建索引不会随单张删除消失
可逆编辑非破坏性编辑记录，含"还原"能力编辑行为只有走一次重编码导出才真正落定
设备印记机型、软件版本、镜头与处理链特征采集链不能关；它是内容级指纹（§7 的 M4）

三条结论：第一，位置是唯一一个"开关明显、价值最高、且绝大多数人从没关过"的字段，所以它同时是本族最容易修和最容易漏的一项。第二，多帧结构是隐藏的载荷放大器：你以为发出去一张图，实际发出去一张图 + 一段含环境音的短片。第三，可逆编辑意味着"你以为你裁掉了背景，对方可以还原"——这一条在本族里最反直觉，因为它让"删掉的那一部分"重新变成载荷（#107 的撤销不对称在这里有一个具体到令人不适的形态：你删掉的像素没有回来，你删掉的那个记录还在）。

3.2 A2 授权层——"允许访问相册"这句话的真实含义

PhotoKit 的授权粒度（四档：无访问 / 有限访问（选中的项目）/ 完整访问 / 仅添加）看起来像范围控制，实际语义要复杂一层：

授权档字面理解真实边界你无法控制的部分
完整访问"它能看到我的照片"能看到图库的全部当前与后续内容，含隐藏与已删除之外的视图，且随时间自动扩大事后无法逐张撤销
有限访问"只给它这几张"只给这一次选中的对象，但该对象是容器（连带全部上下文）该容器的传播路径不可控
仅添加"只能往里写"写入面 ≠ 读取面，但写入的内容会成为图库对象并进入 #128 的索引写入物被别的 App 读到
无访问它什么都看不到但相机通路是另一项授权（相机权限可以拍到同一张图）两个开关彼此独立

两条结论：第一，"删除照片"与"撤销授权"是两个不同方向的收回动作，且都不回收对方已经拿到的容器（#132 的"收回不在你这台设备上发生"在本族第二次成立）。第二，相机授权与相册授权是分开的：一个不能读图库的 App 仍然可以让你现场拍一张带完整上下文的新图——这是本族最常见的漏项，因为审计的人只查相册权限。

3.3 A3 外发层——上下文在哪一跳被删、在哪一跳被加

离机方式上下文命运谁在这里做决定
原文件分享（隔空投送、存到文件、邮件附件）完整保留，含位置与编辑记录你
聊天 App 内"发送照片"（多数默认再压缩）通常被压缩并剥离部分字段，但版本与设置会变对方 App 的实现，你看不见
聊天 App 内"作为文件发送"完整保留（与上一行是两个不同按钮，视觉上却像同一件事）你
截图后再发画面被重栅格化，原容器丢失；但截图带来新的上下文（截图时间、你的设备名、状态栏内容）你，且经常是误选
复制到社交平台（平台侧二次处理）大多剥离，部分平台保留位置；二次分发后无法追平台
iCloud 照片 / 我的照片流类同步原容器上云，跨设备可被再次导出你开的开关
共享相簿 / 协作播放列表原容器 + 参与者身份 + 你的姓名与头像，且位置是这类功能公开承认会被分享的你
第三方云盘 / 备份 SDK取决于该 SDK 是走图库还是走文件，可能整批上传含隐藏相册之外的全部你的一次授权

一条贯穿性结论："发送照片"和"发送文件"在 iOS 的分享面板里挨在一起，但它们在风险上是两个物种。 本族一半的现实伤害来自有人选了后者而以为自己在做前者。

4. 八个核对点（全部可当场在本机验证）

  1. P1 这张图现在带不带位置：在"照片"里上滑看信息卡的地图；或在文件 App 长按 → 显示简介。判定式：能看到地图 = 有经纬度。
  2. P2 它是不是 Live Photo：信息卡里的实况标记，或文件名/配对文件。含音轨的实况图是本族最典型的"多买了一半"。
  3. P3 它能不能被还原：打开编辑 → 若有"还原"按钮，说明存在可逆编辑记录，裁掉的内容仍在容器里。
  4. P4 它在几个云端位置有副本：iCloud 照片是否开启、是否含备份、共享相簿、第三方云盘 App 的自动上传开关（#103 的残余配置思路在此复用）。
  5. P5 相机与相册两个授权分别给了谁：设置 → 隐私与安全性 → 照片；再单独看 相机。分开查，因为只查一个必然漏。
  6. P6 精确位置对相机是否开着：定位服务 → 相机 → 精确位置。这是唯一一条"改一次、影响所有未来照片"的设置。
  7. P7 分享面板上你到底在发哪一种：图片 vs 文件的视觉差异只在预览与文件名上；对敏感图，宁可先"存到文件"再决定。
  8. P8 人物相簿与隐藏相簿的存在本身：它们的可见性受 Face ID 保护，但它们不构成安全边界——图库授权之下、备份之内的边界问题不能靠"隐藏"解决。

5. 存续表：一张图到底能活多久、在几个地方同时活着

（沿用 #116 的证据衰减表与 #107 的撤销不对称，本族把它推到最具体的形态。）

位置谁持有你能否收回收回的真实效果
本机图库你能（删除）进入"最近删除"，通常保留约 30 天；期满或手动清空才是真删
隐藏/已隐藏相簿你能仍是同一个容器与同一份元数据，只是少一个入口
本机备份 / iCloud 备份你 + 服务端不能逐张收回只有覆盖式备份生命周期管理，且删除原图不会即时删除既有备份里的副本
iCloud 照片库服务端 + 你的所有设备逐张删除会跨设备传播（有延迟）但对方已导出/已下载的副本不受影响
共享相簿参与者能移除已保存进别人图库的副本，永久不受影响
对方设备对方不能一切收回动作在这里失效
对方服务器 / CDN平台只能靠请求保留期与再分发不受你控制（#105 的披露边界在此同样成立）
截图谁截谁持有不能原图上下文丢了，但新增了一份"谁在什么时候看到过它"的痕迹（#130 的通路）
索引与人物库系统部分图库条目消失后，已建立的人脸几何与索引不会因为你删一张图而回到过去

三条纪律：先决定离机方式，再决定发不发（发出去之后再研究怎么剥元数据，往往是二次分发）；上下文只在原容器里存在，所以"要不要给原文件"必须逐次决定；对方手里的那份，唯一治理手段是关系与流程，不是技术（#120 的"关系类授权必须创建方撤销"在这里表现为：你能撤的是访问，不能撤的是副本）。

6. 七类契约违背

  • M1 图像即全部载荷。把"一张照片"读成"一段画面信息"，忽略它是容器（本族唯一必需的成功条件）。
  • M2 删除即消失。删除只作用于你这一侧的一个视图；备份、云端、对方设备、索引各自独立存续（#107 撤销不对称第八次成立）。
  • M3 授权粒度即范围。"只给它这几张"限制的是图库的哪几条，不限制这几条里装着什么；也不限制该 App 用相机让你现拍一张。
  • M4 压缩即清洗。再压缩会剥离一部分字段，但不由你保证、随版本变、且剥离之后仍留下内容级印记（同机连拍的噪声特征足以关联"这几张来自一台设备"）。
  • M5 云端优化即剥离。"优化储存空间"改变的是本机存的是全量还是缩略，不改变云端原容器，也不意味着导出时会给你小版本。
  • M6 看到缩略图即已分享。分享面板上的预览与实际载荷不是一回事（#131 显示即属主第四次成立）。
  • M7 关闭权限即断源。关相册权限阻止未来访问，不撤销已导出容器，也不阻止对方转发它已经拿到那份。

7. 后果落点（接 #91 的后果轴）

  • C2 隐私与关系图谱（本族主战场）：一张带位置的图给出住址、通勤、常去场所；一个连拍/多张时间序列给出作息；共享相簿与人物相簿额外给出关系图（谁在你的相册里被命名）。#95 的追踪原料在这里不需要任何 SDK 配合。
  • C1 决策错误 → 人身与财产：把"我在哪儿"从推断变成证据，是 #99（同居控制者）与 #108（高危个体）里最省成本的一条定位路径——攻击者不需要攻破任何东西，只需要是你通讯录里那个会看图的人。
  • C3 声誉与关系伤害：截图 + 原容器 + 编辑还原三者叠加，能让"已经删掉的内容"重新成为可讨论对象；对组织，员工对外发布的图泄露厂区、车牌、工位、白板（白板是最贵的一类，本族里它不是截图问题而是元数据之外的"画面内内容"问题，归 #130）。
  • C4 服务与费用滥用：iCloud 储存被自动上传撑满、备份链里长期存着敏感图，属于低烈度但高持久成本。
  • C5 可用性：对个体是"要不要发"的决策负担；对高危个体是来源污染——你的联系人被要求"拍一张现场"时，他们并不知道自己正在生成一个可识别你的文件。
  • C7 归因：与 #135/#136 不同，本族归因方向是可用的（内容级印记能证明同源），但这恰好是受害侧的坏消息：你能证明这张图来自那台设备，对方也能。 所以本篇的归因上限不是"无法归因"，而是"归因能力不属于你"。
  • 可逆性的特殊位置：本篇的补救几乎全在离机之前；一旦离机，只剩关系治理与删除请求。这条不对称决定了整篇文章的重心必须在"方式选择"而不是"事后清理"。

8. 审计法与判定式

8.1 个人侧：离机之前三步

  1. 要不要位置（P6 决定未来，P1 决定当前；敏感场合先把相机精确位置关掉，再拍）。
  2. 要不要原容器（决定发送方式：再压缩图片 / 截图 / 原文件三选一；对含可逆编辑、实况、全景的图，任何"原文件"路径都是整包外送）。
  3. 要不要对方能转发（共享相簿、群相册、云盘链接是三种不同的转发面，前两种默认可被保存副本）。

8.2 判定式（可执行、当场自证）

"我分享的是画面，还是容器？" 判据只有一个：对方能不能打开"显示简介"并看到地图、设备名、拍摄时间和还原按钮。 如果答案是"能"，那你要审的就不只是这张图，而是这张图所声明的全部上下文；本篇要求你在这个答案出现时改变发送方式，而不是改变图片。

8.3 组织侧：五个动作

  1. 把"对外发布的图"纳入发布前审：位置、门牌、车牌、屏幕与白板、工装、二维码（二维码是容器之外的容器，一张图里可能替你发出一条链接，与 #133 直接接口）。
  2. 对员工手机批量上传的图库做落点约束：企业云盘 App 的"相册自动备份"是一个你从未逐张授权却覆盖全库的通路，与 #110 的落点分类必须对齐。
  3. 共享相簿/协作相册按群组成员关系管理，离职与项目结束时把"人"从关系里撤出（#120 的关系类撤销）。
  4. 对涉密场所立一条零判断规则：不拍照，比拍了再删元数据有效得多——因为 M4/M5 都不由你保证。
  5. 在季度巡检表（#104）加一行："本季对外发布图片是否走过位置与还原检查；抽查样本与结论"。这行不是发现攻击，是检验第 1 项是否真的在做。

8.4 高危个体（接 #108）

  1. 默认假设"任何你拍下的东西都带位置"，直到你亲自为这台设备关掉它；这一条不需要每次判断，属于 #97 说的"家庭规则"型措施。
  2. 不要以为"发到阅后即焚就安全"：阅后即焚消灭的是本机副本，不消灭容器在对方设备上短暂存在时已被二次栅格化（截图）的可能（#130）。
  3. 来源侧要单独教育：你的线人拍给你的每一张图，都在替他们自己声明设备与位置；最小化方案里应包含"用什么设备拍、拍完怎么导出"。
  4. 新设备不等于新图库：从旧设备迁移（#139 的迁移通路）会把旧容器与旧上下文原样带过来——#110 的七条跨域边界里，图库是最容易被忽略的那一条。

9. 设备端可观测性——本篇的诚实边界

  • 能核对：单张图的元数据、位置、编辑可还原性、实况配对；两个权限的授予清单与最近访问时间（粒度有限）；iCloud 与备份的开关状态；共享相簿成员。
  • 不能核对：对方收到了哪种载荷（再压缩还是原文件，取决于对方 App 的当前版本）、平台在传输链上剥离过什么、云端既有备份里还存不存着它、人脸索引与人物库的实际覆盖范围。
  • 结论上限："改变离机方式 + 关掉最高价值字段"，不是"证明泄露没发生"。本篇不提供任何对已导出副本的追溯能力，因为那种能力在端侧不存在。
  • 与相邻各篇同格的位置：这是第五个"风险单位不在这台设备上"的竖条（#129 的签发方、#132 的服务端会话、#135 的批次统计、#136 的协同关系），但比前四个更可自救：前四个的自救点在服务端，本篇的自救点在按下分享之前。
  • 必须写出的自我限制：本篇列出的字段与路径，同时也是"如何让一张图携带更多可识别信息"的清单。因此本篇刻意不给出任何字段构造、伪造、抹除工具的操作步骤，也不给出任何规避对方剥离或反检索的做法（见文末说明）；所有条目一律写成"发送前你应当检查自己这一侧"。

10. 加固清单（按当场可验证排序）

10.1 个人

  1. 关掉相机的精确位置（P6）：一次操作影响全部未来照片，是本族性价比最高的一条。
  2. 把"发照片"默认理解为"发原文件"，直到你确认所选通路会再压缩；对敏感图先自查再发（P1/P3）。
  3. 有可逆编辑的图，先"导出为静态新文件"再分享（P3 的还原按钮存在 = 裁掉的部分还在）。
  4. 实况图当成视频处理（含音轨）；不想带声音就用静帧方式。
  5. 相册授权优先给"有限访问"，并且单独检查相机权限——两个清单分开看，只看过一个是本族最常见的审计漏项。
  6. 共享相簿只放可公开的图，并定期清理成员；把它当作一个公开发布渠道而不是私人备份。
  7. 删除之后记得"最近删除"仍保留约 30 天；处置敏感图时先"永久删除"再报告处置完成。
  8. 不要把云盘 App 的"相册自动备份"当作备份功能而不当作导出功能——它是一条持续的整库外发通路。

10.2 组织 / 企业侧

  1. 发布前审（位置、可还原、门牌车牌、白板与屏幕、二维码）写进流程，而不是写进培训。
  2. 对企业设备上的云盘/备份类 App 明确落点策略：允许备份什么、不允许自动上传哪些相簿。
  3. 建立离职时的共享相簿与协作清单撤销步骤（人从关系里撤出，而不是内容从库里删掉）。
  4. 涉密场所采用不拍规则，替代"拍了再处理"规则——后者依赖你不控制的实现。
  5. 把 §8.3 第 5 项并入 #104 的季度台账，并保留抽查样本作为证据。

10.3 高危个体

  1. 把"拍摄即声明"当作一条固定的来源沟通事项，写进方案书的最小化清单。
  2. 备用机与角色分离（#110）必须包含图库：用于敏感联络的设备不应携带可识别你常用地点的历史图库。
  3. 迁移与恢复（#139）之后重跑 §4 的八项核对，因为旧容器会原样搬过来。
  4. 心理成本要写进方案：本族的伤害形式常常是"我发的时候没想那么多"，复盘比检测有效。

11. 十条常见误解

  1. "照片就是那张画面。"——它是一个容器，本篇的全部内容都在这句话之外。
  2. "我删掉了，就没有了。"——你删掉的是你这侧的一个视图；备份、云端、对方设备、索引各自存续（M2）。
  3. "我只给了它两张照片，所以范围很小。"——范围小，但深度是整份容器；且授权与相机是两条独立通路（M3）。
  4. "聊天软件会压掉信息的。"——多数时候会，但不由你保证、随版本变、且"作为文件发送"绕开它（M4）。
  5. "截图再发就干净了。"——丢掉了旧上下文，新增了截图时间、设备名与状态栏内容，且画面内容风险原样保留。
  6. "隐藏相册是安全边界。"——它保护的是入口，不是容器；授权、备份与迁移不认"隐藏"。
  7. "关掉权限就断源了。"——收回未来访问，不撤销已导出副本，也不阻止转发（M7）。
  8. "开了 iCloud 高级数据保护，照片元数据就被清掉了。"——端到端保护改变的是可读性，不是容器里有什么；这是两个正交问题。
  9. "换了新手机，旧的位置信息就跟我没关系了。"——迁移把旧容器整批带过来（#110 的跨域边界）。
  10. "这属于 iOS 的隐私缺陷。"——不是：iOS 在写元数据上遵循公开的文件规范，缺陷在于没有任何一个面板把"这张图离机时会带走什么"作为一个可审计对象（第十个系统性漏检）。

12. 与既有各篇的接口

  • 接 #118（解析器）：读入侧 vs 写出侧；两篇合起来才是"容器"的完整攻击面。
  • 接 #125（定位与传感器）：那一篇给出"设备知道"，本篇给出"设备把这个知道写进了可转发文件"。
  • 接 #128（索引与聚合）：#128 是设备内聚合，本篇是外发后由别人做的再聚合；同一风险定律的两个方向。
  • 接 #130（显示与捕获）：渲染结果 vs 存储对象；截图是两者的交界（原容器丢失、新容器生成）。
  • 接 #95（追踪与指纹）：内容级指纹是本族唯一不需要权限也不需要网络的识别通路。
  • 接 #110（多身份与落点）：图库是七条跨域边界之外新加的一条：旧设备的上下文会随图库迁移进入新身份。
  • 接 #107（撤销不对称）：第八次成立；本篇把它具体到"删除原图 / 撤回授权 / 移出共享相簿"三个都不追溯的动作。
  • 接 #132（凭证与会话）、#120（关系类撤销）：副本的治理是关系与流程问题，不是开关问题。
  • 接 #100（健康数据）：医疗场景里"拍一张检验单"是最常见的合规外发行为，其载荷正是本篇的容器；两篇的高危清单应合并执行。
  • 接 #99（同居控制者）、#108（高危个体）：本族在这两类人群里是成本最低、收益最高的推断通路，因为攻击面来自日常行为而不是漏洞。
  • 接 #133（链接与派发）：图里的二维码与链接预览是"画面里藏着一个可点击世界"的边界，本族只指出它存在，判定归 #133。

13. 总结

本篇把整族的场地放在一条被系列忽略了二十次的通路上：内容被生产出来的一瞬，与它一起被写进去的那一层上下文，以及这层上下文离开设备的方式。 三层里，A1 给出"你从未被问过的那部分"（位置、多帧、可逆编辑、设备印记），A2 给出"你以为的范围控制其实只限制条目不限制深度"，A3 给出"哪一跳删、哪一跳留、哪一跳加"，并明确指出在 A3 之后你只剩关系治理。它的后果主要落在 C2 隐私与关系图谱上，其次是 C1 的人身与财产推断链；它的补救几乎全部前置在离机之前。正向结论只有一句：分享之前先回答"我发的是画面还是容器"，如果对方面板里能看到地图和还原按钮，那就换一种发法。
