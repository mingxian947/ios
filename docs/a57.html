iOS WebKit JIT 硬化与 Coruna/DarkSword 利用对抗演进

编制日期：2026-10-18 数据来源：WebKit 项目文档、Google Project Zero、Apple 安全公告、CVE 情报库 性质：防御性安全研究分析（Defensive Security Research），不提供可利用代码

1. 执行摘要

JIT（即时编译） 是 WebKit 攻击面中最肥沃的一片土壤：为了性能，浏览器必须在运行时生成可执行代码，而这打破了"数据不可执行"这一最基本的内存安全假设。

Coruna 与 DarkSword 的初始立足点都在 JSC（JavaScriptCore）的 JIT 编译器中：前者依赖类型混淆，后者依赖 DFG 层 GC 缺陷。理解 Apple 为封堵这类缺陷所做的JIT 硬化工程，是理解现代 iOS 攻击链成本结构的必要条件。

本文梳理：

  1. JSC 四级 JIT 管线为何天然产生可利用缺陷
  2. Apple 的五类 JIT 硬化措施及其实际效果
  3. Coruna / DarkSword 如何绕过硬化取得原语
  4. 锁定模式禁用 JIT 为什么是迄今最有效的单点防御
  5. 防御者如何评估"JIT 相关 CVE"的真实风险等级

2. JSC 的 JIT 管线与缺陷成因

2.1 四级执行管线

JavaScript 源码
   ↓ 解析
[1] LLInt（低级解释器）        ← 冷代码，逐条解释
   ↓ 热点计数
[2] Baseline JIT               ← 快速、简单的机器码
   ↓ 更多执行
[3] DFG JIT（DataFlowGraph）   ← 激进优化：内联、逃逸分析、类型推测
   ↓ 最热路径
[4] FTL / B3 JIT               ← 基于 LLVM 的进一步优化

关键点：DFG 与 FTL 是投机优化（speculative optimization）——编译器假设某变量始终是某类型，生成针对该类型优化的机器码。一旦假设被打破，代码会读到错误类型的数据。

2.2 为什么 JIT 必然产生类型混淆

DFG 假设: obj 是 Int32Array
   ↓ 生成优化的加载指令（假设元素为 4 字节整数）
运行时: obj 实际是 DoubleBlock（8 字节浮点）
   ↓ 按错误布局解读内存
读取到相邻字段的原始位模式 = 把数据当指针 / 把指针当数据
   ↓
addrof（读对象地址） / fakeObj（伪造对象）

这是结构性问题，不是实现疏忽。只要 JIT 需要类型推测 + 投机执行，就必须依赖"假设破坏时正确失效（OSR exit）"的逻辑，而该逻辑本身极易出错。

2.3 JIT 提供的三类攻击增益

增益说明
可执行内存JIT 页天然 PROT_EXEC，攻击者获得无需绕 NX 的执行位置
强类型原语类型混淆直接给出 addrof/fakeObj，比栈溢出更强大
可控内存布局JS 对象由攻击者用脚本大量创建，堆塑形门槛低

3. Apple 的 JIT 硬化工程

3.1 Gigacage（巨大笼）

项目说明
原理把所有 JS 堆对象放进一个巨大的预留虚拟地址区域（历史上 1TB 预留）
效果JS 堆内指针可用窄偏移（32 位）表示而非完整 64 位指针
攻击影响一个越界写只能落在 Gigacage 内，无法直接指向任意内存
局限若同时存在"读 Gigacage 基址"的泄露，绕过重新可行

3.2 Pointer Bloating（指针膨胀）

项目说明
原理在 JS 对象内部把指针存储为"索引 + 基数"或带标记形式，而非裸地址
效果弱化为"相对读写"，攻击者必须先获得绝对地址泄露
攻击影响迫使链条增加一步（泄露基址），提高成本

3.3 copy-on-write JIT 页保护

项目说明
原理JIT 生成的代码页写权限与执行权限分离；写完后设为只读可执行
效果攻击者不能直接改写 JIT 机器码注入 shellcode
攻击影响迫使使用 ROP/JOP 或寻找其他可写执行路径

3.4 强化 OSR Exit 与调试检查

项目说明
原理更严格校验类型假设破坏路径；加入断言与不变式检查
效果部分类型混淆缺陷在触发时先崩溃而非静默错误解读
副作用崩溃会生成 Crash Report——对防御者是证据，对攻击者是暴露风险

3.5 移除/限制高危 Web API

措施效果
收紧 WebAssembly 可写代码减少另一条 JIT 执行路径
强化 ArrayBuffer/TypedArray 边界检查削弱越界读写
减少跨进程 IPC 参数信任削弱链内跳转

4. Coruna 与 DarkSword 如何绕过硬化

4.1 共同的必要步骤：泄露基址

两类硬化都把问题转化为"你必须先知道基址"。因此链条第一步都变成信息泄露（详见本仓库 #51）：

类型混淆 / GC 缺陷
   ↓ 获得相对读写
扫描相邻内存找系统库/引擎指针
   ↓ 计算 Gigacage 基址 / dyld shared cache slide
把相对读写升级为绝对读写
   ↓
后续逃逸

4.2 Coruna 的做法

特征说明
多链分版本适配老版本（iOS 13–14）硬化弱，链更直接；新版本需组合多个 CVE
用 CVE 数量换硬化绕过23 个 CVE 中相当比例是"泄露类"，专为基础原语服务
复用稳定组件一旦在某版本取得可用的泄露 + 写组合，长期复用

4.3 DarkSword 的做法

特征说明
选择 DFG GC 缺陷GC 的 free/move 时序错乱产生的悬垂引用，比纯类型检查错误更难在硬化中根除
利用已释放块的可控复用攻击者可精确决定"释放后被什么对象填充"，直接控制读到什么
不依赖改写 JIT 码走 ROP/JOP + 合法签名指针，规避 CoW 页保护

关键洞察：硬化没有消灭 JSC 漏洞，只是改变了漏洞的形态——从"直接任意写"变为"必须先泄露、再相对写、再升级绝对写"。链条变长了，成本变高了，但并未失效。

5. 锁定模式：从根上移除攻击面

5.1 为什么"禁用 JIT"是最强单点防御

逻辑说明
无 JIT → 无 DFG/FTL 投机优化类型推测错误这一整类缺陷不可能存在
无 JIT → 无可执行内存页生成攻击者失去现成的执行位置
无 JIT → 硬化不再是"加密钥"而是"拆门"不是提高成本，而是消除成本
禁用 JIT 后：
  需要新的原生代码执行漏洞（非 JIT 类）
    → 面收窄到解析器（ImageIO/CoreText/媒体）
    → 而这些面同时受 BlastDoor / 附件限制约束
    → 攻击链可行性断崖式下降

5.2 实际效果佐证

  • 已公开的多条高级链在环境探测阶段检测到锁定模式即主动中止（避免在无收益场景消耗并暴露零日）
  • Apple 明确指出多数高级威胁针对极少数人，并建议其开启

5.3 代价

代价说明
Web App 性能显著下降复杂 JS 应用变慢
部分 Web 功能不可用WASM、部分游戏/协作工具
WebGPU/WebGL 禁用3D/地图/部分可视化功能失效
消息附件限制图片/链接预览功能减弱

这是典型的"以功能换攻击面"——对绝大多数用户代价不可接受，对 T0 人群则极其划算。

6. 其他降低 JIT 暴露的手段

手段效果可行性
完全禁用 JavaScript彻底消除 JSC 攻击面高（Safari 设置，但很多网站不可用）
改用非 WebKit 内核浏览器⚠️ iOS 上无效——所有 iOS 浏览器都用 WebKit❌
不访问不明站点减少触发机会中（水坑正是针对"你会访问的正规站点"）
及时升级修补已知 JIT 缺陷高（性价比第一）
企业限制 WebKit 用途减少暴露场景中

重要纠正：在 iOS 上"换浏览器"不能规避 WebKit 漏洞——这是与桌面平台的关键差异。

7. 防御者实用指南

7.1 如何评估 JIT 相关 CVE 的真实风险

CVE 描述特征风险评级理由
"Type confusion in JavaScriptCore"极高直接给出攻击原语起点
"Improper access control in JSC"高常可用于绕过硬化
"Out-of-bounds read/write in WebKit"极高相对读写 → 绝对读写升级路径
"Use-after-free in WebKit/WebGL"高GC/生命周期缺陷，DarkSword 型起点
"Processing maliciously crafted web content may lead to memory corruption"极高Apple 的 RCE 标准措辞
仅性能类、无内存语义低不构成链条组件

7.2 补丁优先级判断法

1. 该 CVE 是否属于"初始执行"环节（JSC/解析器）？
2. 该 CVE 是否属于"泄露"环节（信息泄露）？
3. 该 CVE 是否与已公开在野利用链的组件重合？
   → 三者任一为"是"，应列为最高优先级
4. Apple 使用 "actively exploited" 措辞 → 立即部署

7.3 关键统计认知

历史上被在野利用的 iOS 漏洞中，初始执行 + 信息泄露两类合计占比极高。这意味着：

组织的补丁优先级如果只看"有没有 RCE"，会系统性低估泄露类 CVE——而泄露缺失时链条同样无法成立（见 #51）。

8. 演化预测

趋势判断
JIT 硬化继续但不会根除缺陷✅ 投机优化的本质决定缺陷持续产生
攻击向非 JIT 解析器迁移✅ CoreText/ImageIO/媒体/字体（但受 BlastDoor 压制）
WebAssembly 成为新的 JIT 类面⚠️ 值得高度关注——同样有编译期投机优化
逃逸面权重上升（GPU/驱动）✅ 已在 DarkSword 中显现
锁定模式成为高危人群标准配置✅ 唯一能移除该面的手段

最值得关注的新面：WebAssembly 的运行时编译与 AOT 机制在语义上与 JSC JIT 同构，同样依赖边界检查与类型正确性。历史上每次新执行模型引入都会带来一段高缺陷密度期——这符合本系列反复出现的规律：攻击者总在选择"功能必需 + 实现新 + 审计少"的组件（见 #52）。

9. 总结

#结论
1JIT 的性能收益与内存安全假设天然冲突，投机优化必然持续产生类型混淆类缺陷
2Apple 的硬化（Gigacage、指针膨胀、CoW 页保护）没有消除漏洞，而是把"直接任意写"变成"需先泄露的多步链条"
3Coruna 用 CVE 数量堆过硬化，DarkSword 用 GC 时序缺陷绕开硬化检查——两者都是对硬化成本的工程响应
4禁用 JIT 是全链条中唯一的"移除型"防御，效果远超任何检测与控制措施
5iOS 上换浏览器无效（共享 WebKit），这一常见误解会误导防御投资决策
6WebAssembly 是下一个符合"新实现 + 审计不足"判据的执行面，应提前纳入风险评估
7泄露类 CVE 应与 RCE 类同等优先修补——缺任一环链条不成立，但补齐一环远比补齐全部容易

一句话总结：

JIT 硬化把 iOS 攻击链从"两三个漏洞"推到"六七个漏洞"，这就是防御的价值——不是阻止攻击，而是让攻击贵到值得怀疑。 而锁定模式更进一步：它直接取消了这个市场。
