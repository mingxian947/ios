Coruna 与 DarkSword 场景下的运营商侧信号：它能证明连接，不能证明意图

1. 执行摘要

  • 在定向投放的处置链里，运营商是最常被想当然、也最常被真正忽略的一环。很多人默认"运营商什么都看得到"，实际上它看到的是连接，不是内容；是计费，不是意图。
  • 核心命题一：运营商手里最有价值的东西，不是流量，而是号码与 SIM 的生命周期记录。 换卡、补卡、携转、停机、复机，这几条时间戳往往比任何设备日志都更能解释"为什么短信验证码没有到我这里"。
  • 核心命题二：运营商是"当时只有它知道"的少数场景的唯一证人。 短信是否投递、是否被转发、号码是否被复机、是否出现异常漫游——这些事实在事件发生之后，设备侧通常已经没有任何痕迹。
  • 核心命题三：发起请求的路径不由你决定。 个人能自助拿到的是详单与业务记录；接入记录与位置信息通常只在法律程序下由侦查机关调取，周期以周甚至月计（#170）。
  • 核心命题四：漫游、时区与计费口径，会把一条干净的时间线搅成三份互相对不上的材料。 在把运营商数据写进报告之前，先统一口径，再谈结论（#178）。
  • 核心命题五：运营商数据只能回答"发生了什么"，不能回答"谁干的"。 把连接记录当作归因证据，是最常见的越界（#194）。
  • 一句话结论：把运营商当成"号码与链路的登记处"而不是"监控方"，你能从它那里得到的结论会比预期少，但每一条都很难被别的东西替代。

2. 这一篇补哪一格

本系列此前讨论过的"外部主体"，都还差运营商这一块：

篇目主体它掌握的是
#149 平台方主动通知与被告知窗口设备与账户平台账户侧访问与设备注册
#187 向平台方请求记录设备与账户平台你 → 平台的请求形态
#189 身份提供商与单点登录的会话处置身份服务商会话与联邦断言
本篇 #192电信运营商号码、SIM、链路、投递与计费

关键区别在于：平台方记录的是"你的账户被谁用过"，运营商记录的是"你的号码在什么时候、以什么方式活着"。定向投放里，"号码活着但人收不到"和"号码根本没活过"是两种完全不同的处境，而只有运营商能给出这个区分。

同时本篇与 #159（服务端与账号侧处置闭环）互补：#159 处理的是账号侧存续项，本篇处理的是号码作为恢复通道时的存续项。

3. 运营商手上的五类记录

按"能不能拿到"和"有多有用"两个维度排一次序：

类别典型内容可得性对事件的意义
订阅与实名登记开户信息、证件、副卡关系、套餐高（本人可查）确认号码归属与副卡是否存在
计费与详单通话、短信条数、流量、增值业务订购高（本人可查，通常可回溯数月）发现未授权的增值业务与异常开销
SIM/eSIM 生命周期换卡、补卡、挂失、复机、携转、停机中（本人可申请，部分需到厅）识别 SIM 交换与号码劫持
投递记录短信是否下发、是否送达、失败原因低到中（通常只给汇总）判断验证码为何未到
接入与位置基站接入、漫游地、IP 分配低（一般需法律程序）粗粒度活动范围，不能定位个人

第三行是本篇的核心。 定向投放者如果想绕开短信二次验证，最省力的路径往往不是攻破设备，而是拿到号码——补卡、复机、或通过运营商侧的业务变更把短信导向别处。这条路在设备日志里几乎不留痕迹，在运营商记录里却是一条完整的时间线。

4. 三条你可以马上自查的事

不需要任何程序，今天就能做：

  1. 打一份近六个月的详单。 看两样东西：未曾使用的增值业务（可能是开通渠道被利用），以及在你"以为没收到短信"的时间窗内是否有短信下发记录。
  2. 查 SIM 变更历史。 换卡、补卡、复机、副卡添加，每一条都要能解释。解释不了的那一条，优先级高于任何设备侧异常。
  3. 确认号码当前的业务状态。 是否被设置过呼叫转移、短信转移、副卡、亲情号、以及"停机保号"。这些业务大多可以在营业厅或 App 内一次性查全。

三条共同点：它们都是"号码作为身份通道"的配置项，而配置项是攻击者最喜欢改、受害者最不容易看的地方。

5. 运营商给不了的四样东西

把期待先降下来，后面的沟通才有效：

你想要的现实替代路径
短信内容运营商不存储个人短信内容设备侧备份、iMessage 走平台侧（#187）
精确位置只有基站级粗粒度，且通常需法律程序设备"查找"历史、照片地理位置（#188）
"我是否被定向攻击"运营商不做此类判断，也没有输入综合设备侧与账户侧材料自行判断（#147）
对方是谁连接记录只到号码与 IP 段归因交给专业方，不要自行下结论（#194）

第 3 行与第 4 行是最容易引发失望的两条。运营商的数据是关联性证据：它能证明某个时间点发生了某件事，但无法证明这件事与另一个人有关。

6. 什么时候运营商是唯一证人

四种场景，设备侧与平台侧都帮不上忙：

  • SIM 交换。 号码被复机到另一张卡上，验证码在别处被接收。设备侧看到的是"我收不到短信"，平台侧看到的是"登录成功"。
  • 短信转发与呼叫转移。 业务在运营商侧配置，设备侧可能完全没有提示。
  • 号码找回流程被滥用。 攻击者通过客服渠道完成身份核验，把号码转移到自己控制的卡上。
  • 异常漫游。 设备在你身边，号码却在另一地区产生接入记录——这可能意味着号码被复制，也可能只是计费延迟，必须由运营商区分。

这四种场景的共同结论是：当"第二条因子"本身被接管时，所有基于它的判断都要重做。

7. 请求路径与时限

请求类型谁发起典型耗时你能得到的形式
本人业务查询你即时到数个工作日详单、业务清单、SIM 变更记录
本人投诉与工单你数个工作日工单答复，通常不构成证据
侦查机关调取报案后的办案单位数周到数月调取回执与提取记录
司法鉴定协助鉴定机构经委托数周鉴定意见中的引用（#195）

第二行经常被误当成第三行。 客服工单是服务记录，不是证据；它可以帮助你确认事实，但写进报告时需要注明来源等级（#178 调查记录的分层）。

提前准备的材料只有三样：号码实名信息、事件时间窗、以及"你要证明的具体命题"。命题写得越具体，办案单位越容易判断该调哪一类记录（#187 的五要素同样适用）。

8. 漫游、时区与计费口径

同一件事，在运营商材料里可能出现三份不同的时间：

  • 计费时间：账单出账时刻，可能晚于事件数小时到数天。
  • 投递时间：短信下发与送达是两个时刻，失败重试会产生多条记录。
  • 接入时间：基站记录以本地时区书写，漫游时可能保留归属地时区。

处置纪律只有一条：先把所有时间统一到一个口径（建议 UTC），并在报告里注明每个时间戳的原始口径与换算方式。 不做这一步，后面的"时间线对不上"会消耗掉大量本可用于判断的注意力。

9. 六步处置顺序

  1. 冻结号码侧的高风险业务：关闭呼叫转移、短信转移、副卡与不必要的增值业务。
  2. 固定 SIM 生命周期记录：截图、导出、记下查询时刻与经办渠道。
  3. 核对详单与业务清单，标出解释不了的条目。
  4. 统一时间口径，建立一张运营商侧事实表。
  5. 按需报案，把"要调取什么"写成具体命题（#179）。
  6. 在报告中标注来源等级：本人查询 / 客服答复 / 调取回执，三者不可混用。

第 1 步之所以排在最前，是因为它可逆、成本低、且直接切断最常见的二次利用路径（#184 的可逆优先原则）。

10. 加固清单（八条）

  1. 给号码开独立保护：运营商侧的账户密码、客服密码、业务办理验证，不要与其它账号共用。
  2. 定期查 SIM 变更：把它当成季度动作，而不是出事才查。
  3. 关闭用不到的转移类业务：呼叫转移、短信转移、副卡，不用就关。
  4. 给关键账号加硬件因子：把"号码"从单点依赖降为多因子之一（#189）。
  5. 记下运营商侧的经办时刻：每次查询都留截图与时间。
  6. 统一时间口径：所有材料换算到 UTC 并注明。
  7. 区分来源等级：本人查询、客服答复、官方回执分级标注。
  8. 不把连接记录当归因：运营商数据只用于事实认定，不用于指认。

11. 八条常见误解

  1. "运营商能看到我手机里的一切。" 它看到的是连接与计费，看不到内容。
  2. "收不到验证码就是我手机有问题。" 也可能是号码侧被接管。
  3. "补卡记录不重要。" 它往往是整条链上唯一的书面痕迹。
  4. "客服说没问题就是没问题。" 客服答复是服务口径，不是证据口径。
  5. "详单可以证明我没做某件事。" 它能证明号码侧发生的事，不能证明设备侧。
  6. "漫游记录能定位人。" 只能给出基站级范围，且需法律程序。
  7. "运营商能告诉我攻击者是谁。" 不能，也不应要求它这么做。
  8. "这些都是运营商的义务。" 大多数记录的提供受法律与政策约束，不是义务清单。

12. 与既有各篇的接口

  • 与 #149 / #187 并列：平台侧与运营商侧是两条互不重叠的证据线。
  • 与 #159 衔接：号码是账号恢复通道，处置时与账号存续项一起清点。
  • 与 #170 衔接：跨境号码的记录调取，时间尺度由司法协助决定。
  • 与 #178 对接：运营商材料进入记录体系时，必须标明来源与口径。
  • 与 #189 对接：短信因子被接管后，所有依赖它的会话都要重新评估。
  • 与 #195 对接：需要把运营商材料作为鉴定依据时，先确认其形式合法性。

13. 总结

运营商在事件里的角色，可以压缩成三句话：

  1. 它证明存在，不证明动机。
  2. 它最有用的时候，是"号码还是不是你的"这个问题需要回答的时候。
  3. 它的材料必须先进事实表、统一口径、标好来源，才谈得上结论。

把这三条想清楚，你就不会在等待调取结果的几周里空转，也不会把一条基站记录写成归因结论。
