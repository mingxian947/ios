Mach IPC 与 XPC 接口审计：iOS 沙箱逃逸的攻击面测绘方法

编制日期：2026-10-22 数据来源：Apple Platform Security 文档、XNU 开源子系统与 Mach IPC 规范、Google Project Zero、Citizen Lab 关于 Pegasus/三叉戟（Trident）的公开分析、P0 关于 BlastDoor 与 WebKit 逃逸的议题、CVE 情报库 性质：防御性安全研究分析（Defensive Security Research），不提供可利用代码

1. 执行摘要

沙箱逃逸（sandbox escape）是 iOS 利用链里最"依赖工程细节"的一环，而它的攻击面几乎全部落在进程间通信上：一个受限进程能触达谁、以什么参数触达、对面怎么解析，这三件事决定了逃逸是"理论可行"还是"实际可用"。

本文不谈具体漏洞，只谈怎么把这块攻击面测绘出来——因为对防御方来说，测绘方法本身就是最有价值的产出：它给出可审计的清单、可优先排序的补丁队列，以及可回归的检测基线。

四条结论：

  1. iOS 的进程可达性由两份约束叠加决定：沙箱 profile（能不能发出这条消息）与对端服务的 entitlement 检查（收到后肯不肯做）。审计必须同时看两侧，只看其一都会系统性误判。
  2. Mach port / bootstrap 命名服务、XPC endpoint、系统代理（service proxy）与内核设备节点是四类主要跳板；历史上被反复利用的集中在处理外部不可信数据的守护进程（媒体解析、渲染/图形、通知与安装相关服务）。
  3. BlastDoor 这类"把解析移到强沙箱进程"的设计改变了攻击面形状：它把 WebKit→系统服务的直接可达变为"必须再逃逸一层"，但没有消除接口本身——接口审计的重点因此从"能不能碰到"转成"碰到之后对面解析什么"。
  4. 逃逸原语与代码执行原语的成本曲线不同：逃逸通常需要类型混淆/越界写 + 端口能力获取两步，而端口本身是"能力（capability）"，一旦泄漏即可跨沙箱调用——这是 Mach 端口在公开分析里出现频率远高于其他内核对象的原因。

2. 通信路径的分层与判定者

受限进程（App / WebContent / 媒体扩展 / NSE）
   │  ① 沙箱 profile：允许 mach-lookup？允许 connect 到哪个服务名？
   ▼
命名与传输层
   ├─ bootstrap / launchd：按名字查 Mach port（mach-lookup）
   ├─ xpc_connection / NSXPCInterface：面向服务的会话
   ├─ 系统代理（system service proxies）：跨域特权代理
   └─ IOService / IOSurface / IOGPU：内核态驱动入口（与 #44 图形面重合）
   │  ② 对端校验：调用者 pid/uid、entitlements、会话上下文
   ▼
服务端语义
      ③ 参数解析：反序列化、路径拼接、命令分发、外部数据解析
层判定者攻击者目标审计问法
①内核沙箱（Seatbelt）找到 profile 允许但语义超出预期的服务名"这个受限进程被授予了哪些 mach-lookup 项？"
②服务自身 + entitlement借用合法调用者身份，或替换调用上下文"对面是否校验调用者身份？校验的是什么？"
③服务代码在解析路径上触发内存安全问题"这条接口是否解析来自外部的不可信字节？"

结构性判断：①是"可达性"，③是"可利用性"。②是双方都容易做弱的一环——因为历史上很多内部接口按"能调用我的都是本机合法进程"假设设计。Coruna/DarkSword 这类链条之所以把大量工程放在 ②③ 而不是"发明新接口"，正是这个原因（与 #49 的原语升阶梯一致）。

3. 四类跳板的威胁画像

跳板特征典型风险现实出现频率与已有篇目
A. Mach port（bootstrap 命名服务）能力语义：拿到端口即获得调用权端口传递/继承导致跨沙箱调用；服务端无鉴权最高（公开逃逸分析的主线）本文、#52
B. XPC 会话 / NSXPCInterface类型化消息、解码发生在服务端解码器内存安全、隐式信任调用方、reply 回调反向调用高#65（NSE 与 XPC 回调）、#44
C. 系统代理 / 特权服务代受限进程执行高权操作参数注入、路径穿越、把代理当"特权手脚"中—高#52、#66
D. IO 服务 / 内核驱动入口进入内核态代码路径越界写、use-after-free，直接触及内核对象中（成本高但收益直达 #41）#41、#44、#51

为什么"端口"是核心：Mach 端口不是地址而是能力——它不可伪造、可传递、持有即可调用。沙箱能做的是限制"能否查询/接收"，一旦通过合法路径（例如把一个端口的 send right 随 XPC 消息送进受限进程），后续调用就不再需要突破沙箱。这使得"端口泄漏"类问题的严重性高于同等条件下的"符号可调用"。

4. 审计流程：从可达清单到补丁队列

以下流程是防御方可直接落地的测绘方法，不涉及任何构造利用：

步骤动作产出关键点
1提取目标受限进程的实际 profile（系统内生效版本，而非文档版本）可达服务名集合系统 profile 会随版本合并/继承，以实际生效为准
2枚举这些服务名的宿主进程与所属域（用户态守护/系统代理/IO 服务）跳板分类表（A–D）归属决定后续分析责任方
3对每个宿主判定 ②：是否有调用者身份校验（pid/uid/audit token/entitlement）校验覆盖率"无校验"直接进优先队列，无需漏洞即可标为高危
4对每个接口判定 ③：消息字段里是否存在外部不可信字节（下载的媒体、消息附件、网页可控数据）解析面清单与 #44/#65 的"不可信输入解析"重合项优先
5结合历史 CVE 与补丁节奏，为高 ② 弱 + 强 ③ 的接口打风险分排序后的补丁/加固队列风险分 = 可达性 × 解析不可信度 × 无校验
6固化基线：把 profile、服务归属、校验覆盖写入可 diff 的清单，随版本回归版本间攻击面变化报告新版本"多出来的可达项"是回归重点（#61 补丁工程）

优先级公式（本文最实用的部分）：

逃逸风险 ≈ 可达性(①通过 profile) × 无身份校验(②) × 解析不可信输入(③) × 历史活跃(同族 CVE)

三项中任意为零，风险骤降；因此"最小授权裁剪 profile"（把可达性从 1 变 0）是性价比最高的加固，远高于逐条修 ③ 的解析器。

5. 检测与可观测性

观测点能看见什么现实限制对应手法
沙箱违规拒绝日志（deny）攻击探测过程：尝试 lookup 未授权服务攻击者只走已授权项则不产生 deny；日志在设备侧、留存有限探测阶段的强信号
服务侧异常调用（合法调用者 + 异常参数/时序）② 弱接口的滥用需要服务自己有指标，多数内部服务没有主要缺口
崩溃归因（宿主守护进程崩溃）③ 解析器被触发成熟载荷会规避崩溃（#63 HUNT-04 反向）群体基线仍有效
端口传递异常（受限进程持有特权能力）①+② 组合滥用设备侧几乎无对外可见通道依赖 MDM/备份工件，与 #67 清单同构
系统调用/内核事件逃逸后的行为国家级载荷走文件less 驻留，工件少（#55）事后取证（#62）

结论：IPC 层是 iOS 可观测性最差的一层。攻击面测绘（第 4 节）比运行时检测更现实，因为前者不依赖设备上报能力。这一判断与 #47 的结论同源：越靠近系统内部机制，越只能靠设计与架构防御，而不是靠告警。

6. 加固：三层各自的抓手

层抓手效果代价
① 可达性profile 最小授权；把解析移入强沙箱域（BlastDoor 式架构）直接抹掉整类跳板功能取舍与性能；不影响已被授权项
② 校验服务端强制 audit token + entitlement 校验；拒绝未识别调用者使"借用合法通道"失效兼容性回归风险最高（内部调用方众多）
③ 解析内存安全语言重写解析器；长度/类型严格校验；不可信输入独立进程降低漏洞产生率长期工程，见 #61
跨层语言级迁移（内核子系统内存安全化）+ 并行信任域（SPTM/TXM，#64）抬高逃逸→提权之间的门槛无法覆盖用户态解析缺陷

BlastDoor 类设计的审计含义：强沙箱不是"攻击面归零"，而是"必须多逃逸一次"。因此接口审计在隔离进程上仍然要做——且因为隔离进程本身被设计为处理不可信输入，它的 ③ 权重最高，是测绘工作的第一优先对象。

7. 时间线矛盾模板（IPC 逃逸形态）

延续 #65、#66 的"时间线矛盾"方法，IPC 逃逸的可观测形态：

若 某受限进程出现以下组合
   - 持有不属于其职责的 Mach 能力（特权端口 / 跨域服务句柄）
   - 触发了一次不属于其用户操作序列的服务端调用（无前台、无授权、无通知）
   - 随后出现数据读取或外发（#42、#47）
→ 逃逸已发生的强指示；
  进入 #48 应急时序，#62 做证据保全，
  并按第 4 节流程反查"该可达性是哪条 profile 允许的"

其中"能力持有"是唯一在单次备份内可判定的项，因此取证时应把描述文件/能力清单（#67）与进程级安装数据库一并提取，避免只提取日志（#62 双工具交叉提取）。

9. 总结

#结论
1沙箱逃逸攻击面由"可达性 × 无校验 × 解析不可信输入 × 历史活跃"四项乘积决定
2Mach 端口是能力语义：持有即可调用，因此端口泄漏严重性高于同条件符号可调用
3跳板分四类（Mach port / XPC 会话 / 系统代理 / IO 内核入口），公开分析主线集中在前两类
4只审 profile 或只审解析器都会系统性误判；②（调用者身份校验）是最常被做弱的一环
5BlastDoor 类隔离不消除接口，只增加一层逃逸成本；隔离进程的解析面权重最高
6IPC 层运行时可观测性最差，防御重心应放在测绘与最小授权，而非告警
7裁剪 profile 的性价比高于逐条修解析器；测绘结果应作为可 diff 的版本基线长期维护

一句话总结：Coruna 与 DarkSword 这类链条在沙箱逃逸阶段并不依赖神秘机制，它依赖的是一张"受限进程实际能碰到谁、对面解析什么"的清单——防御方真正该做的，是用同一套方法把这张清单先自己画出来、按可达性裁剪、并把校验补齐，让攻击者的工程成本从"挑一个弱接口"回到"必须再发明一次逃逸"。
