iOS IOKit 内核驱动攻击面：驱动族缺陷测绘与可达性审计方法

编制日期：2026-10-28 数据来源：Apple Platform Security 文档、Apple Security Releases（SWU 公告条目）、XNU/IOKit 公开源码（Apple Open Source）、Google Project Zero 与 Safeguard 系列、Citizen Lab 与 Amnesty 的 Pegasus 取证披露、iOS 分析组件（Ian Beer、Brandon Azlad 等）公开研究笔记、CVE 情报库、本系列前 78 篇分析 性质：防御性安全研究分析（Defensive Security Research），不提供可利用代码

1. 执行摘要

本系列把 iOS 内核提权拆过多次（#6、#33、#41、#51），把沙箱逃逸拆过多次（#5、#29、#40、#43、#52、#68），但没有单独给 IOKit 画过一张图。这一篇补上这块——因为它是 iOS 上"内核代码里最大的一片非 Apple 手写区域"，也是提权链与逃逸链最常借道的那一层。

六条结论：

  1. IOKit 不是"一个组件"，而是几百个内核扩展（driver personality）的集合，每个都通过 IOServiceOpen 向用户态暴露"外部方法（external method）"接口。接口数量 = 攻击面数量，这决定了它的缺陷产出率长期高于 XNU 核心子系统。
  2. 与 #68 的 Mach IPC 面不同：Mach 端口是内核自身的服务；IOKit 是驱动的服务，其参数由内核态代码解析标量/结构体/欧可描述符（OOL）。历史上 iOS 提权链里"最容易找到第一块多米诺"的位置就在这里。
  3. 图形栈（IOGPU / AGX / IOAccelerator）是近五年增长最快的一块：本系列 #58 从"图形 API 面"角度分析过它，本篇从"驱动接口与内核内存边界"角度补另一侧——同一块栈，两条正交的攻击面。
  4. 可达性由沙箱 profile 的设备类授权决定，不是由代码难度决定。因此"谁能在未逃逸状态下打开哪些驱动"是防御方唯一可操作的收敛点，也是本篇 §5 给出的审计方法。
  5. 已确认被利用过的 IOKit 缺陷存在，但不多。公开可确认的例如 Apple 在安全公告中标注"可能已在攻击中被利用"的 CVE-2023-41990（IOHIDFamily） 与 CVE-2023-42917（IOGPU）；CVE-2021-30869（IOUserTexts） 属于同一形态的早期例子。这三条都在 §6 里按"接口形态"而非"新闻价值"归类。
  6. 检测侧的好消息与坏消息：驱动崩溃是强工件（诊断日志会带 personality 名与调用栈），但驱动被合法打开不是工件——IOServiceOpen 对授权进程完全正常，因此不能把它本身当告警，只能做基线偏移分析（§8）。

2. IOKit 在 iOS 栈里的位置

用户态                        内核态
──────────────────────────────────────────────────────────
App（受限）  ── sandbox profile 判定 ──┐
              │                        │
   IOKit.framework（用户态客户端）      │
              │  IOServiceGetMatchingService / IOServiceOpen
              ▼                        ▼
      用户态驱动客户端（IOUserClient 代理）
              │  externalMethod(selector, scalar / struct / OOL)
              ▼
   ┌───────────────────────────────┐        ┌────────────────────┐
   │ XNU kernel                    │◄──────►│ IOKit driver kext  │
   │ mach、vm、vfs、proc、kauth    │        │  数百个 personality │
   └───────────────────────────────┘        └────────────────────┘
              ▲                        ▲
        SPTM/CSM、PPL/RTX（内核隔离域，#27、#64）
概念是什么为什么与漏洞有关
IORegistry / personality设备与服务树，声明每个驱动的用户客户端类决定"存在哪些可打开的服务"，是可达性清单的来源
IOServiceOpen建立与用户客户端类的连接连接建立时驱动可为你分配内核内存与上下文——生命周期起点
External method用户可调用的编号方法，带参数描述符参数解析是"外部输入直接进内核"的那道门，OOB/整数类缺陷高发（对齐 #81 的类轴）
参数类型（scalar / struct / OOL）标量、结构体、可变长（out-of-line）内存OOL 最危险：内核拿到调用者控制的长度与页描述
Connection reference / 对象句柄内核对象引用计数UAF 的经典来源：关闭连接与异步工作项竞争
IOMapMemory / IOMobileFramebuffer 类用户内存映射给驱动跨越"用户/内核"边界的可见性，与 GPU/显示栈强相关（#58）

关键结构事实：外部方法的授权写在驱动的 sExternalMethodData 表里（方法号 + 权限位），而是否允许你打开这个驱动写在调用方沙箱 profile 的 device-type 授权里。两者是两道独立门：逃逸成功才有第一道，参数校验决定第二道有没有实际作用。

3. 为什么 IOKit 是 iOS 缺陷的长期供给方

因素机制后果
代码来源多样除 Apple 自研外，大量为 SoC/外设供应商驱动移植；风格与安全要求不一参数校验、长度检查、错误路径的一致性难以保证
数百个 personality每个设备类都可能带一个用户客户端类接口数量巨大，每个接口都需要独立审计
生命周期复杂连接、内存映射、异步工作循环、power state 转换UAF/竞态的温床（对齐 #81 的 §3.2、§3.7）
必须处理外部内存图形、显示、音频、输入、传感器都需要跨越边界，"用户可控长度/地址"不可避免
长期不变量老驱动接口长期保持兼容（不删不改）老代码持续暴露在新攻击者面前，历史缺陷可能仍可达
可组合性一个"任意读"往往已在驱动里给出攻击者可以只用小原语拼出泄露，无需完整 RCE
GPU 栈持续扩张Metal 与图形 API 每代新增接口；虚拟化为多客户端IOGPU/AGX 面随 iOS 版本净增长（#58）

结论：把 IOKit 当"第三方驱动问题"是错的；它是内核里由 Apple 分发但由生态供给的那部分，治理方式只能是接口收敛与可达性最小化，而不是"多审几遍"。

4. 驱动族与缺陷倾向（本系列视角的测绘表）

按"设备族"分组，各族的历史缺陷倾向与可达性特征。"暴露倾向"是研究结论，不是清单；具体某台设备上某驱动是否可达，必须用 §5 的方法实测。

驱动族代表类（personality/kind）为什么可达面广历史缺陷倾向（对齐 #81 类轴）链上价值
输入与 HIDIOHIDFamily 一族（键盘、触控、传感器、电源键类）输入路径必须被多数进程访问；且常提供回调/事件投递OOB、竞态、引用生命周期；CVE-2023-41990 属此族并被标为可能被利用提权 + 采集双重价值（可拿到按键/事件语义）
图形与加速IOGPU / AGXFamily / IOAcceleratorFamily / IOGPUClient任何 UI 进程都需要；Metal 客户端接口多、参数复杂结构体/句柄校验、OOL、类型混淆、UAF；CVE-2023-42917 属此族并被标为可能被利用逃逸（从 WebKit/GPU 客户端）与提权；与 #43 的 ANGLE/WebGPU 路径重合
显示与帧缓冲IOMobileFramebuffer / IOBacklightDisplay截图、合成、显示模式路径都在此尺寸计算（整数→OOB）、跨进程内存映射信息泄露与截屏采集能力
音频与视频AppleHDA / IOAudioFamily / 多媒体处理族采集与播放权限普遍；与后台状态相关OOL 参数、缓冲区长度、生命周期麦克风/摄像头采集能力（对应 #66 的通路问题）
网络与无线协处理器接口蜂窝/Wi-Fi/蓝牙的用户态胶水类驱动协议数据由外部可控解析类缺陷；且常与协处理器信任域交界（#72）与基带面构成"跨域接口"，风险等级最高的一类
存储与文件系统辅助ANE/存储与加密辅助类文件路径、加密上下文交互状态假设、竞态与备份/密钥通路相接（#74、#53）
文本与输入辅助IOUserTexts、剪贴板相关服务剪贴板与文本替换涉及多进程共享状态生命周期与共享状态；CVE-2021-30869 属此族提权 + 剪贴板窃取（#66 §5 的工件来源）
电源与热管理IOPowerSources / PMFamily状态查询接口简单，但常在内核早期/唤醒路径状态假设、TOCTOU唤醒与持久性配合（#65）
安全协处理器接口SEP/ANE 相关用户客户端跨信任域调用逻辑/授权误用类为主（不吃内存安全缓解，#81 §3.8）直接指向密钥与生物特征边界（#53、#84）

读表方式：一个漏洞的"链上价值"由它能给什么原语决定，而不是由它属于哪个驱动决定。图形族之所以被反复研究，是因为它能同时给出泄露与受限写；SEP 接口族之所以危险，是因为它可能压根不需要原语。

5. 可达性审计方法（防御方可直接执行，无可利用细节）

这是本篇对防御方最有价值的部分："我们的设备上，未提权代码能打开哪些驱动接口"是一个可测量、可收敛的指标。

5.1 清单来源（三条通路）

通路能拿到什么局限
iOS 系统符号/固件分析（Apple Open Source 中 IOKit 家族源码 + 设备上的 kext 资源）驱动类名、外部方法表结构需要与具体 iOS 版本对齐，方法号会随版本变动
沙箱 profile（/System/Library/Sandbox/Profiles/*.sb）**哪些 device-* 类型被允许**，即真正的可达性来源profile 是编译/展开形式，需要按目标进程读
崩溃与诊断日志（Analytics Data）哪些驱动实际被打开、哪些路径崩溃过只能给出"发生过"，不给出"可发生的全部"

5.2 五步审计法

① 选宿主进程 → ② 提取其沙箱 profile 的 device 授权集 → ③ 用 IORegistry 枚举匹配服务
      → ④ 对每个服务列出其用户客户端的外部方法表（方法号/参数类型/权限位）
      → ⑤ 标注"接受外部可控长度或跨边界内存"的方法，作为优先修补/收敛对象
步输出物判定标准
①目标进程清单（尤其是处理外部不可信输入的：浏览器、消息、媒体、扩展宿主）与 #66 §3 的"已授权 + 处理外部输入"筛选条件同源
②允许的设备类型集合集合越小越好；出现 device-* 泛授权要单独记录
③可匹配服务名清单与 profile 交集才是真实可达面
④外部方法表：数量、参数类型分布、是否有 IOStructScalar/OOL参数为 OOL 或可控结构体 → 进入优先清单
⑤一份"接口 × 版本 × 补丁状态"矩阵用于 §9 的暴露窗口跟踪（与 #75 的度量方法一致）

审计纪律：

  • 不要在真机上对生产设备做接口探测。用同版本的隔离设备/测试镜像，按组织流程走（与 #62 的证据保全原则一致）。
  • 输出物是配置与可达性事实，不是利用可行性结论。"某接口可达"不等于"某接口有漏洞"。
  • 把"能否用非 IOKit 通路达成同一功能"也记录下来：很多驱动面是历史兼容产物，可被上游策略关掉。

5.3 收敛手段（防御侧唯一有杠杆的动作）

手段做法效果依据
进程能力最小化不需要的 device-* 类型不要出现在 profile；扩展宿主、内容解析进程应使用受限 profile直接把 ②③ 的交集缩小#52（BlastDoor 的隔离语义）、#68
Web 面收缩锁定模式会显著减少可达的图形/媒体触发面（本系列 #34 的结论）对高危角色等效于 ②③ 收缩#34、#57、#58
版本对齐已知被修补的驱动族（HID/GPU/UserTexts）优先保证全员升级消除"老代码仍可达"这一风险项§3 表格最后一行、#61
采购/SDK 约束企业内自研扩展、驱动类工具（配置描述文件携带的）要登记（#67）避免引入额外可达路径#67

6. 代表缺陷按形态归类（而非按 CVE 罗列）

形态说明公开确认的例子（以 Apple 安全公告标注为准）链上作用
用户客户端生命周期处理错误（UAF 类）连接关闭与异步工作竞争IOHIDFamily 一类：CVE-2023-41990（Apple 标注该问题可能在攻击中被主动利用）提权、跨沙箱边界破坏
加速图形接口的内核侧处理（OOB/UAF 类）GPU 客户端句柄与资源生命周期IOGPU：CVE-2023-42917（同样被标注为可能已在攻击中被利用）逃逸 + 提权；与 #43 的 WebGPU/ANGLE 面在语义上相邻
文本/剪贴板相关服务的内存破坏跨进程共享状态下的对象使用IOUserTexts：CVE-2021-30869（Apple 公告表明该问题报告于公开利用语境）提权 + 内容采集侧信道
长度/尺寸计算（整数 → OOB 后果）驱动解析外部结构体的常见成因散见于各代公告，难以在通报里区分"成因"与"后果"（#81 §3.4 的统计失真问题）任意读写的第一环
授权/参数校验缺失（逻辑类）外部方法权限位配错或身份校验不足通报里常写作"任何进程都可…"/"攻击者可获得 root"不吃任何内存安全缓解，只能靠接口收敛

统计口径提醒：Apple 公告的条目粒度是"CVE × 受影响组件 × iOS 版本"，不含缺陷类别。因此任何"iOS 漏洞类型分布"统计都必须自己做归类映射——本篇 §4 的族分类 + #81 的类分类可以组成一个二维标签体系（族 × 类），建议直接沿用它做追踪。

7. Apple 在这一层做了什么缓解

缓解打的是哪一类现状判断
内核隔离与执行域收紧（SPTM/CSM、可执行/可写页分离、PPL→后继机制）内核侧控制流劫持、页表破坏使"写原语 → 稳定提权"成本显著上升（#27、#64、#41）
用户客户端方法权限位与连接授权逻辑/授权误用类只能减少"不该可达"，无法修复"可达但做错"
分配器与 zone 隔离加固、释放后清零UAF 回填可行性提高工程门槛，不消除缺陷本身（#81 §3.2）
图形栈的虚拟化和 IOGPU 边界收敛GPU 族的跨边界风险与 #58 的观察一致：面在扩大，同时边界也在收紧，净效果随版本摆动
沙箱 profile 精细化、BlastDoor 型独立解析（#52）解析类缺陷的可达性对 Web/消息投递面最有效，因为它删掉入口而不是修 bug
OOL/参数校验 API 规范化与内核内存拷贝检查OOB/整数组件间落地不均；供应商代码是最不均的部分
快速安全响应（RSR）覆盖部分内核/驱动缩短暴露窗口是本层最实用的运营改进（#61、#75）

8. 检测与狩猎：什么可观测、什么不可

信号可观测性处置建议
带驱动 personality 名的内核 panic/IOKit 崩溃报告强（Analytics Data 里可见）做群体基线，突增/新出现的驱动名作为异常（#63 HUNT-04 思路）
未授权 IOServiceOpen 失败（sandbox deny 类日志）中（在诊断日志/设备端 syslog 有痕迹，若被采集）组织侧应明确"deny 事件"是否需要上报（#76 的可见性边界）
成功打开"该进程从不开"的驱动设备侧几乎不可见，需网络/MDM 之外的取证手段只能作为提取后的时序分析工件（#62、#70 方法）
提权后行为（读 SEP 接口、跨进程内存）不可见（架构级，#59、#66）放弃设备侧检测，转向出口与人为信号（#80 §5）
版本 + 补丁状态强（MDM 可见）用它替代"有没有被攻击"的判断；把 §5.3 与 #75 指标合流

表述纪律：未看到驱动异常崩溃 ≠ 没有利用；看到崩溃 ≠ 利用成功。这两句话适用于本层所有检测。

11. 总结

#结论
1IOKit 是"内核里的生态代码"：几百个 personality 各自暴露外部方法，接口数量本身就是攻击面
2两道门相互独立——沙箱 profile 决定能否打开驱动，参数校验决定打开后能做什么；防御只在第一道有杠杆
3缺陷产出率长期偏高的根因是供应商代码风格不一致 + 生命周期复杂 + 老接口长期不删
4已确认被利用过的 IOKit 缺陷存在（IOHIDFamily/IOGPU 等），其链上价值由"能给什么原语"决定，而不是由所属驱动决定
5可达性审计是可执行、可回归的：宿主进程 → profile 授权 → IORegistry 匹配 → 外部方法表 → 优先清单
6检测结果必须按"族 × 类"二维归类，Apple 公告不含缺陷类别，直接引用会造成类型统计失真
7崩溃是这一层最好的工件，但只覆盖部分缺陷；逻辑/授权类与提权后行为不可观测，检测重心仍在入口与出口

一句话总结：iOS 内核里的 IOKit 就像一栋楼的几百个后门——Apple 修的是每一扇门的锁，而防御方真正能做的，是让住在不同房间里的人（沙箱 profile）手里根本拿不到那些门的钥匙，并且每年版本更新时重新数一遍还剩几扇门能打开。
