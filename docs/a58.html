iOS 图形栈攻击面全景：ANGLE、WebGPU、Metal 与 IOGPU 缺陷史

编制日期：2026-10-18 数据来源：Apple 安全公告、Khronos/WebGPU 规范、Chromium ANGLE 项目、Google Project Zero、CVE 情报库 性质：防御性安全研究分析（Defensive Security Research），不提供可利用代码

1. 执行摘要

DarkSword 与 Coruna 的部分链条把沙箱逃逸的主战场放在图形栈，这不是巧合，而是当前 iOS 攻击面密度最高的区域。

图形栈之所以特殊，在于它同时满足三个通常互相矛盾的条件：

  • 必须对渲染进程开放（否则无法显示网页）——沙箱无法关闭
  • 代码量巨大且持续新增（WebGPU 是新 API、ANGLE 是移植层）——审计密度低
  • C/C++ 实现 + 复杂跨层语义——内存缺陷概率高

本文完整梳理 iOS 图形栈的分层结构、各层缺陷类型、历史 CVE 分布，并给出"为什么攻击者选中这里"的量化解释与防御优先级建议。

2. iOS 图形栈分层结构

2.1 从网页到像素的完整路径

┌─────────────────────────────────────────────────────┐
│ Web 层    WebGL / WebGPU JavaScript API              │  ← 攻击者直接可控输入
├─────────────────────────────────────────────────────┤
│ 转译层    ANGLE（GL → Metal 转译）                   │  ← C++，用户态
├─────────────────────────────────────────────────────┤
│ 框架层    Metal / IOSurface / CA (CoreAnimation)      │  ← 用户态框架
├─────────────────────────────────────────────────────┤
│ 服务层    GPU 进程 / WindowServer                     │  ← 独立进程，较高权限
├─────────────────────────────────────────────────────┤
│ 内核层    AGX / IOGPUDevice 等 IOKit 驱动              │  ← 内核态，高权限
├─────────────────────────────────────────────────────┤
│ 硬件层    Apple GPU (Imagination PowerVR 授权衍生)     │
└─────────────────────────────────────────────────────┘

2.2 为什么跨层是核心问题

每一层的输入校验都假设上一层已经做过校验。

JS 层        : 假设 WebKit 绑定层会校验参数
WebKit 绑定层 : 假设 ANGLE 能处理任意合法 GL 调用
ANGLE        : 假设上游传入的 buffer 尺寸正确
GPU 服务      : 假设提交上来的命令流来自合法客户端
IOKit 驱动    : 假设服务层已完成参数范围检查
        ↓
  实际：只有最外层面对攻击者，
       但每一层都可能被直接触达（沙箱允许打开驱动接口）

这是图形栈缺陷的系统性成因，不是某个团队的代码质量问题。

3. 各层的攻击面细节

3.1 Web 层：WebGL 与 WebGPU

API攻击面特征
WebGL（GL ES 2.0 子集）历史久、审计相对充分；但仍需 ANGLE 转译
WebGPU新 API，语义复杂（pipeline、bind group、buffer、texture）；参数对象可深度嵌套

WebGPU 特别危险的三个理由：

理由说明
对象图复杂设备/适配器/管线/绑定组/缓冲区之间存在隐式引用关系，生命周期管理易错
直接暴露缓冲区句柄GPUBuffer 与共享内存/IOSurface 的映射路径让攻击者可控大块内存
实现新WebKit 的 WebGPU 实现相对年轻，边界情况覆盖不足

3.2 ANGLE 转译层

ANGLE 把 GL 语义翻译为 Metal 语义。风险点：

风险类型说明
语义不完全等价GL 与 Metal 在尺寸/对齐/格式约束上不同，转译时校验可能丢失
缓冲区尺寸计算width * height * bytesPerPixel 类整数溢出是经典缺陷
着色器编译GLSL → MSL 转译器本身是复杂解析器（解析器 = 攻击面）
C++ 实现无内存安全保证
上游同步移植 Chromium 代码，安全审查节奏与原项目不完全同步

3.3 框架层：Metal / IOSurface

组件攻击面
IOSurface跨进程共享内存的对象，句柄可在进程间传递；引用计数与映射管理易错
Metal 命令队列命令缓冲构造、资源绑定校验
CoreAnimation图层树复杂，跨进程合成

IOSurface 尤其值得关注：它是"跨进程共享内存 + 引用计数 + 内核对象"三者叠加，历史上是多个平台逃逸的经典面。

3.4 服务层与内核层

组件权限攻击价值
GPU 渲染服务进程高于 WebContent逃逸落点
WindowServer系统级，控制屏幕合成高价值（但历史保护严格）
IOGPUDevice / AGX 内核驱动内核态最高——直接通向提权

内核驱动侧的典型缺陷类型：

缺陷说明
用户传入 buffer 的长度/索引校验缺失越界读写
copyin/copyout 尺寸计算错误内核越界
命令流解析未处理边界情况内存破坏
资源句柄（ioctl 参数）可引用其他进程对象跨进程访问 → 逃逸
引用计数不平衡UAF
结构体未初始化即返回用户态内核信息泄露（kslide）

这解释了 DarkSword 的两阶段逃逸设计：先用 ANGLE 层缺陷建立可控写入，再通过驱动接口缺陷同时获得内核地址泄露与内核读写——一次攻击面利用解决两个环节（详见 #43、#52）。

4. 为什么沙箱必须放行图形栈

4.1 不可关闭的依赖

需求后果
页面合成需要 WindowServer 通信Mach 端口必须在 profile 中
WebGL/WebGPU 需要 GPU 命令提交IOKit GPU 服务类必须可打开
纹理/帧缓冲需要零拷贝共享IOSurface 映射必须允许
视频解码需要媒体硬件相关接口必须可达

沙箱设计者面对的是硬约束：不能为了安全砍掉渲染功能。因此只能选择"放行通道 + 校验参数"——而校验逻辑本身成为新攻击面。

4.2 与其他面的对比

面是否可关闭攻击者偏好度
相机/麦克风✅ 可（需授权）低
网络（WebContent 直连）✅ 已通过服务代理收紧低
文件系统✅ 严格限制低
Mach IPC 传统面⚠️ 部分收紧，历史漏洞多中（已下降）
图形栈❌ 不可关闭高（当前主战场）

核心判断：图形栈是当前唯一"沙箱必须完全放行、且无法在不损失核心功能前提下收紧"的高权限通道。

5. 缺陷史与 CVE 分布特征

5.1 时间线趋势（概念性）

2015–2018  IOKit 传统驱动（HID、音频、显示）为主要逃逸面
    ↓      Apple 大量收紧 IOKit 用户客户端接口
2018–2021  GPU 相关（AGXFamily / IOGPU）开始出现在公开链条中
    ↓      WebKit 图形绑定层暴露扩大
2021–2023  ANGLE / WebGL 层缺陷被研究关注，WebGPU 实现上线
    ↓
2024–2025  **图形栈成为在野逃逸首选**（Coruna 部分链、DarkSword 主链）

5.2 描述措辞识别（防御实用）

Apple 公告中以下措辞通常指向图形栈攻击面：

措辞含义
"Processing maliciously crafted web content may lead to ... memory corruption"WebKit/图形绑定层
"A memory processing issue ... WebGL / WebGPU"转译层
"Validation issues in IOGPU / AGXFamily / AppleParavirtGPU"内核 GPU 驱动——最高价值
"Improper access control in AppleGraphicsControl"图形控制路径
"The content of an IOSurface may be disclosed"共享内存泄露

5.3 组件价值分级（攻击者视角）

组件沙箱可达实现复杂度审计密度缺陷收益综合攻击价值
WebKit DOM/渲染✅高中高RCE高
JavaScriptCore✅极高中高RCE + 原语极高
ANGLE 转译层✅高低逃逸跳板极高
WebGPU 绑定✅高低逃逸跳板极高
IOGPU/AGX 驱动⚠️ 需接口可达高低内核读写 + 泄露极高
IOSurface✅中中跨进程访问高
WindowServer✅高高（长期重点）系统级中（防御成熟）
音频驱动⚠️ 收紧中高逃逸已下降

6. 缓解现状与不足

6.1 已部署的缓解

措施效果
驱动接口参数校验加强削弱直接越界
GPU 进程与 WebContent 分离（多进程架构）单点缺陷不直接等于高权限
IOSurface 引用管理改进减少跨进程误引用
Lockdown Mode 禁用 WebGPU/WebGL直接移除整个面
PAC 在驱动返回路径的覆盖削弱控制流劫持

6.2 结构性不足（攻击者仍占优）

不足说明
代码体量增长快于审计图形栈代码量巨大，模糊测试覆盖不均衡
跨层信任假设无形式化定义每层"假设上游已校验"，缺少统一契约
移植代码的审查时延ANGLE 来自上游，安全修复同步存在时间差
规范复杂度WebGPU 规范本身状态机复杂，实现分歧难以完全避免
不可关闭无法用"默认禁用"换取安全（除非进入锁定模式）

7. 防御建议

7.1 用户/组织侧

措施效果优先级
高危人群启用锁定模式一次性移除 WebGPU/WebGL 面极高
优先修补图形栈 CVE该面是当前逃逸主战场高
不要把图形栈 CVE 当"仅影响图形"它是提权入口高
及时升级逃逸链断裂高
对 Web3D 站点保持警觉异常 GPU 调用最容易出现在真实 3D 站点中中

7.2 检测侧（图形栈利用的高价值信号）

信号含义置信度
IOGPU/AGX 驱动崩溃或异常返回驱动接口利用尝试高
WebContent 创建大量 GPU buffer/texture 后迅速销毁堆塑形 / 接口试探高
WebContent 打开预期外的 IOKit 服务类逃逸准备高
简单页面产生极高 GPU 命令提交速率自动化利用特征中高
WindowServer/GPU 服务出现异常进程生命周期逃逸执行高
内核日志含 GPU 相关符号的异常提权尝试极高

7.3 如果你是自研浏览器/WebView 产品

建议说明
默认关闭 WebGPU除非有明确需求——该面收益小风险大
WebGL 输入做二次校验不要信任上游绑定层的校验
在图形调用路径引入类型/范围 fuzzing该面模糊测试覆盖常不足
明确跨层契约并加断言把"假设上层已校验"变成可验证的检查
跟进 ANGLE/上游安全修复节奏缩短移植时延

8. 趋势预测

判断理由置信度
图形栈在未来 2–3 年仍是逃逸主战场代码增长快、不可关闭、审计密度未跟上高
WebGPU 相关 CVE 将持续上升API 新、用户少、审计弱高
内核 GPU 驱动漏洞价值继续高于用户态一次利用可同时提供逃逸与提权高
Apple 会加强进程分离与驱动校验已有趋势中高
AI 相关图形/计算负载扩大该面端侧推理使用 GPU 计算路径 → 新接口暴露中（新兴）

值得提前关注的新方向：端侧 AI 推理大量使用 GPU 计算（Metal compute / 神经引擎）。这会引入新的、审计密度更低的 GPU 计算接口，符合"功能必需 + 实现新 + 审计少"三判据。历史上每个这样的窗口都会带来一段高缺陷密度期。

9. 总结

#结论
1图形栈是当前 iOS 唯一"沙箱必须完全放行 + 代码复杂 + 审计不足 + 跨权限边界"四者叠加的面
2跨层信任假设不一致是结构性成因——每层都假设上层已校验，而攻击者可直接触达任一层
3DarkSword 选择 ANGLE→IOGPU 路径正是对这一结构的精确利用，一次利用同时解决逃逸与泄露
4内核 GPU 驱动（IOGPU/AGX）的 CVE 应按"提权入口"而非"图形 bug"评级
5锁定模式禁用 WebGPU/WebGL 是移除该面的唯一彻底手段，性价比对高危人群极高
6该面的驱动异常是最高置信度的运行时检测信号——比文件扫描有效得多
7端侧 AI 计算会引入新的低审计密度 GPU 接口，是下一个需预警的窗口

一句话总结：

沙箱能关闭所有"可以不给你"的通道，但关不掉"不给你就没有网页"的通道。 图形栈就是这个必然漏洞——所以它成了攻防双方当下的主战场。
