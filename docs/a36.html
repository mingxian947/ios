iOS Trident 漏洞链技术详解

编制日期：2026-10-13 数据来源：Citizen Lab、Lookout、Google Project Zero、Apple Security Advisory、公开安全研究 性质：防御性安全研究分析（Defensive Security Research），不提供可利用代码

1. 执行摘要

Trident 是 2016 年 8 月由 Citizen Lab 和 Lookout 联合披露的首个被公开确认的 iOS 全链条商业间谍软件攻击。该攻击链由以色列 NSO Group 开发，用于其 Pegasus 间谍软件产品，针对阿联酋人权活动家 Ahmed Mansoor 的设备。

重要澄清：Trident 实际上是1-click（一键）攻击，而非 0-click（零点击）。它需要目标用户点击短信中的恶意链接。真正的 0-click 攻击是在后续代次（ImageIO、FORCEDENTRY）中才实现的。

本文深入解析 Trident 攻击链的技术细节：

  1. 攻击背景与发现过程
  2. 三漏洞串联架构：CVE-2016-4655 + CVE-2016-4656 + CVE-2016-4657
  3. 阶段一：WebKit 信息泄露（CVE-2016-4655）
  4. 阶段二：内核信息泄露（CVE-2016-4656）
  5. 阶段三：内核代码执行（CVE-2016-4657）
  6. KASLR 绕过技术
  7. 攻击链完整流程
  8. 历史意义与后续演进

核心结论：Trident 是 iOS 安全史上的里程碑事件——首次公开证实商业间谍软件可对 iOS 实施全链条攻击。其三漏洞串联模式成为后续所有 iOS 全链条攻击的原型架构。

2. 攻击背景与发现

2.1 目标与投递

目标：Ahmed Mansoor（阿联酋人权活动家）

投递方式：

2016 年 8 月，Mansoor 收到短信：

  "新的秘密在阿联酋监狱中曝光！
   点击链接查看：
   http://xxx.xxx/xxx"

Mansoor 未点击链接，而是发送给 Citizen Lab。

2.2 发现过程

Mansoor 发送短信给 Citizen Lab
        ↓
Citizen Lab 分析链接 → 发现恶意网站
        ↓
联合 Lookout 分析载荷
        ↓
确认是 iOS 全链条攻击（Pegasus）
        ↓
联合 Google Project Zero 分析漏洞
        ↓
2016 年 8 月公开披露
        ↓
Apple 当天紧急发布 iOS 9.3.5 补丁

2.3 历史意义

意义说明
首次公开确认首个被公开确认的 iOS 商业间谍软件
全链条攻击首次证实 iOS 可被全链条攻击
三漏洞串联确立了多漏洞串联的攻击模式
推动行业推动了对商业间谍软件的研究

3. Trident 三漏洞架构

3.1 攻击链总览

[阶段 0] SMS 钓鱼 → 用户点击链接 → 访问恶意网站
        ↓
[阶段 1] WebKit 信息泄露（CVE-2016-4655）
         → 泄露内核基址 → KASLR 绕过
        ↓
[阶段 2] 内核信息泄露（CVE-2016-4656）
         → 泄露内核函数指针 → 获取内核地址
        ↓
[阶段 3] 内核代码执行（CVE-2016-4657）
         → 内核漏洞利用 → root 权限
        ↓
[阶段 4] Pegasus 安装 → 数据窃取 → C2 通信

3.2 漏洞映射

CVE组件类型作用
CVE-2016-4655WebKit信息泄露KASLR 绕过（泄露内核基址）
CVE-2016-4656内核信息泄露泄露内核函数指针
CVE-2016-4657内核代码执行内核提权（root 权限）

3.3 为什么需要三个漏洞

阶段目标为什么需要
CVE-2016-4655绕过 KASLR内核地址随机化，需先知道基址
CVE-2016-4656获取内核地址需要知道具体内核函数/数据地址
CVE-2016-4657内核代码执行最终提权，获得 root 权限

逻辑：

  1. 没有 KASLR 绕过 → 不知道内核在哪里 → 无法攻击内核
  2. 没有内核信息泄露 → 不知道具体函数地址 → 无法精确利用
  3. 没有内核代码执行 → 无法获得 root → 无法安装 Pegasus

4. 阶段一：WebKit 信息泄露（CVE-2016-4655）

4.1 漏洞原理

组件：WebKit JavaScriptCore（JSC）

类型：信息泄露（Information Disclosure）

原理（简化）：

// JSC 在处理某些 JavaScript 对象时
// 未正确初始化内存
// 导致可以读取未初始化的内存内容

// 攻击者构造特制 JavaScript 代码
// 触发漏洞 → 读取内核内存
// → 泄露内核指针 → 计算内核基址

4.2 KASLR 绕过

KASLR（Kernel Address Space Layout Randomization）：

  • 内核每次启动时随机选择基址
  • 防止攻击者知道内核代码/数据的位置
  • 是内核攻击的第一道防线

绕过过程：

1. 访问恶意网页 → 执行特制 JavaScript
        ↓
2. 触发 CVE-2016-4655 → 读取未初始化内存
        ↓
3. 内存中包含内核指针（未清理）
        ↓
4. 从指针值推断内核基址
        ↓
5. KASLR 被绕过 → 知道内核在哪里

4.3 技术细节

关键：WebKit 进程的内存中可能包含：

  • 内核指针（从系统调用返回时残留）
  • 内核数据结构地址
  • 函数指针

利用：

  • 通过 JavaScript 读取这些残留指针
  • 计算内核基址（指针值 - 已知偏移 = 基址）
  • 为后续内核攻击铺路

5. 阶段二：内核信息泄露（CVE-2016-4656）

5.1 漏洞原理

组件：XNU 内核

类型：信息泄露（Information Disclosure）

原理（简化）：

内核在处理某些系统调用/IOKit 请求时
        ↓
未正确校验用户态提供的缓冲区
        ↓
攻击者可读取内核内存
        ↓
泄露内核函数指针/数据地址

5.2 获取内核地址

目标：获取特定内核函数/数据的地址，为代码执行铺路。

过程：

已知：内核基址（从 CVE-2016-4655 获得）
        ↓
利用 CVE-2016-4656 → 读取内核内存
        ↓
获取：
  - 内核函数地址（如 kernel_call 函数）
  - 内核数据地址（如 cred 结构）
  - 内核代码地址（用于 ROP）
        ↓
为 CVE-2016-4657 提供精确地址

5.3 为什么需要这个漏洞

问题：即使知道内核基址，仍需要：

  • 特定函数的精确地址（用于调用）
  • 数据结构的精确地址（用于修改）
  • ROP gadget 的精确地址（用于控制流）

解决：CVE-2016-4656 提供精确的内核地址信息，使后续利用更可靠。

6. 阶段三：内核代码执行（CVE-2016-4657）

6.1 漏洞原理

组件：XNU 内核

类型：内存破坏 → 代码执行

原理（简化）：

内核在处理某些操作时
        ↓
存在缓冲区溢出/类型混淆/UAF
        ↓
攻击者可覆写内核内存
        ↓
劫持控制流 → 执行任意内核代码

6.2 内核提权

目标：获得 root 权限 + 内核读写能力。

过程：

1. 利用 CVE-2016-4657 → 内核内存破坏
        ↓
2. 劫持控制流 → 执行攻击者代码
        ↓
3. 修改进程 cred → uid = 0（root）
        ↓
4. 获得 task_for_pid(0) → 控制内核任务
        ↓
5. 内核读写能力 → 可修改任意内核内存
        ↓
6. 安装 Pegasus → 数据窃取

6.3 提权后的能力

能力说明
root 权限可执行任何系统操作
内核读写可读写任意内核内存
沙箱绕过可脱离任何沙箱限制
文件访问可读写任何文件
进程控制可控制任何进程
网络访问可绕过网络限制

7. 攻击链完整流程

7.1 时间线

T+0s: 用户点击 SMS 链接 → 访问恶意网站
        ↓
T+1s: 恶意网站加载 → 执行特制 JavaScript
        ↓
T+2s: 触发 CVE-2016-4655 → 泄露内核基址
        ↓
T+3s: 触发 CVE-2016-4656 → 泄露内核地址
        ↓
T+4s: 触发 CVE-2016-4657 → 内核代码执行
        ↓
T+5s: 获得 root 权限 → 安装 Pegasus
        ↓
T+10s: Pegasus 开始运行 → 数据采集
        ↓
T+30s: 数据外传 → C2 服务器
        ↓
T+60s: 清除痕迹 → 攻击完成

7.2 攻击链依赖关系

CVE-2016-4655（KASLR 绕过）
        ↓  提供：内核基址
        ↓
CVE-2016-4656（内核信息泄露）
        ↓  提供：内核函数/数据地址
        ↓
CVE-2016-4657（内核代码执行）
        ↓  提供：root 权限 + 内核读写
        ↓
Pegasus 安装
        ↓  提供：数据窃取 + C2 通信
        ↓
攻击完成

7.3 攻击成功率

因素影响
用户交互需要点击链接（1-click）
iOS 版本仅影响特定版本（iOS 9.x）
设备型号影响所有 iOS 设备
补丁状态未补丁设备才受影响

8. 历史意义与后续演进

8.1 Trident 的历史地位

意义说明
首次公开首个被公开确认的 iOS 商业间谍软件
全链条原型确立了"多漏洞串联"的攻击模式
推动研究推动了对 iOS 安全的深入研究
行业影响推动了 Apple 的安全响应机制

8.2 后续演进

代次名称改进交互需求
Trident（2016）第一代首次全链条1-click
ImageIO（2018–2019）第二代零点击（iMessage）0-click
FORCEDENTRY（2021）第三代零点击（WhatsApp）0-click
M.O.（2022+）第四代无持久化0/1-click

8.3 Trident 的局限

局限说明
需要用户交互必须点击链接
仅影响旧版本iOS 9.x（已修复）
易被检测文件系统驻留，可被 MVT 检测
单一投递渠道仅 SMS 钓鱼

8.4 从 Trident 到现代攻击

演进方向：

  1. 零点击：从 1-click → 0-click（无需用户交互）
  2. 多投递渠道：从 SMS → iMessage/WhatsApp/水坑
  3. 无持久化：从文件驻留 → 内存驻留
  4. 反检测增强：从简单隐藏 → 环境感知 + 自毁
  5. 模块化：从固定功能 → 插件化架构

9. 防御与检测

9.1 补丁

Apple 响应：

  • 2016 年 8 月 25 日发布 iOS 9.3.5
  • 修复 CVE-2016-4655、CVE-2016-4656、CVE-2016-4657
  • 所有受影响设备应立即更新

9.2 检测方法

MVT（Mobile Verification Toolkit）：

# 提取 iPhone 备份
mvt-ios extract-backup -o /path/to/backup

# 检查 Trident/Pegasus IOC
mvt-ios check-backup -i /path/to/backup -o results/

检测指标：

类型指标
文件特定隐藏目录/文件
进程异常系统服务进程
网络已知 C2 域名/IP
配置恶意配置描述文件

9.3 防御建议

对个人用户：

  1. 及时更新 iOS：修复已知漏洞
  2. 不点击可疑链接：避免 1-click 攻击
  3. 启用 Lockdown Mode：高危用户强烈推荐
  4. 定期重启：清除无文件驻留

对企业/组织：

  1. MDM 强制更新：确保所有设备已补丁
  2. 网络过滤：阻止已知恶意域名
  3. 安全意识培训：教育用户识别钓鱼
  4. 定期检测：使用 MVT 等工具

10. 总结

Trident 是 iOS 安全史上的里程碑事件：

维度现状
漏洞数量3 个（CVE-2016-4655/4656/4657）
攻击类型1-click（需用户点击链接）
攻击链WebKit 信息泄露 → 内核信息泄露 → 内核代码执行
影响版本iOS 9.x（已修复）
历史地位首个公开确认的 iOS 商业间谍软件

技术要点：

  1. KASLR 绕过（CVE-2016-4655）：WebKit 信息泄露
  2. 内核地址获取（CVE-2016-4656）：内核信息泄露
  3. 内核提权（CVE-2016-4657）：内核代码执行
  4. 三漏洞串联：每个漏洞为下一个铺路

历史意义：

  • 首次证实 iOS 可被全链条攻击
  • 确立了"多漏洞串联"的攻击模式
  • 推动了对商业间谍软件的研究
  • 推动了 Apple 的安全响应机制

对现代攻击的启示：

  • 全链条攻击需要多个零日
  • 攻击链是层层依赖的
  • 防御需在每一层设置阻断
  • Lockdown Mode 可大幅降低攻击面
