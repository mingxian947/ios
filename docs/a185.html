Coruna 与 DarkSword 场景下的更换决策：出事之后，哪些东西真的该换

1. 执行摘要

  • 事件平息后的第一次管理会上，几乎一定会有人提出："要不要把 X 换掉？" X 可能是设备平台、安全产品、云服务、托管商，也可能是安全团队负责人。本篇讨论这个决定的判据结构——什么时候该换、换的是什么、换的过程为什么比事件本身更危险。
  • 核心命题一："被攻破"不是更换的理由，"根因落在该组件的信任假设上"才是。 定向投放针对的是你的暴露画像（#94），换个品牌并不改变"你被盯上"这件事。
  • 核心命题二：迁移期是新的最大暴露窗口。 旧系统在拆、新系统未熟、两套并行、账号双开、策略临时放宽——这四件事同时发生时，你的实际防御强度低于事件前。
  • 核心命题三：不换不等于不改。 多数情况下正确的答案是"换掉那一层出问题的信任假设"，而不是换掉整个产品；这需要能定位到层（#113 的分层、#114 的修复形态）。
  • 核心命题四：更换经常是政治决定，被包装成技术决定。 识别这一点不是为了讽刺，而是为了在决策时把"要给谁一个交代"和"技术风险"分开评估。
  • 核心命题五：换的成本要在决定时算清，不要在执行时算。 迁移的人力、双轨期的费用、培训、集成、数据搬迁、合同违约金，通常被低估两到三倍。
  • 一句话结论：先问"哪一层失效了"，再问"换掉这一层的最小动作是什么"，最后才问"要不要整体换"。

2. 这一篇补哪一格

#110 处理多身份与备用设备架构：怎么在设计上隔离。本篇处理出事之后的存量调整——从现状出发，而不是从白纸出发。

#96 处理设备处置与流转：单台设备怎么退出。本篇是组织级的批量退出与替换。

#167 处理合同条款：签约时怎么约束。本篇处理合同期内要不要终止、终止的代价。

#172 处理业务连续性与降级运行：事件期怎么活下去。本篇是事件后的结构调整，且必须在不中断业务的前提下进行。

#183 处理追偿：向对方主张。本篇是它的替代方案——用"换"来替代"告"。

#160 处理管控栈可见性：MDM/描述文件能看见什么。更换平台时，管控能力的差异是关键判据之一。

3. 四种可更换的对象

"换个供应商"是很粗的说法。实际可换的至少有四层，代价与风险差异巨大。

对象典型触发迁移代价迁移期风险是否解决根因
设备平台长期无法修复、支持终止极高极高部分（若根因是平台层缺陷密度）
安全产品检测失效、误报拖垮运营中中视根因：覆盖缺口是产品问题，绕过是能力问题
云 / SaaS配置权不足、数据位置不合规高高常见（权限与可见性问题）
托管 / 外包服务商响应能力不足、沟通失败中中到高常见（能力与流程问题）

表格最后一列是关键判据：更换只在你确实能指出"该组件是根因所在"时才解决问题。如果根因是"你的账号权限设计过宽"，换成任何平台，过宽的权限依然存在。

4. 判据：根因归属

用四个问题定位根因层。

  1. 入口在谁的控制范围内？ 如果是平台自身的缺陷，且该平台有修复承诺，那么"等补丁 + 缓解"通常优于"整体迁移"。
  2. 失效的是检测、阻断，还是响应？ 检测失效换产品；阻断失效可能是策略；响应失效是流程与人（#176）。
  3. 同类事件在别的平台会不会同样发生？ 会——说明根因不在平台。
  4. 更换之后，哪些控制会暂时缺失？ 这一问最容易被跳过，却是迁移风险的来源。
根因正确动作错误动作
平台缺陷密度高且修复慢评估分期迁移立刻全面替换
检测覆盖缺口换产品 / 加产品换整个平台
权限与配置过宽收紧权限、改架构（#110）认为换平台能解决
响应能力不足换服务商 / 补能力（#176）换设备
人（内部因素）结构与纪律（#186）任何技术更换

5. 迁移本身是最大的暴露窗口

迁移期有四件事同时发生，每一件都会削弱防御：

  • 旧系统在拆：部分控制已关闭，但替代尚未上线。
  • 新系统未熟：默认配置、缺失的集成、未调优的告警。
  • 两套并行：账号、权限、日志、备份出现双份，边界模糊。
  • 临时放宽：为赶进度而开的例外，通常没人负责收回（#104 的例外台账、#177 的访问登记表在此第二次生效）。
迁移阶段主要风险必须同步做的
准备期范围不清、依赖遗漏资产与依赖清单（#167）
并行期双份权限、日志割裂双份清单 + 到期日
切换期控制空窗选择低业务时段 + 加强监测
收尾期临时例外未收回一次性回收审计
稳定期旧系统残留残留清单与销毁确认（#96）

收尾期是最容易失守的一环：迁移项目通常以"新系统上线"为完成标志，而真正的完成标志应当是"旧系统的所有访问、数据、集成都已断开并有记录"。

6. 不换时的补偿控制

如果决定不换（这是多数情况下的正确答案），必须同时给出补偿措施，否则这个决定在下次审计或事件时无法解释。

  • 加一层：在失效的那一层外面加一个独立控制（例如在浏览器与内容之间加一层解析隔离，#118 的解析面）。
  • 缩范围：把高价值数据从该组件能触达的位置移开（#110 的分域）。
  • 提可见性：对该组件的行为加额外日志与告警（#161 的指标）。
  • 定期复议：设定一个复议时点，而不是"以后再说"。

四项里最容易被忽略的是第四项。一个没有复议点的"暂不更换"，在两年后会被读成"从未评估"。

7. 决策表

条件建议备注
根因明确在该组件，且无修复承诺更换分期，先低风险业务
根因明确，有修复承诺与时间表不换 + 缓解设复议点（#180）
根因不明不换，先查清换掉可能只是换掉证据
支持状态终止必须换无缓解选项（#180）
更换成本 > 预期损失 × 3优先补偿控制需书面结论
主要动因是"给一个交代"分开评估政治需求与技术要求分开记录

最后一行需要展开一句："给一个交代"是正当需求，但它不该伪装成技术结论。正确做法是同时写两份：技术评估（该不该换）与管理决定（为什么现在换/不换）。两份都留着，未来无论谁问，都有答案。

8. 加固清单（八条）

  1. 先定根因层，再谈更换对象。
  2. 迁移前做资产与依赖清单，否则范围必失控。
  3. 并行期建立双份清单（账号、数据、集成），每项有到期日。
  4. 切换期选低业务时段并临时加强监测。
  5. 收尾以"旧系统完全断开"为完成标志，不是"新系统上线"。
  6. 不换时给四项补偿：加层、缩范围、提可见性、设复议点。
  7. 技术评估与管理决定分开书面对待。
  8. 更换决定纳入下一年度的预算与培训计划（#176）。

9. 八条常见误解

误解实际情况
"被攻破了就该换"被盯上是暴露画像问题，换品牌不改变
"换了就安全了"根因不在组件时，换了照样发生
"迁移是 IT 项目"它是安全项目：迁移期防御强度最低
"新系统上线就算完成"旧系统未断开等于没完成
"并行期只是多花点钱"双份权限与日志割裂是实质风险
"暂不更换就是什么都不做"必须有四项补偿与复议点
"换掉负责人就解决问题"人的问题需要结构与纪律（#186）
"政治因素不能写进决策"要写，但要与技术评估分开
