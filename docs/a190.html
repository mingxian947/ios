Coruna 与 DarkSword 场景下的第三方 SDK：你发出去的包，没有一个是你自己写的

1. 执行摘要

  • 一个 iOS 应用动辄链接几十个第三方 SDK：统计、推送、支付、广告、地图、客服、风控。出事时，上游的一个版本问题会同时出现在成千上万个应用里，而你既不是发现者，也不是修复者，却要面对用户。
  • 核心命题一：供应链事件的第一个事实是"我不知道我用了什么"。 没有组件清单的组织，在通知到达的那一刻才开始做资产盘点，而盘点的成本高于事件本身。
  • 核心命题二："受影响"分三层：代码层、运行时层、数据层。 只有代码层能靠升级解决；运行时层要看实际触达，数据层要看实际外发。
  • 核心命题三：上下游的义务是不对称的。 上游通知你"有风险"，不等于它告诉你"哪一段代码、影响哪些功能"；下游你必须自己判定"我的用户是否真的被影响"。
  • 核心命题四：重打包与发版是新的暴露窗口。 事件期仓促升级，可能把未经充分验证的版本推给全部用户。
  • 核心命题五：用户告知的口径，必须严于你的事实，宽于你的隐私边界。
  • 一句话结论：把 SDK 当成"外部依赖"就会被动挨打；把它当成"必须随时能说清版本、来源与实际行为"的资产，处置才可能按时完成。

3. 组件清单：事件期最贵的东西，是事前最便宜的东西

一份可用的组件清单至少包含六个字段：

字段为什么必须有常见缺口
组件名与供应方定位上游只写了商业名，没写实际包名
版本号（含构建号）判定是否受影响只记录主版本
集成方式二进制 / 源码 / 动态库不知道是否被二次封装
调用位置哪条功能路径会触发无人维护
数据访问范围能读到什么只信"隐私标签"
更新责任人谁能拍板升级组件已无人负责

最后一行是组织层面的真问题。 一个没有责任人的 SDK，在事件期会变成"没人敢动"的那一个。

4. 三层影响判定

收到上游通报之后，先做三层判断，而不是直接升级：

代码层：我的包里是否包含受影响版本？
   ↓ 是
运行时层：哪些功能路径真的会加载并执行它？
   ↓ 是
数据层：它实际拿到了什么数据、发往哪里？
层判定方法结论形态
代码层产物比对的版本与哈希是 / 否 / 部分（动态下发）
运行时层配置开关、初始化条件、功能入口活跃 / 休眠 / 不可达
数据层网络行为观察与字段核对实际外发内容清单

"休眠"是一个合法结论。 受影响代码被打包但从未被初始化，与"完全没有"不同，与"已受影响"也不同；这一层区分直接影响后续对用户的措辞（#181 审计与认证中的历史事件陈述）。

5. 处置顺序：九个步骤

  1. 确认上游事实：受影响版本区间、缺陷性质、官方建议动作。
  2. 冻结相关配置：先断开可能有风险的远端开关与初始化路径（可逆动作优先，#184）。
  3. 完成三层判定，产出一张影响表。
  4. 评估替代方案：升级、降级、移除、或临时隔离。
  5. 在预发布环境验证：功能回归优先于版本号追新。
  6. 分批放量：先小比例，观察崩溃与关键路径。
  7. 对下通知：按影响层写不同版本的说明。
  8. 留痕：版本、时间、决策理由。
  9. 复盘入清单：把这次学到的东西写回组件清单。

第五步与第六步是事件期最容易被压缩掉的两步。 压缩它们的代价，往往是一次新的、与事件无关的线上故障。

6. 对下通知的三种口径

场景可以说不能说
只有代码层受影响、未激活"包含某组件，但该功能未启用""我们没有使用该组件"
运行时层可达、数据层未触及"功能路径可达，经核查未观察到相关数据外发""绝对没有数据泄露"
数据层已触及"存在相关数据外发，范围为…，已采取…"任何缩小范围的形容词

三行共同的纪律：结论必须带上判定方法与范围。没有方法的结论，在复核时会被当作猜测（#178）。

7. 与上游打交道的四个现实

  1. 上游不会给你 PoC。 它给的是"受影响版本 + 修复版本"，你必须自己完成影响面判定。
  2. 上游的通知可能晚于你的用户投诉。 建立独立的观察渠道（崩溃、异常网络、客服关键词），不要只等邮件。
  3. 上游可能已停止维护。 对不再维护的组件，"移除"往往比"打补丁"更现实。
  4. 上游的措辞会被转述。 你在内部与对外的每一次转述，都会被当成"官方口径"——不要把上游的谨慎措辞改写成确定性结论。

8. 两个结构性建议

建议一：把组件清单纳入发布流程。 每次发版自动生成一份"本次产物包含的组件与版本"，作为发版物料的一部分，而不是事件期临时去找。

建议二：给每个高危组件准备一份"移除预案"。 不需要真的执行，只需要写清楚"如果明天必须移除它，谁来做、影响哪些功能、需要多久"。

这两条的共同点是：把事件期的临时工作，转化为发布期的固定动作（#176）。

9. 加固清单（八条）

  1. 建清单：六个字段，缺一不可。
  2. 指定责任人：没有责任人的组件，等于没有人管。
  3. 分三层判定：代码、运行时、数据，逐层给结论。
  4. 可逆优先：先断开关，再改代码。
  5. 预发布验证：功能回归优先于版本追新。
  6. 分批放量：不要一次推给全部用户。
  7. 口径带方法：每条结论都说明是怎么判定的。
  8. 写回清单：复盘结论必须落到组件清单里。

10. 八条常见误解

  1. "用了知名 SDK 就安全。" 知名度与本次版本的安全性无关。
  2. "上游说修复了就等于我修复了。" 你必须自己发版。
  3. "打包进去就等于在用。" 可能从未初始化。
  4. "没初始化就等于没风险。" 取决于是否可能被远端打开。
  5. "升级越快越好。" 未验证的升级会制造新故障。
  6. "用户不会在意。" 用户在意的是告知是否及时、口径是否一致。
  7. "我们没有数据外发。" 需要有观察证据，而不是断言。
  8. "这不归安全团队管。" 供应链事件的处置是跨团队的，必须有单一协调人。

11. 与既有各篇的接口

  • 与 #153 对照：Web 侧脚本与原生 SDK，是同一类问题的两个战场。
  • 与 #167 衔接：合同条款决定了你在上游不配合时有多少手段。
  • 与 #181 对接：对用户与审计的陈述，必须有范围与方法。
  • 与 #184 对接：重打包与发版的排期，要与其它处置动作统一。
  • 与 #176 对接：清单与移除预案，属于能力建设的固定科目。
  • 与 #195 对接：需要技术意见时，鉴定范围应覆盖"组件是否实际执行"。

12. 总结

第三方 SDK 的本质是你承担了别人代码的风险，却没有别人的上下文。事件期能做对的事只有三件：

  1. 知道用了什么、什么版本、谁负责。
  2. 分清代码层、运行时层、数据层，分别给结论。
  3. 用可验证的口径对外说话，用可回退的节奏发版。

把这三件事做成发布流程的一部分，供应链事件就从"突袭"变成了"演练过的那一天"。
