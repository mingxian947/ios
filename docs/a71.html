iMessage 与端到端消息通路的攻击面分析：0-click 投递面与取证边界

编制日期：2026-10-24 数据来源：Apple Platform Security 与 iMessage 安全文档、Google Project Zero（含零点击消息通路相关披露）、Citizen Lab 与 Amnesty 公开报告、CVE 情报库、MVT 工件范围 性质：防御性安全研究分析（Defensive Security Research），不提供可利用代码

1. 执行摘要

在公开的商业间谍软件案例里，"用户什么都没点就中招"这一形态反复出现，而它最常见的落点不是浏览器，而是消息通路：一条送达的报文就能让设备上的解析代码处理攻击者提供的字节。本文把这条通路拆开，说明它为什么天然构成攻击面、端到端加密在其中起了什么作用（以及没起什么作用），以及调查者能从这条链上拿到什么证据。

四条结论：

  1. 端到端加密保护的是内容机密性，不保护接收端的解析安全：报文必须在设备上被解码与渲染，因此加密与"0-click 攻击面是否存在"是两件独立的事。
  2. 消息通路的危险不来自"发送者可控内容"这一点本身，而来自三项叠加：送达即处理（无用户动作）、富媒体自动解析（附件、预览、缩略图）、扩展参与渲染（通知服务/表情/贴纸类扩展）。这三点在架构上与其他各篇讨论的解析面同构（#44、#52、#68）。
  3. 因此有效的平台级缓解不是"加密更强"，而是推迟或隔离解析：不自动下载远程内容、把解析放进隔离域、限制扩展可触达的能力。#34 的锁定模式正是作用在这三个开关上。
  4. 对调查者而言，消息通路是双刃：设备端取证可以拿到会话元数据与本机落地内容，但服务端因端到端而拿不到历史明文；同时"密钥在设备上"意味着一旦设备被攻破（#41、#53），端到端保护对被感染的那一端不提供任何防御。

2. 通路的分层与处理时机

发送方
  │  服务端路由（账户/设备标识、推送中继）
  ▼
到达层：推送/唤醒  ←──── 与 #65 的推送通路完全重合
  │
接收层：报文解码（协议层解析、类型分派）
  │
渲染层：文本/附件/预览/链接卡片
  │        ├─ 自动下载与缩略图生成（媒体解析，#44 同类）
  │        └─ 扩展参与（通知服务扩展、贴纸/表情类）
  ▼
存储层：本机会话数据库（受 Data Protection 保护）
层是否需用户动作处理攻击者可控字节缓解开关
到达（推送唤醒）否少量（负载字段）专注模式、通知设置、锁定模式收紧
协议解码否是（报文结构、字段）无法由用户关闭（需保持可收件）
富媒体/预览视配置是（图像、音视频、字体等格式解析）关闭自动下载、限制预览
扩展渲染多数自动是（扩展进程内的解析）沙箱范围与扩展能力限制（#52）
存储否内容落地Data Protection 类别（#43、#53）

关键结构点：与浏览器路径（#40）不同，消息通路在"用户尚未决定要不要看"的时候就已经执行了解析。这就是"无交互（L1）/无渲染（L2）"分层（#43）存在的原因：越靠前的层，用户越没有机会介入，因此防御只能靠架构隔离而非用户习惯。

3. 端到端加密改变了什么、没改变什么

维度端到端加密的作用不作用
传输中内容机密性有效（服务端仅见密文与元数据）—
服务端历史明文可得性服务端依法配合也拿不到历史内容元数据（时间、参与者、设备标识）仍在
接收端解析安全无作用：解密后必然本地解析攻击面照常存在（第 2 节解码/渲染层）
被攻破设备上的可读性无作用：密钥与解密结果都在本机取证/入侵同样能读到会话（#53、#42）
备份侧取决于备份的密钥归属（见 #69 的密钥分层）若类别非端对端，云端可解
联系人映射与账户关联无作用标识解析服务仍暴露手机号/邮箱与密钥的对应关系

结论：把"这条消息是加密的"理解为"这条路径是安全的"，是防御沟通里最常见的错误。加密是内容层面的属性；攻击面是解析代码层面的属性。任何声称"因为端到端加密所以不可能被消息投递攻破"的判断都需要按第 2 节重新检查。

4. 投递形态与前置能力要求

形态用户动作需要的前置能力与已有篇目对应
D1 送达即触发解析缺陷无一个报文触发解析层内存缺陷，通常还需 #68 的可达性 + #41 的提权#43（L1/L2 分层）、#49
D2 送达 + 渲染触发无（打开会话即渲染）渲染/字体/图像解析缺陷#44、#52
D3 诱导点击（钓鱼链接）有仅需社工；随后走浏览器路径#40、#66 路径 C
D4 附件外发通道利用无（自动下载后解析）关闭自动下载即可消除#47（外发与隐蔽通道）
D5 已感染设备借用会话无已有代码执行 + 采集能力#42、#53

D1–D2 属于稀有的无交互远程形态，工程门槛高、单条报文价值大，因此公开案例里出现次数有限但影响重大；D3 在实际感染事件中的总量远高于前者。防御预算因此要分人群：高危角色按 D1/D2 假设配置（锁定模式、关闭自动下载、最小授权），普通角色主要防 D3。

8. 总结

#结论
1端到端加密保护内容机密性，不保护接收端解析安全——两者是独立属性
2消息通路的风险来自"送达即处理 + 自动解析 + 扩展参与"三项叠加，而非内容可控本身
3因此平台级缓解的正确方向是推迟与隔离解析，锁定模式正作用在这三个开关
4D1/D2 类无交互投递工程门槛高，防御预算应按人群分配：高危按无交互假设，普通按钓鱼假设
5一旦设备被攻破，端到端对被感染那一端不提供防御；会话内容对本机取证与对入侵者同样可读
6调查上最可靠的时间窗信号常是渲染层崩溃聚合与推送唤醒时刻，而不是消息数据库本身
7自动下载关闭时"附件工件缺失"是预期状态，不能据此推断未收到报文

一句话总结：Coruna 与 DarkSword 这类链条之所以反复把消息通路当作入口，不是因为加密有缺陷，而是因为任何可用设备都必须解密并渲染报文——防御方真正能控制的，是让这份解析发生在多隔离的域里、发生得多晚、以及是否根本没有发生；把这条通路理解为"加密即安全"，是所有关于 iMessage 的风险讨论里代价最大的一个误解。
