iOS 微架构侧信道与硬件级信息泄露：不需要漏洞也能拿到比特的那一层

本文是防御视角的分析与方法论梳理，不提供可利用代码，不涉及攻击脚本、探针焊接指导或任何可直接复现的操作步骤。面向安全研究者、企业安全负责人与需要评估"物理接触风险"的咨询客户。

1. 为什么要单独写这一层

前面的系列已经用了三根轴来切分 iOS 的攻击面：

轴代表篇目切分依据
系统层#2 漏洞类型全景WebKit / PAC / 沙箱 / 内核 / 固件 / 数据 / 协议 / 配置
缺陷类别#81 Bug Class 分类学UAF、越界、类型混淆、整数、TOCTOU、逻辑误用……
被攻击的组件#82–#87IOKit 驱动、第三方 App、锁屏与数据保护、分发生态、智能输入通路

这三根轴都有一个隐含前提：攻击者要利用一段软件里的错误。

侧信道不是。它的定义性特征是：攻击面不来自某个函数的边界检查写错，而来自硬件为了性能而做的共享与预测——缓存、预取器、分支预测器、内存控制器、时钟与功耗路径。目标代码可以是完全正确的，密钥可以是正确隔离的，签名可以是合法的；攻击者读的是"它运行时的物理副作用"。

这带来三个对防守方极其不舒服的性质：

  1. 无法通过打补丁消灭。没有一行代码可以"修好"，只能改变暴露条件（关特性、隔离时序、缩小密钥空间、缩短观察窗口）。
  2. 绝大多数在运行日志里没有痕迹。它不产生异常、不写文件、不改权限、不发出网络包。企业侧"检测能力"几乎为 0。
  3. 威胁模型门槛差异极大。从"一个装了恶意 App 的普通用户"到"国家级实验室里接了探头的设备"，都叫侧信道，但风险等级差 3–4 个数量级。把它们混为一谈是这一层最常见的误判。

本文的目的就是把这四类通路分开，给出各自的可达性判据（防守方能不能在不做实验的前提下判断自己是否真的暴露），以及对应的处置方式。

2. 四类通路与它们在 iOS 上的实际形态

2.1 缓存与内存时序侧信道

原理一句话：共享缓存行被访问后留下可测量的时序差异，攻击者据此推断"被保护的那段代码在什么条件下访问了哪块内存"。常见形式（学术命名，此处仅列概念）：Prime+Probe、Evict+Time、Flush+Reload，以及在 ARM 上需要额外注意的预取器干扰。

在 iOS 上的可达性判据（四个都要满足才算真风险）：

判据说明常见误判
① 与目标同处一个执行域需要能在同一颗 CPU 簇、同一级共享缓存上并发执行代码"App 之间共享 SoC 所以任意 App 都能读密钥"——不成立。iOS 的进程隔离、簇划分与调度使得跨进程稳定共置并非默认事实
② 目标密钥空间小时序噪声大，需要重复采样取平均。AES/RSA 之类在硬件加速单元里完成的运算，几乎不给出可重复的细粒度时序把"论文里在可控服务器 CPU 上的成功率"直接搬成"手机上也行"
③ 观察窗口足够长一次采样不够，需要秒到分钟级的持续执行权忽略了 iOS 对后台执行、脚本执行时长的强约束
④ 攻击者代码能常驻且能反复触发目标需要目标进程在采样期间持续工作把"瞬时通知触发一次解密"当成可用窗口

谁能同时满足四条：一个通过 App Store 或企业证书安装在目标机上、能长时间驻留的恶意 App（高危个体场景），或越狱设备上的任意代码。这也是为什么这一类攻击在 iOS 上的现实定位是辅助手段——用来把"已经拿到的一些原语"变成可用的信息泄露，而不是独立成立的一条攻击路径。

与系列其他篇目的接口：#51（内核信息泄露与 KASLR）、#4（PAC 绕过）里描述的是"信息泄露原语"。侧信道在链条中的角色通常是提供或加强这类原语，而不是替代它们。真实链条仍然是：入口 → 信息泄露 → 控制流原语 → 提权 → 驻留采集。

2.2 推测执行与分支预测

Intel 上 2018 年公开的那一族（Spectre/Meltdown 类）问题，本质是：CPU 在分支判断结果出来之前就先执行，被误执行的那段代码留下了缓存痕迹。ARM 上同样存在这一类问题，具体变体、命名与受影响的核心代际因芯片与微码版本而异，且公开信息不对称——苹果对 A 系列处理器的具体受影响面与缓解方式披露很少。

对防守方更重要的是这三条结论：

  1. PAC 防不住它。指针认证校验的是"指针有没有被改写"，而推测执行攻击根本不破坏控制流完整性——它让 CPU 短暂地"以为"可以走到不该走的地方，读完数据后一切看起来正常。#4 里讨论的 PAC 强度评估，在这一层完全不适用。
  2. 主要缓解在硬件与编译器两层，用户与企业的杠杆很小：分支预测隔离（按进程/地址空间隔离预测状态）、序列化指令插入、编译器层面的推测屏障。这些随系统版本发布，不是可以打开的开关。
  3. Safari/WebKit 侧的软件缓解与它有关：站点隔离、禁用部分高精度计时能力、以及 Web 层对推测执行风险的额外屏障。这一部分与 #3/#21/#30/#57 是连续的：Web 引擎既是远程入口，也是"从网页触发本机侧信道"的少见通路，因此它的计时能力收紧是有意义的。

近年的学术方向（结论层面提一下，不展开）：Apple Silicon（M 系列）上出现了几项针对数据相关预取器、PCIe DMA 与 PAC 交互的高水平研究，以及针对 DDR 内存的电荷干扰（Rowhammer 类）研究。这些成果的目标平台主要是 Mac，而不是 iPhone；把它们直接推断为"iPhone 同样受影响"是不严谨的。判断口径见 #85：以厂商安全发布与明确版本影响面为准，不以论文标题为准。

2.3 故障注入与芯片级物理攻击

形态：电压/时钟毛刺、电磁注入、探针读取总线、微码或固件回滚。目的是让正确实现的硬件"跳过一次检查"，而不是绕过检查逻辑。

可达性判据：需要设备脱离机主控制、专业实验室、以及分钟到小时级的物理接触。这基本等于"设备被扣押、被偷走送检、或走件时被拦截"。

iOS 上唯一不可修补的著名例子是启动 ROM 级的逻辑缺陷：A5–A11 世代的 bootrom 存在不可通过软件更新修复的缺陷（Checkm8 一类），这也是为什么 #64（安全启动链）里强调"能力上限在旧机型上更低"。它严格说不是侧信道而是直接逻辑缺陷，但归属于同一威胁模型——物理接触 + 硬件层。

这一层对个人的含义：如果对手愿意做芯片级操作，那么"锁定模式"、"强密码"、"数据保护等级"（见 #84）都只是提高成本，而不是关闭通路。真正的杠杆在设备是否离开你的视线与旧机型的换代。

2.4 功耗、电磁与时序（面向安全处理器的研究）

针对 Secure Enclave（SEP）与钥匙串密钥的学术研究长期存在，方法多为功耗/电磁迹分析与故障注入的组合，用于恢复密钥或跳过检查。相关的能力边界在 #9 与 #53 已有讨论。

需要明确的现状判断：

  • 这类攻击没有公开的野外武器化案例。它是"国家级实验室能力"，不是商业间谍软件交付链的一环。
  • 它的实际意义更多在于论证密钥存储有上限：SEP 大幅提高了成本，但把"永久密钥"写进任何可物理接触的芯片，都不等于数学意义上的不可获取。
  • 对咨询场景，正确的表述是：评估目标对手是否具备芯片级实验室，而不是评估 SEP 强度。前者决定风险是否存在，后者只决定所需时间。

结论对防守端非常有指向性：

  1. 对绝大多数人，侧信道不是攻击向量，而是取证手段——它发生在设备已经被扣押之后。这一层应该并到 #84（锁屏状态与强制解密边界）与 #62（取证证据链）去处置，而不是单独做加固预算。
  2. 对能装恶意 App 的高危个体，2.1 有边际意义，但处置方式跟 #80 里的高危个体层完全一致（限制可常驻代码的安装来源），不需要新的措施。
  3. 对国家级目标，这一层不需要你来做决策：结论永远是"假设硬件秘密可以被获取，因此把机密从设备里移出去"。见 #80 的高危个体一节与 #84 的密钥治理结论：损失范围由密钥治理决定，不由芯片强度决定。

5. 防守方可以做的四件事（按性价比排序）

这一层的处置动作很少，但每一条都要做到具体：

  1. 换代：把不可修补的启动 ROM 缺陷排除在资产库外。以 A11 及更早机型为界（见 #64 的启动链结论），企业侧用 MDM 的设备清单核对真实机型而不是申报机型。这条对 2.3 是决定性的。
  2. 把"物理接触时长"当作一个可管理的风险指标。行李检查、酒店、跨境通关、快递代签收是高危个体的实际暴露窗口。对策不是"更长的密码"，而是关键内容不落在这台设备上（#80 高危层、#84 密钥治理）。
  3. 收紧计时能力暴露面。Web 侧保持浏览器与系统更新即可，不需要额外折腾；App 侧的正确要求是：不要在应用层做对时序敏感的密钥比较（用密码学等值比较而非短路比较），这是给开发者的唯一一条硬要求。
  4. 在风险评估文档里给它正确的预算。这一层的现实概率极低而成本极高，把它写成独立的高风险项是常见错误（也是把预算从"补丁时效"和"分发面治理"这些真正高频的问题上挪开的常见借口）。参照 #85 的暴露窗口指标体系做优先级排序。

6. 五个常见误解

误解事实
"侧信道是新出现的漏洞类型，苹果会出 CVE"它多数不是缺陷，而是硬件设计代价；常以"缓解措施"而非 CVE 出现，也常常不进入安全发布说明
"PAC / SPTM 让 iPhone 免疫"这些是完整性机制，不处理时序泄露；推测执行甚至能短暂绕过控制流校验的语义（见 2.2）
"Mac 上的论文结论可以直接写到 iPhone 风险清单里"芯片代际、内存类型与调度器差异很大。按 #85：以厂商明确影响面为准，否则只写"未证实"
"只要有恶意 App 就能提取我的密钥"需要同执行域、长窗口、小密钥空间与可重复触发；现实中几乎不成立，别把它当作普通用户的威胁
"所以侧信道可以忽略"反过来说也不对：一旦设备进入"被扣押/被物理控制"场景，它就从"理论"变成"取证工具箱"，评估必须换一套判据（#84、#62）

7. 一句话结论

iOS 的漏洞讨论里，这一层最容易被两种声音扭曲：一种是把它渲染成"你的密钥随时会被读走"，一种是干脆当作学术趣闻跳过。正确的位置是——

它不是入口，也不是提权，它是"当物理与执行权已经不属于你时"的附加泄露通道。

所以对绝大多数用户，最好的侧信道缓解就是 #80 里的第 1、2 层：设备不离开视线、系统保持更新。对少数人，最好的缓解是干脆不让秘密存在于设备中。把这两句写进策略，比追任何一篇论文都有效。
