iOS 与 Android 系统漏洞结构对照：同一类缺陷为什么在两个平台上代价不同

本文是防御视角的架构对照分析，不提供可利用代码，不做厂商优劣评价，也不比较两平台的漏洞数量统计（这类比较缺乏可比口径）。本文只做一件事：把"同一类系统缺陷"放进两套分发与信任结构里，看它的修复路径、可达人群和处置责任为什么不同。所有具体版本与组件差异以两家官方安全公告为准。

1. 为什么需要这篇对照

系列里的 #2 按系统层次分类、#81 按缺陷类别分类、#90 按攻击者起始位置分类、#91 按后果分类、#93 按引入阶段分类、#94 按实际暴露人群分类、#111 按修复载体分类。这些轴都隐含一个前提：平台结构不变。

一旦跨平台比较，这个前提就没了。同一条"图像解析里的越界写"（#81 的 OOB 类）在两个平台上的处理流程完全不同：谁收到报告、谁写补丁、谁把它带进设备、多久到达、能不能强制——这四问的答案由分发结构决定，而不是由缺陷类别决定。

因此本文的对照口径是固定五个问题：

  1. 修复由谁产出（单一供应商还是分层供应链）；
  2. 修复由谁送达（厂商直接推还是经第三方环节）；
  3. 修复能强制吗（个人延后、企业锁定的自由度）；
  4. 缺陷可达面由什么决定（默认安装来源策略、默认开启的解析能力）；
  5. 缓解机制是否随硬件代际分叉。

一句判读：比较平台不是比较安全性，而是比较"一条缺陷从被发现到不可利用，中间要经过几个不由你控制的环节"。

2. 五个结构性差异

结构差异iOSAndroid对缺陷处置的实际影响
S1 供应链形态单一供应商：内核、框架、驱动、固件同一家产出分层：AOSP 核心 + 芯片组厂商驱动 + OEM 定制 + 运营商配置Android 上一条 CVE 的"受影响范围"必须问到机型与 SoC；iOS 的范围以版本+机型列表表达（#75 的公告读法）
S2 修复送达环节厂商 → 设备（OTA），环节少AOSP 补丁 → OEM 集成 →（运营商认证）→ 设备，环节多送达延迟差异远大于缺陷本身差异；#85 的"暴露窗口"在 Android 上更难预测
S3 更新粒度整机镜像为主，辅以增量安全响应与服务端载体（#111 的 V1/V2/V5）分层更新：内核与核心框架（GKI）、模块化组件（Mainline 之类经服务通道更新）、OEM 层各自节奏Android 的部分组件可以不等整机就修复；代价是"已修复"需要按层核对，验证判据更复杂（#111 第 5 节）
S4 安装来源策略默认封闭：App Store 之外仅测试分发、企业分发与描述文件通道（#67），侧载受系统级限制默认开放但受策略约束：可允许第三方来源，工作场景可由 MDM 关闭；同时有应用级完整性校验机制iOS 的滥用集中在"合法签名链被借用"（企业证书、配置描述文件）；Android 的滥用集中在"来源与安装时刻"（#86/#97）
S5 硬件代际耦合缓解机制高度绑定芯片代际，旧机型无法回溯（#79/#94）高端与中低端、不同 SoC 之间能力差异更大，且部分安全特性依赖 OEM 是否实现两平台都有"设备代际即安全决策"的问题，Android 的方差更大，iOS 的分界线更清晰可判定

S2 与 S3 是一对反向权衡：iOS 的更新链路短，所以"一条更新修全部"，代价是链路短不等于送达快，装不装仍由人决定；Android 允许组件分层更新，所以一部分修复能绕过 OEM 节奏，代价是"这台设备现在是什么状态"变成三层问题。

3. 十二项对照：同一缺陷类在各环节上的差别

环节iOSAndroid谁的处置动作因此不同
内核XNU（Mach + BSD + IOKit 驱动模型）Linux 内核 + OEM 变体驱动类缺陷的归属：iOS 找 Apple，Android 要先判定驱动来自谁（#82）
强制访问控制沙箱（Seatbelt 策略）+ 代码签名强制SELinux 域 + 应用沙箱逃逸后的"第二层"不同：一次逃逸在两平台上换来的能力不等价（#68）
完整性防护代码签名与库验证贯穿加载链（#73）签名 + 验证启动 + 应用级校验，OEM 实现有差异加载链类缺陷的影响范围：Android 需按 OEM 判定
安全协处理器独立安全子系统承担密钥与敏感状态（#9/#53）各方案实现（可隔离硬件密钥取决于机型是否支持）"设备被拿走时密钥是否可提取"在两平台上是机型问题而非平台问题（#84）
信息通路消息解析在隔离网关后处理（#65/#71）通知与应用级解析分层0-click 面的位置不同，但都不等于"没有解析暴露"（#60）
Web 引擎系统级单引擎，JIT 与 WebAssembly 受严格约束（#57）引擎作为可更新组件，可经服务通道更新修复到达速度：Android 的引擎层常先于系统补丁
图形栈图形/WebGPU 相关栈作为历史高价值攻击面（#58/#40/#43）GPU 驱动来自芯片组厂商同一缺陷类别，但补丁责任人不同
无线与基带基带栈由厂商统一更新（#26/#72）基带与固件由芯片组/OEM 分别交付基带类修复的可见性：Android 更难自查
侧信道硬件级侧信道随芯片代际变化（#88）同样存在，且缓解实现依赖内核配置与 OEM这类问题都不能靠"更新一下"解决，需按 #88 的能力口径判断
漏洞赏金与披露单一赏金计划 + 集中公告（#75）平台层 + 组件层 + 多家厂商各自公告情报源数量与口径不统一，监测成本不同（#85）
补丁状态可读性版本号 + 构建号 + 增量编号（#111 的 C1）安全补丁级别（SPL）+ 组件层状态审计时"证明已修复"的证据形式不同
企业强制能力版本区间约束、配置描述文件、受限功能开关设备/工作资料分层、策略下发、合规检查强制更新可行度：取决于设备所有权模型（#76）

4. 用 #81 的缺陷类做行：修复路径长度差多少

缺陷类（#81）iOS 修复要经过Android 修复要经过结构性结论
内存越界 / 整数溢出（系统解析器）Apple 单点视解析代码归属：平台层或 OEM 或第三方库越靠近"谁都能改的层"，验证越难
类型混淆（脚本引擎）Apple 单点，且常叠加语言层硬化（#79/#81）引擎层与系统层可分离，可较快到达模块化让单点缺陷到达更快
驱动/UAF（IOKit 类）Apple 单点常落在供应商驱动，链路更长两平台差异最大的一类：责任归属而非技术难度
逻辑误用 / 授权模型缺陷Apple 单点平台 + OEM 定制策略两层授权类缺陷在两平台都"修得慢"，但原因不同
信息泄露（KASLR / 侧信道）需版本或代际配合依赖内核配置与 SoC都不适合用"等更新"当主要处置（#88）
TOCTOU / 文件与备份路径Apple 单点依赖存储实现与 FBE 细节处置动作相同（#74 的备份边界），差别在证据形式

这张表的价值不在于"哪边更好"，而在于给出一个可操作的推论：在 Android 上处置一条系统漏洞，第一步是确认它属于哪一层；在 iOS 上处置一条系统漏洞，第一步是确认它属于哪一种载体（#111）。

5. 攻击者视角的选择规律（只作为防御推论）

不写任何手法，只写结构结论：商业攻击能力的采购方向（#77）长期同时覆盖两个平台，说明攻击侧按目标人群与暴露窗口选型，而不按平台品牌选型。由此推出三条防御含义：

  1. 暴露窗口 > 缺陷质量：一条中等缺陷 + 一条长送达链，往往比一条严重缺陷 + 一条短链路更危险——这正是 #75/#85 把优先级从"分数"改成"窗口"的理由，跨平台时更成立。
  2. 规模决定投递方式：目标人群的分发结构决定了攻击者需要不需要用户动手（#90 的 P0–P5），两平台在"默认安装来源策略"上的差异（S4）直接改变这一段的成本。
  3. 同一批人两平台都暴露：跨平台通信的两端不构成隔离（#71 同一条道理）——为某个人换平台，不改变他所在的通信关系带来的暴露（#99/#108）。

6. 对企业与个人的实际含义

对象应该拿走什么
个人平台选择不解决加固问题：#80 的通用清单在两平台内容一致；真正决定结果的是更新节律与默认开启的解析能力（#94 的 V2/V4）。把"换平台"当处置动作，等于把风险换成另一套不由你控制的链路。
混合平台企业两套强制机制的可达范围不同，不要用同一套指标报告"合规率"；风险报表应区分"厂商已发布修复"与"设备真的在跑修复后的代码"（#111 的 C1–C5），Android 侧还要区分修复落在哪一层。
采购与安全基线决定暴露长尾的是支持年限、更新送达记录、是否可被 MDM 强制这三项，而不是品牌；旧机型停留（#94 的 V1）在两平台都是最稳定的长期风险来源。
高价值个体判断依据是"这台设备的缓解层是否已到期"（#79/#94）与"我能不能强制自己立刻更新"，两者都比平台名称更有决定性。

7. 三个不能误用的地方

  1. 不要把对方平台的事件当自己平台的证据：同一缺陷类在一个平台上的可利用性，不能推断另一个平台的可利用性，因为可达面、缓解层与责任人都不同。
  2. 不要做漏洞数量的横向统计比较：两边的披露口径、公告粒度、赏金规则与安全补丁级别的定义不可比（#75 已经说明披露本身有结构性偏差）。
  3. 不要把"分层更新"读成"更安全"：它提高部分组件的到达速度，同时降低状态可读性——它把风险从"晚到"换成了"难验证"，这是 #111 第 5 节判据要变复杂的原因。

8. 常见误解

误解更正
"两个平台的漏洞谁更多"没有可比口径；可比的只有"一条缺陷到不可利用要经过几个环节"（第 1 节五问）
"iOS 单一供应商所以修复一定更快"环节少不等于送达快：装不装、重启不重启仍由人决定（S2/S3）
"Android 能模块化更新所以不用管系统版本"组件层修复不覆盖内核与 OEM 层，仍要按层核对（第 4 节）
"驱动类缺陷两边难度差不多"差异最大的一类：Android 的难点常在责任归属而非技术（第 4 节）
"侧载政策差异等于漏洞差异"它改变的是攻击者需不需要用户动手，不改变系统缺陷本身（S4 + #97）
"旧 iPhone 比旧 Android 更安全"两平台的长尾都由机型上限与代际决定，分界线清晰度不同但都存在（S5 + #94）
"给高危的人换平台就降低风险"跨平台通信端不构成隔离，暴露主要由关系与账户结构决定（#99/#108）

9. 一句话结论

同一类系统缺陷在两平台上的代价差，几乎不来自缺陷本身，而来自五个结构：供应链是否单一（S1）、送达是否经第三方环节（S2）、更新粒度是否分层（S3）、安装来源策略（S4）、缓解机制与硬件代际的耦合方式（S5）。

由此得到两平台各自的第一动作：iOS 先看载体类型（#111），Android 先定缺陷所在层；两平台共同的长期风险都是设备代际与更新停留（#94），而它不由平台名称决定。跨平台比较的产出只有这一个：把处置责任落到正确的那一层，从而知道该向谁要证据。
