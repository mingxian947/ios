iOS 近场支付与钱包凭证攻击面：不需要攻破设备也能花钱的那条路

本文是防御视角的分析与处置方法，不提供可利用代码，不包含中继装置制作、协议绕过步骤或任何可直接照做的攻击操作。面向需要评估资金与物理访问风险的用户、企业安全负责人与咨询场景。

1. 为什么这是一个独立的攻击面

前面的文章基本都在处理"软件里的错误"：#2 按系统层分，#81 按缺陷类别分，#82–#88 按被攻击的组件与通路分（驱动、App 配置、锁屏、分发、智能输入、微架构侧信道）。

支付与钱包这条路的特殊之处在于：大部分真实损失不需要设备上存在任何漏洞。

  • 中继攻击里，设备与卡片都完好无损，被欺骗的是"距离假设"。
  • 账户侧加卡滥用里，攻击者用的是发卡行的合法流程，Apple 与设备只是被绕过的旁观者。
  • 小额离线免密里，损失来自网络规则的配置选择，而不是实现缺陷。
  • 设备丢失场景里，风险取决于锁屏状态与数据保护等级（#84），而不是钱包本身是否有 bug。

所以这一层要评估的不是"iOS 有没有漏洞"，而是信任是在哪里被赋予的、由谁验证、能撤销吗。这是它值得单独成篇的原因。

2. 把这条栈拆开看

┌─ 商户 / 终端 ─────────────────────────────────────────┐
│  受理终端、在线网关、CVM 要求、离线限额、拒付处理       │
├─ 支付网络 / 发卡行 ────────────────────────────────────┤
│  令牌服务（DPAN 生命周期）、授权规则、风险引擎、Provisioning 审批 │
├─ 设备侧（本文重点）─────────────────────────────────────┤
│  Secure Enclave 上的个性化应用实例（密钥永不离开 SEP）  │
│  NFC 控制器与天线、安全通道会话                         │
│  钱包 App / Pass 库、Apple Cash、订单凭证              │
│  认证策略：面容 / 触控 / 密码 / 锁屏计时               │
├─ 账户侧 ───────────────────────────────────────────────┤
│  Apple ID 设备清单、iCloud 钥匙串、家庭共享、eSIM 与短信接收方 │
└────────────────────────────────────────────────────────┘

关键设计事实（决定后续所有判断）：

  1. 卡号被替换为设备账号（DPAN），每笔交易使用一次性密文，真实卡号不参与近场交互。
  2. 私钥在 Secure Enclave 内生成与使用，#9 与 #53 讨论过 SEP 密钥提取的能力上限——那是国家级实验室课题，不是这类欺诈的常规手段。
  3. 加卡的决定权在发卡行，Apple 只是把请求转过去。这条决定了最大风险面在账户侧。
  4. 小额离线可以不做在线授权，这是可用性换来的窗口，也是中继类风险的根因之一。

3. 四条通路，按"谁必须失败"分层

通路需要设备被攻破吗需要账户被接管吗现实损失量级防守杠杆位置
① 近场中继（把卡/设备的信号延伸到远处）否否单笔中小、可拒付支付网络规则、限额、终端 CVM 要求
② 设备丢失或被盗后刷否（但要已解锁/低风险状态）否有限，钱包受认证约束锁屏状态与数据保护（#84）
③ 账户侧加卡滥用（SIM 转移、短信/电话社工发卡行、在别的设备上把卡加进钱包）否是（核心）高、持续发卡行验证方式 + Apple ID 设备清单治理
④ App 与 Pass 层滥用（Core NFC 标签读写、登机牌/门禁/学生证、Apple Cash 转账欺诈）视情况否中，常表现为物理访问与社交工程应用审核与配置（#83/#86）、凭证管理

① 中继：被欺骗的是"距离假设"

公开研究与媒体演示早已把这类攻击从理论变成"可购买到的工具"话题；厂商与发卡行的回应主要落在限额、终端要求与风险引擎上。对个人而言这条路的正确心态是：它是支付网络的责任面，不是你的设备加固面。你的可操作项只有：知道哪些卡开了免密小额、以及出问题后有拒付通道。

② 设备丢失：真正起作用的是认证时机

钱包不是"丢了还能刷"的敞口：每次支付需要本机认证，设备被远程抹除、退出登录或被移除出账户后卡片即失效。这条通路的实际风险来自 #84 描述的窗口——设备处于已解锁状态、密码强度不足、或短期离开视线（餐厅、试用、代拿行李）。加固动作全部落在锁屏策略那一层，与钱包无关。

③ 账户侧：这一条才是高频高损失

典型形态是移动号码被劫持或通信被截获，再用"合法"的重置/加卡流程拿到钱包里的卡。相关事实：

  • eSIM 与号码携带是主入口之一：签约关系在运营商手里，不在 Apple 手里（蜂窝侧边界见 #72）。
  • 短信/通话类一次性验证是弱点：只要发卡行接受这类因子，设备之外的通路就足以完成加卡。
  • Apple ID 的设备清单与家庭共享决定了一张卡能被同步到哪些设备（#84 的密钥治理结论在这里同样成立：损失范围由密钥与账户治理决定）。

可执行的处置（这才是本文的重点动作）：

  1. 对每一个钱包内卡片回答：发卡行用什么方式批准加卡？如果只是短信或电话，视为高风险并优先处理。
  2. 号码侧：运营商账户加PIN/线下变更约束，禁止线上补卡与携号转移（各运营商名称不同，动作相同）。
  3. 账户侧：定期核对 Apple ID 设备清单，移除不认识的设备和不再使用的旧机（#80 月度清单里应加这一条）。
  4. 高价值个体的正确做法：主账户资金不放在可被手机号验证的卡上，与"敏感内容不落在这台设备上"是同一条原则的两个方向。

④ App 与 Pass 层：钱包不只是卡

钱包里还能装登机牌、酒店房卡、门禁与学生证、车钥匙。这意味着：钱包凭证是一次物理访问令牌。丢失风险的评估口径要改：不是"损失多少钱"，而是"谁能进入哪些门"。

App 侧的 NFC 读写（标签、会员卡、公交卡）主要风险不是协议，而是被诱导的交互——恶意 App 或诱导性页面让你完成一次不该做的绑定，这与 #86 描述的滥用 App 生态完全同构。

4. 缺陷类别映射（对齐 #81）

如果把这一层硬塞进 #81 的类别表，会发现行几乎是空的：

类别在这一层的出现频率说明
内存破坏类（UAF/越界/整数/双重释放）低不是这一层的主要损失来源
逻辑与授权误用主导加卡审批、拒付规则、离线限额、凭证撤销时机
信息泄露中商户/终端侧、通知与凭证可见性
密码学低（实现强，边界在密钥治理）参见 #88 的 SEP 物理研究上限
TOCTOU低不是本层瓶颈

这正是 #83 那句结论的重演："Apple 补丁修不到的那一片攻击面"——而且支付这块连"配置修补"都多在发卡行与运营商手里，用户能做的只有把流程变严。

5. 企业视角：这条面上真正能控的三件事

个人谈加固，企业谈治理。给企业安全负责人的三条：

  1. 公司卡与报销卡：离线限额、单笔免密额度、CVM 要求是可协商参数；把它当成配置项来审，而不是当成"员工自己的事"。
  2. MDM 能做什么：设备限制项可以禁止向钱包添加卡片、可以限制某些近场功能，但无法替发卡行做加卡审批。别把 MDM 当成资金风控（能力边界参见 #76）。
  3. 事件响应顺序：怀疑员工设备或号码被接管时，第一步永远是在支付网络与运营商侧锁死（挂失卡片、锁定号码），第二步才是设备取证。反过来会留下一段持续失血窗口。设备侧的证据在这里价值很低——交易记录与授权轨迹主要握在发卡行侧。

6. 五个常见误解

误解事实
"手机丢了钱就会被刷走"钱包支付要求本机认证；风险来自锁屏状态与设备被解锁，而不是钱包本身（#84）
"有令牌化就不用担心中继"令牌化解决的是卡号泄露，不解决"距离假设"被破坏；缓解在限额与终端策略侧
"Apple 批准了加卡"加卡由发卡行批准；攻击者走的是合法流程，所以加固点在验证因子而不是设备
"开强密码就够了"强密码保护设备，不保护账户与号码；账户侧接管可以在任何设备上重放
"MDM 能阻止这类损失"MDM 只能限制设备端功能，不能替代发卡行风控与运营商签约约束

7. 一句话结论

支付这条面是系列里少见的"设备安全做到 90 分也不会变好，账户与协议治理做到 90 分立竿见影"的领域。

  • 对个人：核对每张卡的加卡验证方式，锁好号码，定期清 Apple ID 设备清单，把免密小额额度调低。
  • 对高危个体：主资金账户不要挂在手机号可验证的卡上。
  • 对企业：把公司卡的限额与 CVM 当配置审，事件响应从"锁卡锁号"开始。

设备端你只要维持 #80 与 #84 的既有结论即可——真正需要动手的是设备之外的那两个环节。
